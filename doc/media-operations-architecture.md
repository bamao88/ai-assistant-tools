# 新媒体运营统一架构

更新日期：2026-10-23。本文是业务职责树和协作关系的唯一说明。命名与字段合同见 [固定规则](media-operations-contract.md)，38 个现役入口的完整去向见 [迁移计划](plan/media-operations-restructure.md)。当前运行清单仍见 [现役导航](media-operations-catalog.md)；下述整合尚未执行。

## 1. 按业务对象组织，再按交付调用能力

上一版按运营环节和动作罗列入口，导致作品管理、排期、记账和复盘分别维护同一条内容链路。现在以内容生命周期为中心，把共享方法作为内部模块，把能独立交付的专业工作流作为被调用能力。

```text
运营工作区：账号定位、角色、渠道、事实源、授权
│
├─ 内容管理 content-manage
│  ├─ 来源与作品登记：素材归属、关联、查重、内容入库
│  ├─ 选题与计划：候选、取舍、角度、简报、批次
│  ├─ 作品与版本：作品 ID、制作输入、选定版、状态
│  ├─ 排期与渠道事实：账号分配、计划、提交、定时、公开记录
│  ├─ 指标与分析：官方导出入库、快照、口径、表现与缺口
│  └─ 复盘与改进：原因假设、改进动作、采用、效果复查
│
├─ 知识管理：原始资料 → 观点 → wiki / pending → 检索与修订
├─ 客户管理：人员、客户和学员资料 → 识别、记录、同步与分析
│
└─ 被按需调用的专业工作流与平台执行
   ├─ 调研：账号调研、产品调研、专题调研
   ├─ 来源处理：平台正文/列表、音视频转录与解析
   ├─ 制作：文章、视频、卡片、配图、图解、项目制作编排
   ├─ 平台物料：标题、封面字、平台正文、标签、发布包
   └─ 平台执行：认证/切换、上传/草稿/提交、评论/回复
```

这是职责树，不是要求把每个节点注册成 Skill。内容管理的六个模块共享作品与渠道对象，用户不必依次点选“入库、排期、采数、分析、复盘”。专业工作流也可以接独立请求：只写文章、只改标题、只取字幕时，直接完成该项，不强制创建正式作品或走完整运营流程。

初始化负责建立或补齐账号定位、对标资料、素材索引与运营底座，连接已有事实源并安排首轮内容验证；完成后，日常管理交回上述领域入口。

## 2. 内容管理的六个模块是一套闭环

| 模块 | 处理的对象与产出 | 与其他模块的交接 |
|---|---|---|
| 来源与作品登记 | 登记来源、素材、候选或正式作品，复用去重键与现有 ID | 来源处理负责取回材料，本模块记录归属与关联 |
| 选题与计划 | 判断做什么、为什么做、面向谁，形成范围与制作简报 | 需要证据时调用调研或知识检索；按明确决定推进作品 |
| 作品与版本 | 素材清单、确认决定、制作状态、选定稿及资产关系 | 调用专业制作工作流，接回产物与检查结果 |
| 排期与渠道事实 | 一个作品各账号的计划及真实投稿/发表状态 | 发布执行提供观察和回执，本模块按证据记账 |
| 指标与分析 | 官方原表、按发布 ID/时点/口径的快照、可比分析及缺口 | 从各渠道事实定位作品，供复盘判断使用 |
| 复盘与改进 | 基于证据的原因假设、改进动作、采用状态和效果复查 | 返回下一轮选题、计划或制作约束，形成循环 |

排期、内容入库和数据分析归属于这个业务入口；它们以模式或 reference 被按需执行。单篇和一批内容采用同一核心方法与事实模型，不另建批量版本的 Skill 或运营总账。

### 三种“入库”有共同入口体验，也有各自数据合同

| 类型 | 写入对象 | 去重/引用依据 |
|---|---|---|
| 内容与素材入库 | 来源索引、候选、作品及其资产关系 | 来源、已有作品 ID、素材及版本 |
| 知识入库 | 提取观点、wiki、pending 和知识关系 | 原件、观点、已有知识页及处理日志 |
| 运营数据导入 | 指标快照、官方原表引用及导入记录 | 发布 ID、账号、采集时点与指标口径 |

内容管理负责第一项和第三项；知识管理负责第二项。用户只说“入库”时先结合当前对象判断，不能把原文、成稿和指标表送进同一条写入命令。一个任务同时涉及多类入库时，领域入口组织交接并保留引用，不复制资料。

## 3. 每类事实只有一个责任方

| 事实或产物 | 唯一责任方 | 其他层怎样使用 |
|---|---|---|
| 账号定位、人设、真实身份与权限配置 | 项目已有事实源 | 领域入口加载；工具不按目录名猜账号 |
| 候选、作品身份、生命周期、选定版本关系 | 内容管理模块 | 制作工作流读输入、返回实际产物 |
| 稿件、口播文字、图片、视频及制作检查 | 对应专业工作流 | 内容管理关联版本；平台物料按确认稿派生 |
| 平台标题、正文、标签等最终字段 | 平台物料模块及其项目事实映射 | 发布只核对和填写，不在后台另写一版 |
| 计划与各渠道发布记录 | 内容管理模块 | 执行器返回实际观察，不按退出码推断公开成功 |
| 官方指标快照、分析、复盘和改进状态 | 内容管理模块 | 改进反馈到选题和制作；发布器不维护另一套数据表 |
| wiki、知识决策、知识索引与日志 | 知识管理模块 | 内容管理和调研以来源引用消费 |
| 客户、学员及其业务记录 | 客户管理模块 | 内容运营需要材料时按授权取用，不将客户资产改成内容台账 |

“唯一责任”落实到字段与原文件：MiMi 继续用现有 `item.copy`，ZH 可继续用 `publish_<account>.md`；共享方法规定唯一选定稿和引用关系，不强制所有项目复制出同名文件。专业工作流可以按项目合同修改被授权的正文文件；生命周期模块维护状态和版本关系，不重复改写正文。

## 4. 职责与复用范围是两个维度

“通用”和“项目专属”不是职责树里的上下两层。领域管理、专业制作、平台执行和引擎的每一层，都要检查哪些规则共同适用、哪些差异由媒介或项目引起。拆分单位是规则、模块和实现，不能按旧 Skill 的项目名前缀整包定归属。

| 变化来源 | 应维护的内容 | 归属与复用 |
|---|---|---|
| 共享方法与不变量 | 输入如何成为产物、事实与证据、状态关系、完成条件 | 公共工作流及其 references/引擎；只维护一份 |
| 媒介、平台、风格或存储特化 | 卡片分页、口播可说性、平台字段、视频配方、wiki 格式、台账读写适配 | 按任务选用的共享模块或 adapter；限定使用场景仍可以跨项目通用 |
| 项目政策与配置 | 定位、人物、人设、品牌、来源政策、成功标准、选定模板、必要的独有编排 | 项目规则与资源绑定；确有独有完整流程时才有项目前缀入口 |
| 运行事实与状态 | 原文、作品与账号 ID、选定版本、发布和指标、会话、素材使用账本 | 原项目/运行环境的事实源；复用方法不等于共享数据或权限 |

例如“知识卡片”是一种通用制作工艺，“小红书尺寸”是共享平台特化，“WXP 人物与黑粉品牌”是项目选择，“本次选定封面和素材使用次数”是运行事实。它们不能因为第一次一起在 WXP 使用，就整体归为项目专属。

### 各运营环节都横向拆分

| 运营环节或业务对象 | 共享方法 | 可复用的特化 | 项目保留的差异与事实 |
|---|---|---|---|
| 账号初始化与定位 | 资料盘点、定位假设、资源关系、首轮验证 | 平台起号资料与内容形态 | 真实受众、品牌、投入、账号、事实源 |
| 调研与证据 | 问题拆解、来源登记、主张与证据、冲突和缺口 | 账号/产品/专题报告方法、来源适配 | 当前问题、项目经验、取舍偏好、落点 |
| 选题与计划 | 信号→候选→价值/准备度→取舍→简报 | 搜索、平台巡看、内容形态评估 | 人设适配、优先级、决策权、候选池 |
| 内容生命周期 | 来源、作品、版本、选定稿、依赖与交接 | 现有文件/台账的字段映射 | 原 ID、目录、状态值、独有编排 |
| 文章、口播、视频 | 事实锁定、结构与表达、制作和质检 | 长文、可说性、时间轴、画面配方 | 作者经历、表达偏好、人物与选定样例 |
| 卡片、封面、图解 | 信息组织、图文分工、生成/排版、整组检查 | 知识卡片、markdown 渲染、封面 kit、图型 | 品牌、人物原图、已采用风格、资产账本 |
| 平台物料与分发 | 确认稿派生、标题/封面字/正文分工、读回与回执 | 平台硬限制、字段、发布/认证环境 | persona、CTA、渠道账号、授权停止点 |
| 数据与复盘 | 原表证据、口径/窗口、缺失、比较、假设、改进行动 | 各平台导出解析与发布 ID 关联 | 本项目目标、账本、实验和采用事实 |
| 知识管理 | 索引→全文→引用、查写分离、演进/矛盾、索引日志一致 | wiki/pending/schema 及采集适配 | 知识空间、主 profile 保护、裁决权和资料 |
| 客户管理 | 候选检索、证据匹配、去重订正、镜像/回写分离 | 数据源和外部表适配 | 学员/就业/线索政策、允许回写字段与私有数据 |

内容管理六模块的共同方法不能在通用、ZH、MiMi 再各写一份；同样，通用研究、分页和视频质检也不能在项目制作包中各写一份。“全局安装”“源码已放 tools”“根路径可配置”都不足以证明跨项目可用。

### 不把共享模块全部注册成 Skill

有独立交付与持续直接需求的完整工艺保留公共入口，如专题研究、知识卡片制作、封面设计；口播文字编辑可作为视频制作的独立请求模式。平台规格、证据合同、wiki adapter、项目 profile 和检查政策作为按需模块，不逐项增加 Skill。

项目入口也不按名称对称生成。WXP 小红书和公众号可直接调用公共制作方法并加载自己的上下文；个人风格资料本身不需要一个“项目内容制作”大入口。ZH、MiMi 保留确有数据接入或完整生产编排的项目入口，其公共部分仍回到共享来源。

## 5. 一次任务怎样装配并完成

目标调用关系如下；这是一套待实施的加载合同，当前运行入口尚未切换：

```text
用户的任务 + 当前项目（可无）+ 原材料 + 交付位置/停止点
  → 领域入口或可直接调用的专业工作流
  → 解析项目绑定；不从通用引擎的默认账号反推项目
  → 按需加载：共享方法 + 媒介/平台适配 + 项目差异
  → 调同一执行核心，完成实际交付和检查
  → 返回产物/证据/实际状态，按授权写回原事实源
```

绑定只引用已有资料，按任务包含：项目根与数据映射、来源及选定输入版本、作者/品牌/风格引用、目标平台和具体账号、输出位置、可写范围与授权停止点。身份不需要时不强行要求账号；只有原材料和明确输出目录的独立研究或卡片请求，也应能够完成。

通用工作流不得缺省读写 ZH、假扮其作者或使用其人像。缺少必要业务身份时明确定位缺项；不依赖身份的部分继续完成，最终仍以正向交付验收。

### 方法只有一份，加载有明确路径

完整工艺的方法和质量门归属其公共 Skill；跨多个业务域共同使用的对象合同、证据规则、平台规格放在 tools 内 `shared/` 的规范路径。单个工艺独用的 reference 留在原工作流，不为了目录对称再造共享包。代码共性放共享引擎，项目政策通过显式参数或适配器传入。

在现有 `registry.yaml` 中增加一种 `uses_methods` 依赖声明，指向实际的仓库相对文件；不另建一份模块注册表。脚本依赖继续使用 `uses_engines/uses_vendor`。调用整个工作流指向其 `SKILL.md`，只复用局部方法指向其规范 reference，不能借局部引用跳过完成合同。检查器需同步验证文件存在、源码引用一致和依赖无环；当前检查器尚不具备这项能力。

源码之间使用规范源码的相对引用，不依赖某台电脑的 `~/.agents/skills` 安装位置。项目 profile、品牌资源可维护于集中源码中的项目资源包；私有事实、凭据、会话及使用账本留原项目或运行目录，绑定不复制其值。

### 规则不能按读取先后互相覆盖

来源真实性、权限、平台硬限制、数据归属和选定版本关系是不变量。媒介规则只作用于对应产物；项目可选择声明为可配置的风格、模板、配方、字段映射，并增加更窄的业务约束，不能静默覆盖公共核心。出现冲突先确认责任方并统一方法，不能简单宣布“项目 Skill 优先”。

### 完整交付的边界

- 账号、产品与专题调研保留各自完整报告；证据方法共同维护，产品调研仍可服务非自媒体任务。
- 来源采集和音视频解析交回材料后，原文章/研究任务继续完成；只取字幕则到素材交付停止。
- 文章起草、重写、润色是同一工作流的模式；口播文字请求在转录/剪辑/成片审批前分流，交付文字即停止。可说性只用于实际说出口的文字，不默认改写文章。
- 完整知识卡片工艺从 WXP 提升为公共工作流，保留分析、连续稿、解释单元、分页、图文构想、生图、整组检查。markdown 卡片排版仍接收已有稿件进行渲染，两者不相互替代。
- 封面公共工作流复用 brief、生成/渲染与质检；WXP 品牌、ZH 人像和 kit、MiMi 封面固定内容由项目提供。kit 显式绑定资源根与状态根，不能将素材账本写回共享源码目录。
- MiMi 完整批量生产保留项目编排；公共来源查重、媒体校验、导出和审阅包实现抽出，版本与排期仍归内容管理。
- 平台物料支持单项标题/正文和整包请求；公共平台适配不得默认采用 ZH 或 AI PM 身份。
- 知识方法与 wiki 存储适配公共化后，用自己的知识空间验证；客户域先抽共性方法，保留 ZH 业务入口，不因架构对称便承诺通用 CRM 已可用。

## 6. 平台执行与管理的权限边界

内容管理可以修改本地计划、记账和分析，不能据此获得平台上传、定时或提交权限。内容发布入口按请求只处理认证/账号切换，或进一步上传、建草稿、提交；只检查登录时不触发发布。

小红书认证模块复用同一账号选择和身份核对规则。登录动作按本次目标环境适配：发布使用当前已绑定的正式浏览器，采集工具在其自身环境核验；不把一个工具的登录状态搬作另一个环境的身份。取消互相冲突、未经本次选择的默认登录路线。平台互动保持独立任务范围，采集、点赞、评论和发布分别按实际授权执行。

合并后的知识入口默认检索只读；入库、裁决、修订与沉淀按明确请求和原有写入合同执行。入口统一不等于权限合并。

## 7. 落地与维护

目标入口及现役能力去向只在迁移计划维护，实施后由 `registry.yaml` 生成现役导航。旧的 32 个目标和后续 21 个门面均不再是执行指标；本轮 [复用审计](plan/media-cross-project-reuse-audit-2026-10-23.md) 记录现役证据，不另立命名规则。

实施先做双向拆分：项目包里的公共方法抽出，公共包里的作者身份/品牌默认迁回项目，再消除方法冲突、更新调用并删除重复。每次抽取必须验证另一个项目或无项目任务真正能完成，不以文件搬迁或参数化数量作为完成条件。跨项目并行运行不得修改全局风格工作副本或共写资产账本。

保持既定顺序：先整理模块、合并方法、更新调用方并删除重复入口，验证完整任务后，最后统一项目/Skill 名称。所有自有标识小写，不留旧名兼容。目录、安装和协议文件的细则按固定规则执行。

当前只完成架构、规则和计划修订，源码仍为 38 个现役入口，未执行合并或重命名。已有源码和安装检查只是 `logic/contract`，尚未完成本架构下的真实业务回放或独立 Agent 验收。
