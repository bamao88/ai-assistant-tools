# 官方表格采集：已纠正的做法与实际经验

开始本项目的平台采数前，先读本页，再按 [共享采集流程](/Users/xpw/.agents/skills/content-operations-ledger/references/platform-reconciliation.md) 操作。本页记录本项目实际发生的偏差与证据；共享文件维护可复用的导出、下载和核对步骤。仅用已有数据复盘时不强制重新采集。

## 当时偏差在哪里

2026-10-20处理缺失数据时，前段工作花在管理页卡片及页面数字的读取／核对，没有把“下载官方原表，再处理表格”作为表现采集的明确主流程。负责人随后明确纠正：“你在做数据采集的时候应该是采用各个平台官方支持的数据导出按钮，导出表格，在对表格进行处理啊”。身份、状态与排期仍需要页面核对，但它们不替代表现数据的官方表格。

当次小红书第一次点击官方导出，另发生了**浏览器下载事件等待超时**：`Timed out after 30000ms waiting for download.`。随后核对下载目录确认文件已落盘，没有重复导出。因此已知的是“事件没有按预期返回”，不是“平台导出失败”；底层为什么没有收到事件尚未确认，不能扩大成所有浏览器工具都不支持下载。

## 已验证的修正路径

| 具体经历 | 当时不能据此做的判断／动作 | 后来成功的做法与证据 |
| --- | --- | --- |
| 先读取管理页卡片、寻找页面指标，负责人要求改用官方表格 | 不能把页面指标抓取当作这一轮官方表现采集完成，也不能因DOM容易读就跳过导出 | 核身份后优先确认官方导出入口与范围；下载后处理原表。最终小红书／抖音各1份XLSX，B站12份CSV，见 [当次回填记录](/Volumes/ExtSSD2601/MiMi_TV_Operations/reviews/2026-10-20-live-reconciliation/README.md) |
| 小红书`waitForEvent('download')`等30秒后超时，实际文件已下载 | 不能直接宣布导出失败、换抓卡片数，或立即再点一次导出 | 核实下载目录新文件后归档，记录等待超时及实际文件时间依据；[下载回执](/Volumes/ExtSSD2601/MiMi_TV_Operations/reviews/2026-10-20-live-reconciliation/xhs-export-receipt.json)明确“未重复导出” |
| B站从稿件管理进入数据中心，父页内有嵌入的分析区域；需要切到具体稿件的数据总览 | 不能把父页面／趋势模块看不到按钮当作“没有导出能力”，不能混用不同稿件的同名CSV | 使用页面实际出现的分析区域／子页，进入稿件分析→切换视频→数据总览→导出数据。逐条核当前BVID，记录源页和下载名后归档；[12条回执](/Volumes/ExtSSD2601/MiMi_TV_Operations/reviews/2026-10-20-live-reconciliation/bilibili-export-receipts.json)可追溯 |
| B站下载文件多次叫“近30天播放量数据趋势.csv”，有系统追加的序号 | 不能按文件名猜是哪条稿件、把旧文件当新下载，或把“30天”当全部文件实际范围 | 点击前登记目录基线和当前稿件；识别本次完成的新文件，读取表内日期，再按BVID保存，不覆盖以前原件；操作路径与每次范围见同一回执及CSV |
| 首份B站小丑鱼预检导出只记录了父页URL，URL不含BVID | 不能声称每份源URL都已直接证明稿件，也不能只靠归档文件名认定身份 | 该份以 [当时选中稿件的标题／首次时间](/Volumes/ExtSSD2601/MiMi_TV_Operations/reviews/2026-10-20-live-reconciliation/bilibili-official-export-view.txt) 与 [稿件清单BVID](/Volumes/ExtSSD2601/MiMi_TV_Operations/reviews/2026-10-20-live-reconciliation/bilibili-inventory.json) 对照；原CSV全“-”未记成绩。后续11份源URL带BVID。以后优先保留带BVID分析页；父页不带时须同时保存这组匹配证据 |
| 小红书新稿页面为“-”，Excel相同列却给0；B站新稿CSV全为“-” | 不能统一补零或用实时卡片数替换；小红书原表已有0也不能删除改写 | 原表原值保留，小红书5项附统计未就绪证据及quality标记，B站缺值不造指标；进入后续采集待办。见 [质量修正记录](/Volumes/ExtSSD2601/MiMi_TV_Operations/reviews/2026-10-20-live-reconciliation/availability-completion.json) |
| 旧抖音记录把账号号填为稿件ID；导出作品名称还附带正文 | 不能把账号ID当作品ID、只按文件名或截断标题强行匹配 | 用实际标题／正文、首次发布时间及可见原生稿件ID核对；不暴露ID时记录复合匹配限制。账号ID误填已审计纠正，未猜测补齐全部作品ID |

上表是当次经验，不是当前后台永远不变的界面合同。入口改变时按真实可见页面更新证据，不能照旧坐标或猜接口地址操作。

## 采集成功的完成依据

按共享流程完成“核账号与范围→官方按钮→确认新文件完整落盘→原件归档和回执→核标题／时间／BVID／字段／日期→归一化→入库”。点击按钮或收到下载事件都不是单独的完成证明；不能以另存页面、自己拼一个CSV、截取卡片数字冒充官方原表。

小红书原表首行是合并的导出说明，第二行才是字段；抖音第一行是字段，作品名称可包含正文；B站CSV有BOM、范围合计和逐日行。解析需用实际字段和合并单元格语义，不按三个平台同一模板取第一行。B站“累计”按文件内范围记录，不冒充生命周期累计，逐日和合计不重复相加；时长单位有官方说明后再标准化。通用字段规则见 [数据合同](/Users/xpw/.agents/skills/content-operations-ledger/references/data-contract.md)。

下载或平台仍未给有效数据时，保存原页／原件和具体缺口，写下次动作；如实报告哪一步未完成。此次Skill修订是历史经验整理和流程检查，不能写成重新导出成功或独立定时采集E2E通过。
