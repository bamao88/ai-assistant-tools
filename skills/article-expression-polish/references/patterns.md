# 文章表达润色模式

本文件集中保存文章表达润色规则。这些规则原本分散在来源型长文写作、旧的最终润色入口、项目写作流程文档、共享写作流程和账号复盘里。

## 核心定义

机器腔不是一组禁用词，而是一种写作姿态：

- 作者站在文章外解释文章在做什么，而不是让事实自己推进。
- 段落里有预热、过渡或总结句，但没有新的信息负载。
- 文字看起来被过度工程化：整齐对比、强行三点、加粗标签、重复脚手架。
- 文章带着聊天残留：用户反馈、修改过程、助手自述。
- 文本通过模糊主体、模糊来源或抽象名词回避责任。

搜索可以帮助发现症状，真正的检查要回到段落级删除和重写。

## 主要检查

### 1. 信息负载检查

编辑前先标出不能改变的内容：

- 事实、来源归属、姓名、数字、日期、引用。
- 标题立场和小节顺序。
- frontmatter、链接、图注、代码块。
- “可能”“大概”“据说”“据我了解”等不确定性标记。

如果一句话既别扭又绑定事实，保留事实，重写句子，不要悄悄加强原有判断。

### 2. 删除检查

删除或合并只是在表演结构的句子：

- “这里的关键是……”
- “这一段真正讲清楚的是……”
- “视频里有一页很直白……”
- “后面所有复杂功能，都可以放回这里理解……”
- “接下来我们看……”
- “这件事真正有价值的地方是……”
- “从这个角度看……”

这些句式不是永远不能用。判断标准是：如果下一句可以独立成立，这个包装句就失败了。

### 3. 真实主语检查

让真实对象成为句子主语：

| 问题写法 | 更好写法 |
|---|---|
| 这里说明了 Clay 的系统很复杂 | Clay 把 Agent 任务拆成可恢复的工作流 |
| 这段提示词里有五个要素 | 这条提示词指定了检查对象、频率、动作、汇报规则和停止条件 |
| 视频里有一页很直白 | Jason 的幻灯片把变化写成 `Chat -> Workstream` |
| 这里的关键变化是工作单元 | 一个 PR、一个 launch、一个 Slack 反馈入口，都可以各占一条 thread |

通常不是“换一个词”就能解决，而是要“让事实自己推进”。

### 4. 信息密度检查

每个段落至少应该包含下面一种内容：

- 事实
- 机制
- 例子
- 边界
- 来源判断
- 基于材料的判断增量

如果一个段落只是在解释上一段为什么重要，就合并或删除。

### 5. 结构和深度检查

文字干净不等于文章自然。草稿太均匀、太完整、太急着总结，也会有机器腔。

重点检查：

- 模板式开头：强对比后接“这篇要讲的就是……”。
- 资料堆叠式开头：连续交代来源标题、讲者身份、文档对象和术语定义，正文主题迟迟没有出现。
- 每一节都是同一种形状：问题、解释、方案、结论。
- 每一节都用整齐金句收尾。
- 同一个论点在开头、中间和结尾反复重说。
- 结尾从一个案例过快上升到普遍规律。
- 结尾为了“正常收尾”而补一段总结、升华或口号，材料本身已经结束却继续解释意义。
- 事实、数字或工程词只作为可信度装饰，没有颗粒度、基线、失败模式或来源边界。
- 为了显得有用，在正文里替读者提炼“应该学到什么”“应该怎么用”，把来源整理写成讲义或行动清单。

修改方式：

- 材料本身不均匀时，允许小节节奏不均匀。
- 开篇先落到文章要精读的对象、问题或变化；必要背景分散到读者真正需要的位置。
- 有些小节可以停在事实上，不必每一节都闭环。
- 保留真实的不确定、取舍和未解决问题。
- 如果草稿缺少机制，回到一手来源；不要把二手摘要润色成假深度。

## 中文机器腔模式

### 元叙事

常见表现：

- “这里的关键是”
- “这里不做完整配置手册”
- “这篇只解释……”
- “这里先不展开……”
- “这一点很重要”
- “这句话的意思是”
- “可以这样理解”
- “这一段真正讲清楚的是”
- “这段的层次很清楚”
- “某某开场给了一条线”
- “演讲按……往前推”
- “某某给了一句很直接的判断”
- “某某把……说得很直接 / 讲得很直接”
- “这句话把……讲出来了”
- “这段原话很重要”

修改方式：

- 去掉解释外壳。
- 直接写主体和动作。
- 把解释放进事实链条里。
- 需要限定范围时，用标题、小节顺序或对象结构承载，不在正文里写作者的取舍说明。
- 材料顺序不要写成导览词；让接口、产品、系统或人物动作成为句子主语。
- 引用前只保留必要来源归属；引用后直接写这句话对应的事实场景、系统动作或变化，不评价引用本身。

### 空转过渡

常见表现：

- “接下来”
- “下面”
- “回到开头”
- “从这个意义上说”
- “与此同时”
- “值得注意的是”
- “需要指出的是”

修改方式：

- 直接进入下一段。
- 只有过渡词真的改变时间、来源或逻辑时才保留。

### 假深度和揭示句

常见表现：

- “真正”
- “本质上”
- “这才是”
- “最值得关注的是”
- “背后的真实信号”
- “不只是 A，更是 B”
- 反复使用“不是 A，而是 B”

修改方式：

- 如果对比真实存在，只说一次。
- 如果词语只是在增加戏剧感，删掉。
- 不要在同一段堆叠多个揭示标记。

### 多余拆句

机器草稿常把一个想法拆成两句：

```text
长期工作需要定期回到现场。
Jason 在视频里用了一个 PR 例子……
```

如果第一句没有新增信息，直接从第二句开始。

### 翻译腔和名词化

常见表现：

- “上下文边界的管理”
- “工程层面的解法”
- “这个判断本身”
- “能力的释放”
- “价值的体现”

修改方式：

- 还原动作主体和动词。
- “团队管理上下文边界”
- “工程师把规则写进测试”
- “这个判断改变了排序”

### PPT 和咨询腔

注意这些词：

- 赋能
- 抓手
- 闭环
- 落地路径
- 颗粒度
- 维度
- 价值主张
- 方法论沉淀

只有来源本身使用这些词，并且文章正在分析这个词时才使用。

### 公式化列表

机器草稿经常把内容强行整理成三点或五点。列表不是问题；当来源本身有列表，或工作流确实需要步骤时，列表很合适。问题是每一节都用编号结论收尾。

修改方式：

- 真实流程、组成要素、API 或判断标准可以保留列表。
- 浅层列表改回自然段。
- 加粗小标题只在确实提升操作文档可读性时使用。

### 自问自答式推理

常见表现：

- “那到底是 A 还是 B？答案是……”
- “这个设计聪明在哪？它……”
- 连续几个设问句，作者马上自己回答。
- 前文没有真实提问，后文却用“答案是”“边界是”“关键是”公布结论。
- “某某讨论的，就是这个问题 / 这条边界：……”

修改方式：

- 直接陈述事实或判断，不先搭一个虚拟问题、边界或悬念。
- 只有问题真的对应读者疑问时，最多保留一个。
- 把问题链改成一句包含关键变量的紧凑判断。

### 负向排比和整齐对比

常见表现：

- 反复使用“不是 X，而是 Y”
- 结尾写成“A 决定下限，B 决定上限，C 决定……”
- 相邻段落都使用同一种对比节奏。

修改方式：

- 只有当对比是最清楚的表达时，保留一个。
- 其它部分改成正向直接陈述。
- 不要把句式对称当成论证。

## 中文公众号案例模式

这些规则来自多轮中文文章修改。目标是公众号或平台文章时，它们比通用关键词禁用更重要。

### 评论前文

常见表现：

- “上面那张图画得很干净……”
- “前面那段说的就是……”
- “我们刚才提到的……”

修改方式：直接写下一个事实。除非回指能带来新证据，否则不要要求读者回头重新评价上一段。

### 引用和原话包装

常见表现：

- “某某在视频里给了一句很直接的判断：”
- “这句话把问题讲清楚了。”
- “这段原话真正值得看。”
- “下面这句很关键。”

修改方式：

- 引用前只写必要来源归属，例如“Isabella 的原话是：”。
- 引用后写原话对应的具体案例、条件变化或系统动作。
- 不用“直接、重要、关键、清楚”评价原话；如果原话确实重要，让后面的事实链条承担解释。

例：

修改前：

> Isabella 在视频里给了一句很直接的判断：`when the model moves...`
> 这句话把 Agent 运行系统的维护难度讲出来了。

修改后：

> Isabella 的原话是：`when the model moves...`
> Sonnet 4.5 到 Opus 4.5 之后，模型行为已经改变，harness 还在执行旧补丁，Agent 会被旧规则拖慢。

### 列表前预告列表

常见表现：

- “三件事最值得记”
- “下面我列五点”
- “几个最容易混淆的词”
- “那段代码当时叫法很多：X、Y、Z”

修改方式：直接列出来。标题、项目符号或标点已经能告诉读者下面是列表。

### 教师腔第二人称

常见表现：

- “下次你看到……”
- “建议你……”
- “记得……”
- “你会发现……”
- “你要学会……”
- “读者应该带走……”
- “这篇文章帮助你理解……”

修改方式：用客观句，或把用户、产品、系统作为主语。分析文和学习笔记不要扮演老师，除非格式本来就是教程。

### 替读者完成学习

常见表现：

- “读者应该带走的判断是……”
- “你需要从这里学到……”
- “这篇文章会让你明白……”
- “建议你把这些问题列出来……”
- “对正在做 X 的人来说，这场分享最值得拆开的不是 A，而是 B。”
- 在结尾机械追加“行动清单”“启示”“怎么用”，而来源本身并不是教程。

修改方式：

- 把“收获”改成来源对象、人物、系统或案例的具体动作。
- 文章可以讲清事实、机制、边界和判断依据，但不要替读者安排结论和用途。
- 开篇如果要交代内容范围，直接写来源讲了哪些对象、动作和问题；不要先替读者说明这些内容为什么值得看。
- 如果确实需要说明读者价值，放在选题卡、摘要或内部 brief；公开正文里让事实链条承担学习效果。
- 只有用户明确要求教程、清单或操作建议，或来源本身就是教程时，才使用第二人称和行动步骤。

例：

修改前：

> 读者应该带走的判断是：哪些是你的产品判断，哪些只是运行时负担。

修改后：

> Claude Managed Agents 把 session、sandbox、events、凭据和观测收进平台层；产品侧继续定义任务、上下文、工具边界和成功标准。

### 戏剧化铺垫

常见表现：

- “结果听到一半，我手里的笔停了一下”
- “我盯着那个画面想了一会儿才反应过来”
- “最让我意外的一段”
- “那个最容易被忽略的真相才显出来”

修改方式：把有用的方法、判断或场景放在前面。知识写作不需要靠小说式悬念证明价值。

### 问题链

连续三个以上设问，通常会像模型在用问题推进推理。

修改方式：改成一句紧凑判断，或者只保留下一段真正回答的那个问题。

### 强行回扣开头

常见表现：

- “回到开头那个问题”
- “正如文章开头所说”
- “还记得我们一开始说的吗”

修改方式：通过具体场景、来源原话或最终判断回到主题，不要宣布环形结构。

### 刻意升华收尾

常见表现：

- “这也许就是……的真正意义。”
- “最终，这件事提醒我们……”
- “从这里开始，行业会……”
- “读完这条视频，最该记住的是……”
- 正文已经讲完来源案例后，结尾又补一段泛泛总结、价值判断或行动建议。

修改方式：

- 来源整理文可以停在最后一个事实、案例、边界或来源链接上。
- 如果结尾没有新增事实、机制、边界或判断依据，删掉。
- 需要收束时，用来源中的具体对象或变化收束，不做励志式、行业趋势式或教学式升华。
- 不要为了文章“完整”而写一个单独的漂亮结尾。

### 过度加粗的小标题句

机器草稿经常把加粗主题句当成伪小标题。中文公众号正文里，这会让页面看起来分块很多，但并不会更锋利。

修改方式：只给真正的核心判断加粗。如果一篇文章里加粗句很多，大多数应该改回正文或正式小标题。

### 轻量编辑：短段落，少脚手架

公众号正文主要在手机上阅读。一个技术上清楚的段落，如果铺垫太多，仍然会显得累赘。

优先：

- 一个段落只讲一个想法。
- 格式允许时，把重要判断单独成行。
- 先直接给判断，再解释。
- 用事实过渡，少用作者旁白过渡。

删掉：

- 评价性填充：“他的逻辑很硬”“这个说法很清楚”“这点很有意思”。
- 转述性填充：“他举的例子”“下面这句”“换句话说”。
- 没有边界作用的程度副词：“很”“挺”“某种程度上”。
- 暴露修改过程的编辑注释括号；应该直接写正确句子。

### 表达润色后的过度修正

不要为了修掉“太圆滑”，把草稿改得松散。

注意：

- 每个数字或判断后面都加防御式不确定。
- 太多“他说 / 他没说 / 他提到”，让文章像原始笔记。
- 用密集的随意比喻，把技术分析改成表演。
- 标题用了数字，第一段却马上弱化这个数字。
- 边界只写成免责声明，没有变成更深入的问题。

修改方式：不确定性只在关键处使用一次；之后要么追机制，要么删掉这个判断。

## 通用机器腔信号

这些旧检查项仍然有用，尤其适合受英文写作影响的中文草稿：

- 重要性膨胀：`pivotal`、`transformative`、`landmark`、`标志着重大转变`。
- 模糊权威：没有来源归属的 `industry observers`、`experts believe`、`有观点认为`。
- 英文草稿里浅层的 `-ing` 逻辑：`highlighting`、`underscoring`、`reflecting`、`showcasing`。
- 宣传腔：`vibrant`、`groundbreaking`、`breathtaking`、`seamless`、`powerful`。
- 绕开朴素系动词：可以用 `is` 或 `has` 时，硬写 `serves as`、`stands as`、`boasts`、`features`。
- 过度三段式：`innovation, efficiency, and transformation`。
- 为了避免重复，不断给同一个对象换名字。
- 虚假的范围结构：`from X to Y`，但 X 和 Y 不是一个真实光谱。
- 该说明行动者时，使用被动句或无主句。
- 过度使用破折号、表情符号、加粗。
- 聊天机器人残留：`I hope this helps`、`of course`、`let me know`。
- 发布文本里残留知识截止时间免责声明。
- 泛泛积极结尾：`the future looks bright`、`exciting times ahead`。

## 对话残留

永远不要发布：

- “用户指出……”
- “上一版的问题是……”
- “这里不应该这么写……”
- “我已经修改……”
- “这次我们要避免……”
- 修改说明、评分、检查总结或流程道歉。

用户反馈用于修改文章，不用于成为文章内容。

## 反馈学习

用户指出机器腔、奇怪表达或不符合写作风格时，把反馈当作偏好信号，而不是只当作本句修改要求。

沉淀前先分类：

- 只影响当前事实、来源或上下文的，不写入规则。
- 能复用到后续文章表达的，写入本文件的相应模式。
- 只属于某个账号/作者口吻的，写入项目风格文件，不污染通用规则。
- 属于选题、结构、来源处理或素材取舍的，交给来源写作技能处理。

写入规则时要提炼成中性表达：

- 记录“问题表现”，不要记录用户抱怨。
- 记录“改法”，不要记录聊天过程。
- 给一个短例子，避免后续代理只记抽象原则。

例：

```text
问题表现：作者站在文章外评价一句话“很直白”“很具体”，但没有增加事实。
改法：把被评价对象变成句子主语，让事实自己推进。
例子：不要写“这页很直白”，写“Jason 的幻灯片把变化写成 `Chat -> Workstream`”。
```

## 过度人味化

文本被“人味化”之后，如果看起来像刻意表演，仍然会有机器腔。

注意：

- 突然出现与文章口吻不匹配的俚语。
- 第一人称标记过多。
- 直接复制风格指南里的口头禅。
- 把严肃技术段落改成随意闲聊。
- 每个段落都用段子收尾。
- “说白了”和“不是 X，而是 Y”叠在一起。

好的表达润色通常更安静：包装更少，主语更具体，动词更干净。

## 案例库

### 来源阅读里的元评论

修改前：

> 视频里有一页很直白：Chat -> Workstream。Jason 把它拆成三步……

修改后：

> Jason 的幻灯片把变化写成了 `Chat -> Workstream`。一个 workstream 对应一条能长期存在的 thread……
