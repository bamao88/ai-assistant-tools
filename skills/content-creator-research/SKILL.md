# 内容账号与对标研究

把公开账号与作品资料变成可追溯的研究结论，让用户知道值得借鉴什么、适用于谁、迁移还需要验证什么。按用户的问题决定深度；不以指标门槛、固定采集数量或报告篇幅决定是否可以研究。

## 选择研究范围

| 用户意图 | 执行范围 | 按需读取 |
|---|---|---|
| “这个号是谁、做什么、值得关注吗” | 轻量了解：定位、代表内容、值得继续看的问题 | [轻量报告](references/report-template.md) |
| “深拆这个号、分析它的做法” | 单号深拆：只展开影响本次判断的维度 | [单号报告](references/single-blogger-report.md)、[分析字段](references/breakdown-tables.md) |
| “比较这几个账号、选主对标” | 横向比较：统一可比口径，保留各号的学习价值 | [对比矩阵](references/comparison-matrix.md) |
| “分析他们的标题、封面、开头或评论区” | 专项表达分析，不自动扩成完整账号报告 | [钩子分类](references/hook-formulas.md) |
| “研究这个赛道的账号分布、供给和内容缺口” | 基于账号和作品样本的赛道研究 | [赛道模板](references/output-templates.md) |

轻量与深度是同一入口的范围选择。没有明确深拆要求时，先完成能回答用户问题的研究；不要为了进入另一档工作流而重复采集。

## 开始前

确认目标账号/链接或赛道关键词，读取用户提供的材料及当前项目的定位、受众和研究目的。先用可访问资料解析账号，只在目标确有歧义或缺失信息会改变判断时补问。

用户指定研究的对象即研究对象；[对标适配判断](references/screening.md) 用于说明迁移价值，不用于按粉丝量、赞粉比、更新频率排除用户指定对象。多号对比时也保留低数据、小样本或停更账号在本次问题中的实际价值。

## 采集与证据

先读 [采集与证据规则](references/data-collection.md)，再按实际平台读一份 reference：

| 平台 | 研究说明 |
|---|---|
| 小红书 | [xiaohongshu.md](references/xiaohongshu.md) |
| 微信公众号 | [gongzhonghao.md](references/gongzhonghao.md) |
| 微信视频号 | [shipinhao.md](references/shipinhao.md) |

本入口与[采集与证据规则](references/data-collection.md)决定材料复用、工具选择、异常归因和研究完成标准；平台 reference 用于确认本次补采支持的命令、参数、字段、错误信号、恢复操作和账号映射。异常原因按现场证据判断。使用当前可用的浏览器、连接器或有实际路径的 CLI，先核对能力与目标环境。已有原文、导出、截图或逐字稿足以回答时直接消费，无需触发平台认证；补采结束后继续分析成稿。独立抓取流程的工具选择和取数结束点不接管本研究。

- 研究只读取公开可访问资料或用户授权提供的材料。搜索和浏览小红书使用独立测试会话；本地 CLI 显式 `--account 测试号`。测试会话失效时在该环境恢复，不静默换到运营号。
- 记录实际读取的作品、时间范围、采样方法、列表和详情覆盖、失败与缺项。高互动样本与普通样本分开，避免只看成功案例。
- 采集量按问题与证据缺口决定；可以补充、缩小结论或报告外部阻塞，不能把固定篇数、成功比例或滚动次数当作研究通行证。
- 核对正文、图片和视频实际读取范围。只看封面、标题或字幕时，不能声称完整看过作品或其视觉表现。
- 只得到部分公开列表时就写部分；最早可见作品不等于起号日期。已触达当次公开分页末尾也不证明全部历史。

## 分析与成稿

把结论分为可观察事实、基于证据的解释、仍需验证的假设。每项关键判断给出作品链接或资料位置；统计说明分母、时间、缺失字段和样本选择，缺失值不填零，不猜指标。

围绕账号定位、内容主线、形式、标题封面、开头与结构、发布节奏、公开互动反馈及迁移成本展开。商业化只在本次问题需要时分析；目标受众与真实粉丝画像分开，不从评论头像推断人口属性。

观察到互动较高只能说明样本关联。没有曝光、点击率、播放留存或对照数据时，不把公开赞藏评写成点击/留存效果，不将标题、封面、时段或商业化密度直接认定为原因。样本里未见某种内容只证明本轮未见，不证明赛道空白。

交付先回答用户的核心问题，再给必要比较、代表作品和可借鉴做法。报告简要交代覆盖范围与局限；写作清楚不等于隐藏研究边界。模板是可裁剪的结构参考，不要求填满无证据字段、凑建议数量或生成额外发布文案。

## 交付核对

- 用户问题是否得到回答，研究对象和资料是否匹配？
- 关键结论能否追溯到实读材料，统计口径与缺项是否清楚？
- 是否区分观察、解释和假设，结论强度是否匹配覆盖范围？
- 建议是否服务当前项目，说明可借鉴点、适用条件和下一步验证？
- 是否按实情标记完成、部分完成或外部阻塞，且未越过用户授权？

存在证据缺口就补最能影响判断的资料；外部不可访问时明确其影响与恢复动作，不要求用户重提原任务。

## 上下游边界

只要原始列表/正文，无分析报告 → `platform-fetch`。根据项目决定下一篇做什么 → `content-topic-planning`，可消费本研究的结论。已有来源需要写完整文章 → `source-longform-writing`。制作平台标题、正文、封面文案与发布包 → `content-package-create`。

研究完成不自动上传、发布、评论、点赞、收藏、关注或私信，也不自动写入共享知识库。用户同时明确授权的后续制作或发布任务，由主流程继续交给相应入口，不以本研究边界中断整个请求。

维护或评估此 Skill 时读 [场景与验证说明](references/test-cases.md)。
