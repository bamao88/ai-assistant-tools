## 工作流程

**步骤 1 — 先锁发布契约。**
在运行任何会打开平台后台、访问平台 API、上传素材、写草稿或点击按钮的命令前，先把这三件事确定下来：

- **目标平台**：看用户表述定位到上表的一行。没有明确平台、多个平台混在一起或平台与内容形态冲突时，先问清楚，不要猜。
- **发布账号**：必须明确本次用哪个平台账号/slot/profile。若用户已指定账号，后续全程固定；若平台 reference 有固定白名单或单账号默认，先向用户说明“本次将使用账号 X”；若平台存在多个可选账号或无法判断账号，先列出候选并询问。账号未确定前，不做网络 preflight，不打开发布页，不写草稿。
- **最终提交权限**：必须明确最终“点击发布 / 定时发布 / 提交审核 / 群发 / 投稿 / 保存草稿”的动作由谁完成。

提交权限分两类：

| 权限 | 含义 | 默认 |
|---|---|---|
| `manual-submit` | Agent 只填表、创建草稿、保存草稿或停在待发布页；最终发布按钮由人点击 | 默认使用 |
| `agent-submit` | 用户明确授权 Agent 直接点击发布、定时发布、提交审核、投稿或群发 | 仅在用户明确说“你直接发布/定时发布/点击发布/不用我介入”等，并且平台 reference 允许时使用 |

如果用户只说“发到某平台”但没有说明是否要机器点击最终发布，按 `manual-submit` 处理；若该平台没有安全草稿/预览中间态（例如 B站 `upload-video` 执行即投稿），必须反问确认是否授权 `agent-submit`，不能默认投稿。

**步骤 2 — 读对应的 reference，完成账号落地。**
一次只读一个 reference。reference 里有账号列表/白名单/固定 profile、CLI 路径、平台专属前置步骤、子命令、失败兜底。**不要凭记忆拼命令** —— 照着 reference 抄。若 reference 与本文件冲突，以本文件的“发布契约”和“本地网络前置门”为上位约束；reference 只能补充平台域名/账号/发布细节，不能跳过契约确认。

**步骤 3 — 发布前先做本地网络前置门。**
所有平台发布都先走本地网络分流，不把登录、上传、写草稿、提交审核等发布动作交给 Tailscale exit node 或代理出口。不同平台的域名/IP 不一样，但动作统一：在任何会访问平台网页、API、上传入口、草稿接口的命令前，先运行 `publish-network-preflight` 对应平台的 `apply`。

```bash
/Volumes/ExtSSD2601/AI_Assistant/tools/engines/route-bypass/scripts/publish-network-preflight.zsh <platform> apply
```

平台参数：

| 目标 | platform |
|---|---|
| 小红书 | `xiaohongshu` |
| 微信公众号 | `gongzhonghao` |
| 视频号 | `shipinhao` |
| B站视频 | `bilibili` |
| 抖音视频/图文 | `douyin` |
| 知乎/掘金/CSDN/百家号/思否/头条文章草稿 | `article-drafts` |

`apply` 会重新解析当前平台域名的最新 IPv4、把新 IP 钉到本地网关路由，并刷新受控 `/etc/hosts` 块（目前小红书上传关键域名需要）。如果 IP 变了，重新跑同一条 `apply`；不要手工改 `/etc/hosts` 或手工 `route add/delete`。如果 `apply` 因管理员权限或路由校验失败而失败，停止发布，先解决网络前置门，不继续打开发布页、上传素材或提交。

**步骤 4 — 执行并结构化汇报。**
执行时始终带着步骤 1 的契约：平台、账号、`manual-submit`/`agent-submit`。报告：发到了哪个平台/账号、是否由 Agent 点击了最终提交、是草稿/待人工点击/已发布/已定时/已投稿、草稿链接或 media_id/publish_id、需要用户手动确认的后续动作。

## 多笔记发布顺序

用户给出一组待发布内容时，按队列逐条执行：一次只打开/上传/提交一条，确认该条成功并写入状态记录后，才进入下一条。禁止为了省时间把多条真实账号笔记放进一个后台批量循环里一次性提交；发布流程当前依赖浏览器状态、网络分流和平台审核反馈，批量并发或无人值守循环会放大失败并造成误报。

## 正式账号活跃会话异常处理

一旦正式账号的发布会话已经打开，尤其是素材已经上传、表单已经填写、封面/标签/定时信息已经进入页面时，遇到弹窗、遮挡、平台校验、按钮不可点、登录态提示或其他阻挡，默认动作是**先处理当前页面，把当前这条发布完成**。

- 先观察当前前台窗口或可控浏览器页面，判断卡在什么弹窗/字段/按钮。
- 能在当前会话里关闭弹窗、点击确认、补字段、重试按钮、等待平台处理的，优先在当前会话内解决。
- 不要把“关闭当前进程、改脚本、重新上传/重新发布”作为第一反应。
- 只有当前会话不可恢复（页面崩溃、窗口已关闭、上传状态丢失、账号明确退出、平台明确拒绝继续）时，才停止并说明原因。
- 当前发布完成后，再修脚本、补测试、沉淀 reference，避免后续复发。

这条适用于所有真实账号平台，包括小红书、公众号、视频号、B站、抖音和文章分发平台。它优先于平台专属 reference 里的普通失败重试建议，因为频繁中断已上传/已填写的真实账号发布流程会增加风控和误操作风险。

小红书视频发布有额外稳定性门槛：在 `测试号` 跑通本地网络分流与 host 探测、上传进度推进、封面、标签、发布按钮可点击链路前，不得对真实账号执行 `publish-video` 或自动点击最终发布按钮。真实账号任务只能按 `references/xiaohongshu.md` 的逐条流程执行。

视频号发布同样有测试号门槛：`aipm`（AI PM 小助理视频号）同时是默认账号和测试号。视频号链路未稳定，或用户要求“测试/验证流程/先跑一条”时，必须使用 `--account aipm` 和 `--fill-only`；只有测试链路确认稳定、用户明确指定真实账号并授权后，才切到 `zhanghe` 等真实账号 slot。

## 一稿多发（多平台）

用户要求"同时发小红书 + 公众号 + 知乎"这类一稿多发：

- **拆成多次独立发布**，每个平台各自读自己的 reference、各自走完整流程，不要试图一条命令处理混合目标。
- 各平台对内容形态要求不同（小红书图文需配图/长文需卡片图、公众号需封面图、文章直传走 Markdown/HTML，今日头条当前走浏览器编辑器），按各 reference 的要求分别准备。
- 逐平台汇报结果；某个平台失败不影响其他平台，明确列出成功与失败。

## 与其他 skill 的边界

- **抓取/调研内容**（搜笔记、拉文章、看博主、扒字幕） → `platform-fetch`
- **博主调研报告**（拉博主全部笔记 + 分析） → `blogger-research`
- **评论 / 点赞 / 收藏** → `xhs-interact`；**登录 / 切号** → `xhs-auth`
- **小红书复合运营工作流**（边搜边发边互动） → `xhs-ops`

## 安全与确认总则（各 reference 另有平台细则）

- **真实发布是对外动作**：默认 `manual-submit`，只到"草稿/填好待用户手动点发布/保存草稿"。只有步骤 1 已锁定 `agent-submit`，且对应 reference 明确支持自动提交，才允许点击最终发布、定时发布、提交审核、投稿或群发。
- **先 dry-run / 测试模式**：文章直传必须先 `--dry-run`；公众号优先 `--dry-run` 预览；小红书"测试模式"绝不调用 `click-publish`；抖音测试阶段/测试号必须使用 `--fill-only`，绝不点击最终发布；视频号默认保存草稿，明确确认正式发布/定时发布才加 `--publish`。
- **不编造内容**：标题、正文、话题、封面必须来自用户提供的真实素材，缺信息先补齐再发。
- **账号要选对**：多账号平台先列账号、与用户确认后全程固定，不中途换号。
- **平台关键词限制不同**：不要把小红书 10 个关键词原样搬到抖音。抖音视频/图文最多传 5 个话题，按内容源顺序取前 5 个。
