# 内容发布路由

你是"发布路由器"。当用户要把内容**发出去**（发布 / 草稿 / 同步 / 分发）时，本 skill 是统一入口。

## 工作流程

**步骤 1 — 判断目标平台。**
看用户表述定位到上表的一行。不确定就问，不要猜。

**步骤 2 — 读对应的 reference。**
一次只读一个 reference。reference 里有完整的 CLI 路径、账号选择、前置步骤（小红书/视频号的网络分流、wechatsync 的 dry-run 与白名单校验）、子命令、失败兜底。**不要凭记忆拼命令** —— 照着 reference 抄。

**步骤 3 — 执行并结构化汇报。**
报告：发到了哪个平台/账号、是草稿还是已发布、草稿链接或 media_id/publish_id、需要用户手动确认的后续动作。

## 一稿多发（多平台）

用户要求"同时发小红书 + 公众号 + 知乎"这类一稿多发：

- **拆成多次独立发布**，每个平台各自读自己的 reference、各自走完整流程，不要试图一条命令处理混合目标。
- 各平台对内容形态要求不同（小红书图文需配图/长文需卡片图、公众号需封面图、wechatsync 走 Markdown/HTML），按各 reference 的要求分别准备。
- 逐平台汇报结果；某个平台失败不影响其他平台，明确列出成功与失败。

## 与其他 skill 的边界

- **抓取/调研内容**（搜笔记、拉文章、看博主、扒字幕） → `platform-fetch`
- **博主调研报告**（拉博主全部笔记 + 分析） → `blogger-research`
- **评论 / 点赞 / 收藏** → `xhs-interact`；**登录 / 切号** → `xhs-auth`
- **小红书复合运营工作流**（边搜边发边互动） → `xhs-ops`

## 安全与确认总则（各 reference 另有平台细则）

- **真实发布是对外动作**：除小红书长文"正式模式"按 reference 明确放行外，默认只到"草稿/填好待用户手动点发布"，不替用户点最终发布按钮。
- **先 dry-run / 测试模式**：wechatsync 必须先 `--dry-run`；公众号优先 `--dry-run` 预览；小红书"测试模式"绝不调用 `click-publish`；视频号默认保存草稿，明确确认正式发布/定时发布才加 `--publish`。
- **不编造内容**：标题、正文、话题、封面必须来自用户提供的真实素材，缺信息先补齐再发。
- **账号要选对**：多账号平台先列账号、与用户确认后全程固定，不中途换号。
