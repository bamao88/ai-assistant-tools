# 产品深度研究

通用能力：账号定位、事实、素材与输出位置遵循当前项目；项目已有专属入口时优先沿其规则衔接。

给定产品名或链接，就开始研究；未指定交付形态时，默认交付独立的完整研究报告。默认自主完成，不把资料搜索、研究角度和章节选择逐步交还用户；仅当同名产品、研究对象或重要访问权限无法判定时询问。用户说“写一篇文章”也包含完成文章所需的全貌研究。**先弄明白这款产品如何成立、如何运转、怎样变化，再决定文章讲什么。**

研究不是把官网、访谈和几篇报道拼接成公司介绍。先画全貌，再追最能解释它的机制；交付应让读者既看懂用户实际得到什么，也看懂产品、创始人、技术、分发和商业选择如何相互作用。参照 [跨案例研究经验](references/case-lessons.md) 理解不同类型产品应怎样改变研究重心；案例是判断示范，不是固定目录或事实来源。

## 1. 固定对象，画出第一张全貌图

先记正式名称、产品 URL／App ID／仓库、公司或卖家主体、创始人与账号、研究日期。名称、主体或版本变过时沿稳定 ID 追踪；把**首次上线、重做、开始推广、来源发表和指标统计**各自放到时间线上。当前页面不能自动代表历史版本。

第一轮广搜只为发现值得深挖的机制，快速回答这些问题，并为每个答案标明原物与空白：

- 谁在什么情境下遇到什么问题？原来用什么替代？谁决定购买、谁真正使用？
- 从发现、首次体验、产生结果、付费到复访／流失，用户实际走哪条路？产品靠什么供给持续价值？
- 创始人和团队带来了什么技能、渠道、资产、关系或特殊约束？这些如何进入具体选择？
- 能力怎样做出来：数据、模型／技术、内容、人工和外部依赖如何分工？在质量、成本和规模上受什么限制？
- 第一批用户怎么来，后来谁持续生产素材、产品内容或销售机会？分发是否依赖创始人、平台、伙伴或用户自己？
- 谁付多少钱，钱何时进来，获取与交付成本在哪里？增长、使用、收入与利润分别有什么证据？
- 它与当时可用的替代品相比选了什么切口？经历哪些失败、转向、版本变化；现在处于什么状态？

这些是**视野**，不是七个等长章节。不要因标题写“月收”就只研究营销，也不要因产品叫 AI 就只列模型。对一个简单消费 App，分发与留存可能是核心；对技术平台，质量和系统架构可能决定产品；对创始人驱动的公司，个人能力、关系或作息可能是稀缺资源。PM 看用户和流程，CEO 看资源配置与经营，CTO 看实现、质量和约束；按本案的解释力加深，不平均分配篇幅。

## 2. 从线索追回一手原物

优先找**能直接见到行为或原话**的材料，并判断它究竟能证明什么：

| 要验证的事 | 应追的原物 |
| --- | --- |
| 产品与体验 | 可访问产品的真实操作，官网／商店当时页面，演示录像、文档、定价页、版本记录、取消路径；可行时走完核心任务并记录地区、版本和访问范围。跨付费、登录或个人数据门槛时依据已有授权；没有授权且该步骤确实必要时再问。 |
| 选择与过程 | 创始人／员工完整访谈、原始播客与字幕、本人文章或帖子、发布日志、技术分享、开源提交、招聘、公开事故复盘。 |
| 用户与合作方 | 带日期的用户评价和使用记录、社区提问、客户案例原页、创作者／伙伴自己的内容、广告或销售活动原页。 |
| 结果与经营 | 当时的后台或平台记录、财报／交易文件、指标定义、价格和费用原页；同时查能否独立观察到使用或付款。 |
| 市场与替代 | 同时期竞品产品、价格、文档、用户比较与迁移理由；别把今天的功能投射回过去。 |

实际检索从「产品名及旧名 + 域名／App ID + 创始人实名／handle」开始，再组合 `interview`、`podcast`、`AMA`、`changelog`、`pricing`、`architecture`、`postmortem`、`case study`、`review`、`exit` 等与本案有关的词。找到线索后，再用 `site:` 对官网、视频制作方、应用商店、GitHub、用户社区或数据平台定向追查，不要让最初的站点限制漏掉未知来源。已知节目时用**原始节目标题 + 嘉宾名**找制作方上传、完整字幕和时间码；已知独特一句话时加引号反查原帖。发现新人物、伙伴、工具、版本号、截图或交易数字，就用它们生成下一组查询，并沿“原文／View source／引用”回溯。保留真实搜索词、命中、未命中及日期，不能把后来才查的材料倒写成早期研究已知。

二手文章和聚合页可指路，核心经营、技术或因果判断应回到原帖。逐篇核对链接跳转后的作者、标题、日期、正文和帖子 ID；同一转载站一篇可靠，不等于另一篇也可靠。创始人亲述是其**一手自述**，用户评论是该用户的**一手经历**，官方产品页是公司的**公开承诺**，亲测只覆盖自己实际走过的流程；这些来源的证明范围不同。看不到完整流程、后台或内部实现时，明确到此为止，不以截图、演示或建议补足。

## 3. 找决定性机制，沿动作追深

在全貌图上圈出最能解释“为什么是这款产品、为什么现在、结果怎样发生”的一到数条机制。优先追**独特、有结果、有取舍且有足够原物**的转折。问一个反事实：去掉这个环节，产品的体验、增长、收入或成本会怎样变化？如果答案不变，它可能只是背景。

每条机制尽量还原为：**触发问题 → 谁选择了什么、放弃了什么 → 谁用哪些输入和工具反复执行 → 产品／内容／技术怎样交付 → 用户或市场怎样响应 → 看什么指标 → 下一轮改什么**。追“合作”要找到双方分工、交付物和对价；追“技术领先”要找到任务、系统边界、失败模式、评估和成本；追“创始人特质”要接起**过往经历、失败、训练或工作方式、受众与关系如何积累 → 形成何种能力或资源 → 改变哪些产品与经营选择 → 带来什么结果**，不能停在履历或性格词。成功和失败都查，尤其查做过却无效、转向前的限制和随着规模出现的新问题。

当来源写“优化”“自动化”“社区增长”“用户喜欢”时，不复述概括词：搜索实际页面、视频、截图、流程、人员、日期、预算和结果。把**本人做过的事、本人给别人的建议、公司宣传、外部观察、研究者推断、尚待验证的解释**分开；不能把建议倒填成历史，也不能把时间上的先后直接写成因果。重要说法有冲突时并列来源与口径，继续找能排除某种解释的证据；找不到就保留真正影响判断的争议。

## 4. 给数字和判断装上边界

每个关键数字记录：是谁提供、原始页面或时间点、发布日期、统计窗口、地区／产品／用户范围、定义、是否预测或归因、取数或计算方法。自然月收入、滚动收入、MRR／ARR、交易额、现金回款、利润、ROAS、下载与活跃订阅不能互相替换。单次爆发、长期留存、广告归因与净现金各回答不同问题；缺费用或续费数据，就不要算出精确单位经济。

内部证据笔记可用「亲测观察／平台记录／当事人自述／另一方亲历／二手线索／研究推断」区分。研究报告与公开文章都只在需要时解释决定性边界，避免段段插入防错声明。所有重要结论都能回到原始链接、视频时间码、截图、版本或计算；材料不足时缩小**结论**，不缩小用户要求研究的产品全貌。

## 5. 先交完整研究，再按用途写文章

以下是本 Skill 所有研究报告的默认交付标准，同时适用于给用户本人和面向外部读者的报告。完整研究应独立可读，先让读者看懂产品和关键发现。**研究底稿与读者报告分开保存，默认只交付读者报告**：底稿保留检索、核验和细节，报告把分散发现整理成明确的事实、机制和有依据的判断，不复述 Agent 做过哪些工作。只有会改变当前结论的证据边界才写进正文；其余记录单独保存，不以折叠附录的形式全量装入读者版。研究资产应覆盖：

1. **整体判断与产品实际使用**：目标用户、核心体验、持续价值和本案最关键的机制。
2. **时序与选择**：创始人／团队起点，产品版本、增长和商业转折，失败与代价。
3. **机制深挖**：与本案最有关的用户、技术、内容供给、销售／获客、组织或单位经济过程；说明每个动作由谁做、依据何在、结果如何，不按固定模板平均铺开。
4. **市场及当前状态**：同阶段替代品、差异、可复制的条件、无法简单复制的资产，以及哪些发现会推翻现有判断。
5. **可接手证据资产**：逐项来源索引、关键数字口径、真实检索路径与未命中、亲测范围、冲突和高价值未解问题，单独保存为研究底稿。正文在重要主张处保留原始来源引用，用户需要审计或接手研究时再提供底稿。

### 研究报告的可读性

报告正文首先服务想理解产品的人；证据账本服务要回查材料的人。按读者需要回答的问题整合发现，交代产品怎样运转、关键选择及其影响和当前能成立的判断；不按资料发现顺序或研究步骤排篇。细节是否进入正文，取决于它能否帮助理解机制或改变判断，不能只因已查到就保留。完整研究指研究覆盖充分，不要求成品展示全部材料。

- 用具体的人、设备或动作解释关系。技术机制先说明用户会遇到什么、系统如何处理，例如如何区别轻挥与大力挥拍、何时给出反馈；再补确有必要的术语。保持来源能支持的精度，不为通俗化补造行为或因果。
- 每段讲清一个问题及其前后关系，拆开同时塞入事实、推断、限制和研究过程的长句。段落中的抽象判断必须接到具体动作；只有重复上一段结论的总结句可以删去。
- 事实归属和必要限定直接写进主张，例如“创始人说”“两位评论者描述过游玩”。只在缺口会改变读者对当前主张的理解时展开解释；其余取证范围、未命中、版本指纹和数字口径放进证据资产。不要对没有提出的主张逐项反驳，也不要每段都重复未完成亲测。
- 步骤用于实际操作，表格用于简短对照。人物经过和因果关系用连贯段落展开，不在宽表格中同时堆叠事实、解释和免责声明。压缩重复与填充内容，保留理解机制所需的例子和产品全貌。
- 交付前完整通读正文，检查非专业读者能否直接理解每句话、章节之间能否自然接续；逐段判断它在回答什么产品问题，删除只用于汇报工作或证明调研充分的内容。收到“整篇绕口”或“可读性差”的反馈时，先检查结构、叙述姿态和信息安排，再重写受影响段落；不能只替换几个词，也不能用更短的名词短语继续压缩难句。

### 图片与亲自操作的演示

产品界面、操作步骤或反馈效果需要画面才能讲清时，把图片直接放在报告对应段落中，让读者在同一份报告里看见；来源链接用于回查，不能代替图片。选择能支持解释的画面，裁取可读的内容区域，配简短说明，不统一堆到文首或另做必须跳转的图库。

需要操作演示时，默认由 Agent 亲自进入产品、走步骤并录制，不让用户承担演示、截图或录屏工作。将录制结果直接嵌入对应段落，可用 GIF 展示短流程、视频提供暂停播放；当前阅读器无法显示时，补充同一份内容的图文阅读版，优先把媒体嵌在文件内以便直接阅读和携带。

在底稿中记录每个画面的来源、日期及实际覆盖范围，区分亲自拍摄的产品操作、官方演示与研究者绘制的说明图。报告图注说明画面展示的产品行为，必要时简明标明演示范围，不写操作日志。不得用合成画面、模拟传感器或静态教程冒充真实输入与完整体验。设备、权限或访问条件确实阻塞时，先完成可操作部分的记录，将具体阻碍留在底稿，报告只说明影响结论的未验证范围，不把剩余演示交回用户。

交付前在实际阅读界面检查图片能否原位显示、小字能否读清、动图或视频能否播放，以及媒体和附录链接是否有效。文件写入成功或媒体编码成功不能代替阅读验证。

以“研究报告”交付时，直接呈现完整结果。以“深度文章”交付时，也独立保存上述研究资产；默认写成**产品全貌叙事 + 本案决定性机制的纵深**，让读者同时理解产品、用户、创始人、技术与经营怎样相互作用，并给最有解释力的部分足够篇幅。已有全篇和专题旧稿时，回到原物合并发现、去重并修正来源问题，重新组织一篇，而非拼接段落。只有用户明确要运营、技术、创始人等单一专题时，才从全貌研究中裁出专题文章，底稿仍保留其他重要发现。用户已经授权自主成稿时，自行决定标题和结构并完成，不因常规角度选择停下；若另有适用的文章写作技能，按该技能的表达与素材规范处理，并遵循用户已给的自主授权。

文章用真实场景、人物动作、失败尝试、数字变化和原始画面推进，写得有阅读感。结论回答“他具体怎样做到、为什么这套办法在这里有效、有什么条件与代价”，让读者自己判断可学什么；不堆“启示”套话，也不把研究过程、免责声明或资料清单写成正文。

## 何时继续，何时结束

若核心机制还只能用“靠 AI／内容／增长”概括，尚不知谁做了什么、用户是否得到结果或数字口径是否成立，继续沿该缺口找原物。若新增搜索只重复同一转述，已定向追过本人、产品、另一方、用户和平台记录，且重要主张的证据范围可说清，就停止搜索并交付；把无法公开核实的关键问题留在研究资产里。对象身份、权限或关键来源缺失到无法建立基本产品图时，说明具体障碍并请求所需输入。
