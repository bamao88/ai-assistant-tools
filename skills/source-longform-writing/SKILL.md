# 文章写作：视频与资料转长文

通用能力：账号定位、事实、素材与输出位置遵循当前项目；项目已有专属入口时优先沿其规则衔接。

这个技能负责把一手内容源变成独立可读的中文长文。账号定位只提供背景，不替代这篇文章自己的选题判断、读者判断和写作结构。

用户只需给来源和写作目标，不必自行串联字幕提取、来源阅读、文章写作和表达润色。对用户称为“文章写作”；`source-longform-writing` 是保留的调用名，旧入口 `video-source-longform-writing` 已并入此处。

## 从写作目标选择入口

| 用户想完成什么 | 负责入口 |
|---|---|
| 把 YouTube、播客、访谈、网页或论文写成完整文章；重写来源型文章 | 本技能，按需衔接资料获取、配图和润色 |
| 只取字幕、逐字稿、关键帧或视频研究包 | `video-content`；平台原文与列表采集用 `platform-fetch` |
| 已有文章，只改表达、顺中文或减少机器腔 | `article-expression-polish` |
| 起标题、写笔记正文、平台配文、封面文字或制作发布包 | `content-package-create` |
| 尚未决定做什么，找题或比较多个选题 | `content-topic-planning` |

写作前为当前来源确定文章角度，是本技能的内部工作，不要求用户先调用选题技能。WXP 口播台词由 `assistant_wxp_self_spoken-script-style` 处理，不把口播风格直接套到文章。

如果用户要先对一款产品做整体深度研究，并把研究成果作为独立的学习交付，先使用该项目的研究工作流完成研究。此时不要为了写文章，提前收窄为一个选题或确定文章读者、平台、标题，也不启动下文的方向卡。研究完成后，要从中写来源型文章时，再使用本技能的方向卡和写作流程；用户明确要求从范围已确定的材料写文章时，也按下文流程执行。

## 必须先执行的工作流

进入来源型文章任务后，先补齐并阅读来源，再判断方向、写正文和处理表达。除非用户明确说“直接写，不需要先对齐”，否则来源型长文只让用户确认两次：方向是否成立，最终稿是否达标。调研、读者判断、材料取舍、素材选择和表达清理，是写作侧内部工作，不摊给用户。

硬门：

- 用户说“可以，写一篇文章”“写一篇”“来一篇”“就按这个写”，只表示希望写作，不表示跳过方向确认。
- 只有用户明确说“直接写”“不用确认方向”“不需要先对齐”“按你判断直接出完整稿”，才可以跳过方向卡。
- 如果当前对话里已经给过方向卡，但用户没有明确确认方向成立，不写完整文章。
- 如果误写了完整稿，把它降级为未确认草稿，先补方向卡，不继续润色、发布或扩写。

### 0. 检查并补齐来源材料

- 先复用当前对话、项目和用户已提供的原文、字幕、研究包或素材索引；核对是否对应本次来源、读取范围是否足够，不因换入口重复抓取。
- 只有 YouTube 等视频链接，或缺少可读字幕时，读取并使用 `video-content` 获取转录与必要元数据；只需字幕就不默认下载整片或制作全套研究包。重要引语、数字和专有名词保留时间戳与来源信息，区分人工字幕、自动字幕和转写结果。
- 网页、论文与官方资料使用当前可用的网页或文档读取能力；公众号等封闭平台按 `platform-fetch` 的对应 reference 获取。工具命令从其现有说明读取，不在这里另维护一份。
- 获取后实际阅读与文章有关的原始材料，判断证据和上下文是否足够；页面标题、视频简介、工具摘要或二手概述不能替代全文或字幕阅读。
- 采集和转录是写作的内部步骤。拿到材料后回到下述方向判断，不把“字幕已提取”作为文章任务完成。必要素材因登录、删除或不可访问受阻时，说明实际缺口及对写作的影响，不用摘要补造原文。

### 1. 方向确认前先自检

拿到来源后，先在内部回答：

- 这篇文章的选题是什么；
- 这篇文章到底要讲什么；
- 主来源里最值得精读的模块是什么；
- 这个模块是否有足够上下文支撑独立成文；
- 这篇文章写给谁；
- 读者读完是否会更清楚一个具体对象、机制、系统、产品变化或组织实践；
- 哪些内容不应该写进正文；
- 材料是否足够，缺口在哪里。

这些问题回答不清时，不进入方向确认。继续调研、缩小选题、换角度，或者说明这个来源暂时撑不起一篇清楚的文章。

给用户看的方向卡默认只包含：

```text
选题：
文章摘要：
大纲：
```

其中“文章摘要”要接近正式摘要：用几句话讲清文章要讲什么，而不是讲写作计划。核心读者、素材基础、不写什么、风险和缺口默认内部处理；只有它们会影响方向判断时，才在方向卡后用一两句话说明。若有多个可行方向，可以给 2-3 个方向候选，但每个候选都要包含选题、摘要和大纲。

读取 `references/source-reading.md` 和 `references/quality-gates.md`。

### 2. 方向通过后写完整文章

正文是独立内容载体，不能让读者感到背后有调研过程或修改讨论。

要做：

- 回到主来源和补充来源，按确认过的选题重新整理材料。
- 围绕来源里的知识点写正文，不从自己的常识、工具摘要或搜索过程写。
- 外部媒体只提供角度和包装启发，正文不写成“某摘要认为”“我调研发现”。
- 如果是重写任务，先摆脱旧稿上下文，只保留已确认的标题、来源、事实、引用和方向。
- 用户反馈后，先重读全文，再判断标题、开头、小节、段落和素材是否要联动调整。
- 文章内容稳定后，使用 `article-expression-polish` 做表达清理；如果是账号特定的文章口吻问题，使用该账号的文章风格依据。`assistant_wxp_self_spoken-script-style` 只负责口播脚本文字，不用于文章润色。

读取 `references/quality-gates.md`。

### 3. 最终稿连同素材一起确认

用户第二次需要看的，是接近定稿的最终文章，不是只有文字的半成品。

要做：

- 整理标题、摘要、段落密度和小节顺序。
- 决定哪里需要截图、GIF、字幕拼图、表格、树状结构、引用或第三方图片。
- 视频素材需要解释动作时再做 GIF；原话有价值时再做字幕图；第三方图片质量更好且来源清楚时可以使用。
- 图片、GIF、字幕拼图和图注放在对应内容块附近，和正文一起进入最终稿。
- 所有素材都要服务文章问题，不能只是装饰，也不能只是证明“看过来源”。
- 最后检查来源、路径、图注、隐私和 frontmatter。

读取 `references/source-assets.md` 和 `references/quality-gates.md`。

## 边界

适用场景：

- 官方博客、官方文档、产品说明、技术报告、论文和 GitHub 仓库精读
- 一手文章、博客、论文、字幕稿、演讲、播客、访谈、工作坊和会议视频整理
- 公司、产品、技术、基础设施、组织实践和行业机制分析
- 判断来源素材应该如何进入正文：引用、截图、GIF、字幕拼图、树状结构、表格、代码块，或者不进正文
- 当前草稿的问题在结构、标题、来源处理、来源层级或素材整合时的文章重写
- 用户想把英文材料改写成可读中文学习材料，而不是逐字翻译时

不适用场景：

- 只抓取或转录来源材料、无需文章：使用 `platform-fetch`、`video-content` 或对应网页读取能力。完整写作请求由本技能编排获取材料并继续完成文章
- 不服务文章的纯视频剪辑或素材生产：使用 `video-clip`
- 生成发布包或封面：使用 `content-package-create`；草稿上传或平台发布：使用 `Agent-Publish`
- 只做表达润色、提升真人写作感、节奏清理、机器腔清理或最终口吻调整：使用 `article-expression-polish`
- 账号定位、选题池、数据回填等账号专属工作：交给项目智能体

## 核心原则

- 原始内容源是主角。文章要让读者理解来源说了什么，以及为什么值得读。
- 多个来源讲同一件事时，按知识点合并，不要机械地写成“文章说”“视频说”。
- 解读要克制。可以解释机制和影响，但不要把一篇来源精读膨胀成原创宣言，除非用户明确要求。
- 优先使用一手来源。二手资料可以帮助补背景，不承担核心事实。
- 不把调研过程、用户反馈、修改理由或当前对话写进公开文章。
- 视觉素材和引用必须有信息量。如果截图、GIF、引用或表格只是在证明“我看过这个来源”，就删掉。
- 文章标题、封面标题、摘要、平台配文和封面图各有规则，不要混在一起处理。
- 文章表达润色规则集中交给 `article-expression-polish`，不要在这个技能里另写一套分散清单。
