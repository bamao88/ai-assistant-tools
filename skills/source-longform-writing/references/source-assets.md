# 来源素材与资产选择

文章内容稳定后，再用这个参考文件整理素材：引用、截图、图片、图表、UI 状态、GIF、字幕拼图、代码块、表格或示意图。

真正要问的不是“能提取什么”，而是“什么能帮助读者更快、更准确地理解来源”。

## 素材清单

选题阶段可以先记录素材候选，但不要急着制作。稳稿后，给候选素材做一份简短清单：

```text
来源位置：
来源说了什么或展示了什么：
信息量：
最适合的正文用法：不用 | 引用 | 截图 | GIF | 字幕拼图 | 表格 | 树状结构 | 示意图 | 代码块
是否进入正文：是/否
理由：
```

要更频繁地选择“不用”。大多数来源细节应该变成正文里的自然叙述，而不是素材堆叠。

## 资产类型怎么选

- **引用**：原话本身重要时使用，例如定义、判断、指标、特殊说法、公开承诺。引用要短。
- **截图**：用于稳定的视觉证据，例如 UI 入口、图示、图表、演示文稿结构、产品状态或公开来源中的图片。
- **GIF**：用于一张静态图解释不清的连续动作，例如创建、切换、触发、查看状态、运行命令、编辑状态、展示产品工作流。
- **字幕拼图**：用于一段连续表达，且准确措辞本身有价值时。它服务观点，不服务装饰。
- **表格**：用于比较、选项、取舍、按类别整理来源观点、前后变化。
- **树状结构**：用于层级关系，例如文件结构、记忆层、权限层、组织结构、智能体/工具边界、经验存放位置。
- **示意图**：用于工作流、循环、架构、依赖关系或因果链。
- **代码块**：用于命令、配置、API 形状、prompt 或结构化例子；这些内容用散文会丢失形态。

不要因为素材存在就使用素材。如果配图说明只能写成“这是来源里的某个页面”，就删掉。

## 视频与音频来源

处理 YouTube、播客、工作坊、会议演讲、产品演示和访谈时：

- 缺少字幕、元数据、关键帧或研究包时，使用 `video-content`。
- 文章确实需要短片段或 GIF 时，才使用 `video-clip` 或 ffmpeg。
- 产品动作或工作流状态变化的 GIF 通常控制在 8-20 秒。
- 如果画面动作本身解释不清楚，需要给 GIF 加字幕。
- 字幕拼图要少用，只用于观点密度高的一小段连续表达。
- 资产文件名按时间戳和机制命名，不要叫 `clip1` 或 `image2`。
- 图注要说明素材证明了什么或展示了什么，最好带时间戳。

典型来源型长文不需要很多素材：

- 第一个核心机制附近放 0-1 张核心截图、GIF、表格或示意图
- 如果还有第二个真正重要的机制，再补 0-1 个 GIF 或截图
- 原话特别重要时，使用 0-1 个字幕拼图或短引用
- 层级关系比段落更清楚时，可以加入树状结构或表格

## 文章、博客、论文与文档来源

处理文章、博客、官方文档、论文、GitHub README 和技术文章时：

- 优先使用来源里的官方图示、表格、代码和官方截图，不要默认生成泛用视觉图。
- 重复出现的来源观点可以压缩成表格，不要散落成一串段落。
- 来源在讲层级、归属、文件结构、记忆、权限或流程时，优先考虑树状结构。
- 不要截图普通段落，除非排版本身就是要说明的内容。
- 不要为了装饰小节开头而引用原文。

## 第三方图片

可以使用第三方图片，但要满足这些条件：

- 图片比自行截图更清楚，或者能提供原始来源没有的背景信息。
- 来源、版权和引用边界清楚，不能把社交平台随手配图当事实来源。
- 图片进入正文是为了帮助理解文章问题，不是为了让版面热闹。
- 图注说明图片和正文机制的关系，而不是只写来源名称。

## 放置检查

定稿前检查每个进入正文的素材：

- 素材前一段是否制造了“读者需要看到它”的理由？
- 图注是否解释了机制，而不只是给图片命名？
- 删掉它会不会影响理解？
- 来源归属是否足够清楚？
- 是否包含隐私信息或无关 UI？
- Markdown 路径相对文章文件是否有效？

通不过这些检查的素材，删掉。
