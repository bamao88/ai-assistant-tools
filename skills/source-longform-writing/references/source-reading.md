# 来源精读与摘要写作

## 选题对齐

来源型文章开始前，先对齐选题，不要直接进入正文。

选题对齐先在内部完成，不要把自检问题摊给用户。内部要判断：

- 这篇文章的具体读者是谁；
- 读者读完能更清楚什么；
- 文章最值得写的角度；
- 来源里直接回答文章问题、值得展开的材料；
- 哪个模块足够精彩、上下文足够、离开完整来源也能独立成文；
- 建议结构；
- 还缺什么事实或素材；
- 其他媒体、博主、社区或原发布方的写法启发；
- 哪些内容不应该写进正文。

内部判断通过后，给用户看的方向卡默认只包含三项：

```text
选题：
文章摘要：
大纲：
```

其中“文章摘要”接近文章发布时的摘要，直接说文章要讲什么，不说“我准备怎么写”。如果核心读者、素材缺口或风险会影响用户判断方向，才在方向卡后补一两句话。

账号定位只提供边界，不自动决定读者。不要因为账号名或历史定位，把所有文章都写给同一种读者。

## 文章问题

不要从“这个来源讲了哪些内容”开始。先判断文章到底要帮助读者理解什么。

写作前先在内部写一句话：

```text
这篇文章帮助读者理解：________。
```

这句话只用于内部定方向。不要把它照搬进正文，写成“读者应该学到什么”“这篇文章帮助你理解什么”。

好的来源型文章通常回答这些问题之一：

- 这个来源揭示了哪个产品、工作流、公司、人物或技术机制？
- 什么发生了变化？这个变化为什么值得本账号读者理解？
- 看完这个来源后，读者能比之前更具体地理解什么？
- 来源里哪一部分真正值得保留？哪一部分应该舍弃？

如果来源本身撑不起一个清晰的文章问题，不要靠泛泛评论补足。应该缩小题目，或者告诉用户这个来源价值不足。

## 外部写法扫描

拿到一个来源或主题后，要主动查看公开发布方式，再决定自己的写法。不要只靠已有知识判断选题热度和文章角度。

重点看：

- 原发布方的标题、摘要、配图、章节和发布语境
- 媒体报道的标题、切入角度、读者承诺和遗漏点
- 博主、社区或 newsletter 的概括方式和传播钩子
- 哪些角度已经被写透，哪些角度更适合本账号补充

这些内容用于判断选题和包装，不等于要写进正文。正文通常不出现“某摘要说”“我调研了几篇文章后发现”。

## 来源层级

除非用户另有要求，按下面顺序使用来源：

1. 公司、实验室、项目的一手材料：官方文档、官方博客、产品说明、技术报告、论文、GitHub 仓库。
2. 一手表达：演讲、YouTube 视频、播客、访谈、会议分享、字幕稿。
3. 产品文档、客户案例、工程博客、更新日志、公开演示。
4. 高质量二手报道和媒体写法作为背景与角度参考。
5. 社交平台和推荐流只能作为线索，不能作为唯一事实来源。

如果用户明确排除某类来源，把它写进内部上下文卡的“禁止来源”，并且不要使用。

## 文章形态

### 官方来源精读

适用于主来源是官方文章、文档、论文或公司博客的情况。

推荐结构：

- 从来源里的具体问题、机制、变化或分类开始
- 说明来源实际在描述什么
- 必要术语在第一次出现时简短解释
- 把机制连接到产品、工程、组织、商业或用户工作流影响
- 结尾回到这个来源帮助读者理解了什么

避免：

- 默认做全文翻译
- 用“这篇文章很重要”这类舞台提示开头
- 每一段都写来源书目式归属
- 在来源边界已经清楚时，反复过度免责声明

### YouTube / 播客 / 访谈整理

适用于主来源是演讲、播客、访谈或字幕稿的情况。

推荐结构：

- 开篇用一句话落到精读对象和角度。不要把讲者身份、视频题目、文档对象、术语定义连续堆在首屏。
- 只交代必要的讲者身份和主题。讲者所在团队、岗位或工作位置只有在它影响材料视角、可信度或文章价值时才写。
- 围绕文章问题重组内容，不预设知识点或章节数量。章节分量可以明显不同；有完整经验和追问的段落应充分展开，材料薄的部分可以压缩、并入或删除。
- 可以只精读一个最有价值的模块，不需要覆盖整条视频。这个模块应同时满足：内容本身有价值、来源里有足够上下文支撑、离开完整视频也能独立成文。
- 保留有用的例子、数字、比喻和具体表述
- 只有原话本身重要时才使用短引用
- 把官方文档、演示文稿或补充材料并入同一个知识点

避免：

- 按字幕顺序机械复述
- 开头写成来源信息清单：谁讲的、视频叫什么、文档里有哪些对象、术语是什么意思，然后才进入文章主题
- 把视频里所有内容都写进文章，导致精读变成全片整理
- 写成“视频先说了什么、后说了什么”
- 每一节都强行改成建议或清单
- 让写作者变成主角，例如反复写“我学到”
- 把第三方摘要当成正文里的研究证据
- 为了证明做过调研，把社区讨论、二手摘要或素材取舍过程写进正文

#### 访谈的深度来自经验细节

触发场景：把播客或访谈写成来源型文章，尤其是用户指出内容浅、只剩通用建议时。

- 精读时保留有依据的经验链：人物当时遇到什么、为什么这样判断、做过什么、得到什么反馈，以及哪些地方仍然犹豫。来源缺哪一环就保留缺口，不为叙事完整补造经历。
- 主持人的追问可能改变建议的含义。应保留会揭示实际执行程度、适用条件、失败或不确定性的回应，不能只留下听起来确定的结论。
- 区分亲历、对客户的观察、他人案例、建议和现场尝试；不能把建议写成嘉宾自己验证过的方法，也不能把一次演示写成长期经验。
- 细节先通过主线判断，再决定展开程度：它是否回答标题承诺的问题，是否仍在讨论同一类对象，是否给前文增加原因、证据、反馈或必要限制。材料本身有价值，不等于适合进入本篇；不能仅凭“都和做产品有关”拼接收费产品、个人工具与平台演示。
- 深度来自相关材料里的经验与因果，不靠新增章节、通用方法论或每节末尾的启示。允许某一部分占较大篇幅；删去无关模块时，保留并讲透主线细节，不把全文重新压成几条通用结论。也不能替来源补一条未经讲述的业务链路，让无关案例显得连贯。
- 用户指出一个遗漏时，先检查整篇是否都在过度概括；回看完整来源，修正取材方式，不只往被点名的段落补一句。

例子：不只写“找 10 个潜在客户验证需求”。若来源包含主持人追问嘉宾自己的公司是否也这样做、嘉宾回答“我们会尝试，10 个是好的起点”，应保留这个回应，体现实践程度与数字的含义；来源没有招募渠道，就不能补写成嘉宾的获客教程。

不适用场景：用户明确要求极简摘要、要点清单或逐字翻译时，遵守指定形式；也不为增加人物感而把无关闲聊全部收入正文。

### 公司 / 产品 / 技术分析

适用于目标是理解一个产品、公司、技术机制或生产实践的情况。

先辨明用户要的是产品博客、技术解读还是知识讲解。写产品博客时，产品本身是叙述主角：围绕它让人做什么、遇到什么具体问题、采用了什么做法及带来的体验展开。概念解释只补理解该做法所需的背景，不借产品引出一套通用知识课程。

章节跟随产品问题和叙述推进，不默认按配对、采集、处理、输出等实现模块切分。讲“怎么实现”时，先沿一个具体操作理清：输入从哪里来、由谁处理、怎样变成屏幕上的结果；正文保留必要的中间因果，不能把传感器、算法和反馈分散介绍后就当作解释完成。实现细节要接到可见动作和具体取舍上；字段、参数、接口、兼容性和核验口径只在影响当前理解时展开。用户明确要工程拆解或操作文档时，再采用相应的模块结构。

博客的阅读感来自具体情境、产品选择和自然衔接，不能只给技术说明换口语词，也不能靠虚构亲测、戏剧化场景或密集设问制造趣味。人物、经营和风险按主线需要取舍，不为凑全貌机械增设章节。

避免：

- 公司百科
- 纯功能清单
- 没有产品或系统语境的纯工程教程
- 没有来源支撑的市场预测

### 开发工具 / 平台能力定位

写 SDK、API、托管运行时、开发平台、Agent harness、云服务能力时，首屏先把对象放到开发链路或系统栈里。

优先说明：

- 它处在模型层、API/SDK 层、harness/runtime 层、业务应用层、运维/安全层中的哪一层。
- 它上接什么、下接什么，替开发者接管了哪部分工作。
- 开发者读完能更清楚地判断哪些能力要自建，哪些能力可以交给平台。

避免把开头写成“做 A 就不用，做 B 才需要”的选择题。先说明对象在整个开发链路里的位置，再写适用场景和取舍。

降低门槛靠系统位置、上下游关系和具体运行动作，不靠一层层路牌式导览。不要写成“先把对象说清楚”“可以理解成”“如果你只是……”这类把读者一路牵着走的解释。

## 多来源合并

多个来源讲同一件事时，按知识点写：

- 同一个知识点只定义一次
- 补充不同来源里能加强这个知识点的细节
- 只有来源归属会改变可信度或含义时，才在正文点名来源
- 除非用户要求做来源对比，不要分成“官方文章部分”和“视频补充部分”
- 二手摘要可以帮助选择角度，但公开文章不应该写成调研记录，除非文章本身就在讨论这些摘要

## 多轮反馈后的重构

当用户连续指出“文章不知道在讲什么”“像东拼西凑”“脱离来源类型”“开篇就不对”时，不要继续局部修句。

要回到来源和选题问题：

- 重新判断文章到底精读来源里的哪一个模块。
- 重新写一句内部问题：这篇文章帮助读者理解什么。
- 判断现有大纲是否还成立；如果不成立，整篇重写。
- 用户已经明确要求重写时，不沿用旧正文，只沿用确定的标题、来源、事实和输出路径。

## 翻译与改写

用户要求为了个人学习而翻译时：

- 除非用户要求重写，否则保留原文结构和内容顺序
- 用自然中文，不做生硬直译
- 更适合保留英文的术语保留英文，并补一句中文解释
- 用户明确要求不要总结时，不要擅自摘要
- 如果版权限制不允许在当前渠道提供全文翻译，就改为写原创阅读笔记，或请用户提供可处理的授权摘录
