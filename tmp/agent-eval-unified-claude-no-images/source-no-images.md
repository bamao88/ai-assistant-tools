# 大家都在讲 AI 评测，但 Agent 评测是另一回事

这几个月我每天早上第一件事是打开飞书，看一个 Agent 昨晚替我干完的活。

它整宿守在后台成批跑测试，自己把程序拉起来、把 query 喂进去，跑完一行行读运行日志，把每一次 **MCP 调用**、每一段代码执行、每一回**自我修复**都过一遍，圈出哪几个模块没做好，再直接上手改生产级代码。

我醒来时，飞书里躺着的是一份按优先级排好的 **BUG 列表**，外加一整夜跑出来的结果和一串建议合入的 **pull request**。

我这三个月闭关深度用 Claude Code 和 Codex 自研一套 Agent 评测体系之后，感受最强的一个变化：

**评测不再只是给模型打分的考官，它正在变成能自己改代码、推着产品往前走的自动驾驶。**

这篇我想讲清楚三件事：

1. 这套**自动闭环**到底怎么转起来的；

## 一、自己改代码的闭环

先把上面那个让我兴奋的东西讲透，因为它是这套体系的终点，也是理解其它一切的入口。

过去衡量一个评测团队干得好不好，我只认一个**北极星指标**：模型或 Agent 的**迭代周期**。

一个场景被发现出了问题，到根因被定位清楚，到模型权重被重训、或者 Agent 的 prompt 和架构被调过一轮，再到这个修复被验证确实有效，这一圈走下来要花掉多少时间。一份总分再漂亮，本身都不是产出，**这一圈转得有多快才是**。

过去这一圈，每一环都得靠人去推。到了 AI Coding 时代，它头一回能靠自己转起来。

具体怎么接：评测一发现哪个场景做得不行，Agent 当即扎进代码库，把那段对应的 prompt、把它自己的架构和相关代码挨个翻一遍，对着这个 bad case 动手改，改完跑通就提一个 **pull request**，新版本再回到评测里重跑一轮。

我在自研的 Excel Agent 插件 ExcelMaster 里部署的，就是这么一个**自动 debug agent**，开头那段早上飞书里的 BUG 列表和 PR，就是它的产出。

这套东西对 Agent 产品尤其管用。**把一个 Agent 做得更好，真正的功夫很少花在动模型权重上，大头都在调它的 harness、改它的 prompt、重写那些管编排的代码，而这几样活儿，刚好落在 Agent 自己最拿手的范围里。**

一套好的评测集，配一个能动手的自动评价器，就能直接接上自动的代码迭代，跑成「研发 → 评测 → 优化」的全自动端到端循环。

## 二、闭环怎么转起来

这个闭环不是凭空出现的。它能成立，是因为评测从数据到打分到报告，每一个环节都已经被 Agent 重做了一遍。

**数据采集和标注，从纯人工变成全流程自动化。**

过去靠人一条条挖、一条条标，如今从挖掘、清洗一路到预标注，每一道工序都能甩给 Agent 来做。从千万级的原始数据收到百万、再筛到十万，这条漏斗**每往下一层都安排一个 Agent 守着质量**，这种盯法能达到的精度，纯脚本根本够不着。

**Trigger，从规则匹配升级到语义理解。**

Trigger 是判断「这条数据值不值得拿去评测」的闸门。过去多用代码型 Trigger 检测关键词，举个例子，一条对话里用户冒出一句「你好笨」，背后大概率是模型在这一轮答砸了。现在能换成 **AI 型 Trigger**：抽一批样本喂给一个小模型，让它照结构化标准去掂量这条 query 到底配不配进评测集。

**执行打分，从死脚本变成 agentic workflow，这是变化最大的一块。**它落在三个子环节上：

1. **打分：从 LLM\-as\-Judge 到 Agent\-as\-Judge。**不再是丢一段固定 prompt 让大模型随手给个分，而是派一个 Agent 把 trace 一条条深扒、跟几个头部模型横着比，再交给下一个 Agent 归拢成报告。没有标准答案时，就把 GPT\-5、Claude 拉来当参照系，几个模型投票取最大公约数。

2. **运行：从死脚本到 Agent 看护。**纯脚本只要撞上 Agent 反问用户、中途崩溃这类意外就当场僵住；换成 Agent 盯着批量任务后，该点的鼠标它点、崩了它重启、脚本临时冒 bug 它现场就改，隔天再由另一个 Agent 去验收那几百条 trace，一个管看护、一个管验收。

3. **纠偏：用统计学接住不确定性。**Agent 打分准确率会在九成到九成五之间浮动，我的做法不是假装它准，而是承认它会错。只要下游还守着人工抽检，波动就能算清楚；偏差一旦量出来，就在输入端反向补偿回去，再多挂几个异构数据源互相兜底，单个 Agent 偶尔失手，也拖不垮整套评测的结论。

**报告，从写死的网页变成动态可交互。**

过去的报告是一堆冷冰冰的数字。现在每一类场景的报告都该长得不一样，能点选、能下钻、能一路回溯到训练数据：写代码的任务按写代码的方式可视化，处理表格的任务按表格的方式可视化，两类不该共用一张报表。**一个问题，只有被算成数字、画成图、明摆在工程师眼前，他才会真的动手去改。**

## 三、底层不变

执行层被翻新成这样，很容易让人以为评测是个全新的东西。其实不是。下面这四条科学评测的底层判断，五年前对，今天还对，到 Agent 时代依然对。

**第一，评测的终极产出是迭代闭环，不是报告。**

它是其它三条的总纲：所有采集、标注、打分的设计，最后都要服务于「让这一圈转得更快」。

**第二，对模型团队来说，评测集要略微领先于训练集。**

一套评测集如果只能验出模型早就掌握的东西，对优化就没什么用；它的难度得卡在比模型当下水平再高一点的位置，专门去戳那些它还搞不定的地方。**评测集先往前探半步，训练这边才知道劲该往哪使。**

**第三，好评测集有三条铁律。**

1. **难度故意调得比真实世界更狠。**40% 简单中等、20%–30% 偏难，再永远空出 10%–20% 的极难题；真实世界里万分之一才撞上一次的极端 case，到评测集里得抬到 1% 上下。我管这叫「**撵驴原则**」，但分寸要拿捏，别滑到 Humanity's Last Exam 那种尽考现实用不上的偏门能力。

2. **尽量用真实数据。**训练集可以九成五靠合成，评测集得倒过来，合成顶多占两三成。因为评测集规模大概只有训练集的万分之一，体量小，每条都上真数据也扛得住成本。

3. **单位投入是训练集的 10 到 100 倍。**哪怕请 985 博士来标注研究级难度的题，这账也划算。

**第四，Look at your data。**

分数再好看，也顶不上你亲手去翻一个个 bad case。一个评测平台最值钱的能力，是让人能揪着一条出错的 case 往回查，一直查到病根上：是哪类数据喂少了，还是质量太差，又或者标签本身就标反了。**问题得先被看见，才谈得上被改掉。**

## 一个判断：

## AI Coding 时代，优先自研评测平台

第一节那种「评测直接驱动改代码」，前提是评测跟你自己的代码库、harness 彻底打通，否则无从谈起。于是一个很多团队都纠结的问题就浮上来了：评测平台，是拿现成的来接，还是自己动手搭一套。

很多团队的第一反应，是直接接一个 LangSmith 或 LangFuse 这样的第三方平台。我的判断很明确，在 AI Coding 时代，**优先自研**。

**第三方平台生来就是冲着大众场景做的，什么任务都能接一点；可评测真正的价值，偏偏长在你那个具体的细分任务上，要的是为它量身做的可视化、跟它深度咬合的集成，这恰恰是通用平台给不了的。而 AI Coding 又把自研的成本和门槛砸到了前所未有的低。**

就拿 ExcelMaster 来说，能落地的定制至少有三层：

1. **直接可视化表格数据。**通用平台只会甩给你一段纯文本 trace，读不懂 Excel 的行列结构。

2. **把 Claude Agent SDK 焊进评价器。**打分的那个 Agent 就不再只会报个分数，而是真能分析、真能上手。

3. **数据集平台和本地 harness 无缝衔接。**一条 trace 刚写进盘，打分就自动启动，评测一冒出问题，debug agent 顺着这条线就摸进代码库去改了。

这种贴着细分任务的深度定制加端到端打通，没有哪个通用平台办得到。搁以前自建一套评测平台是件奢侈的事，现在这笔成本，是真降下来了。
