# Claude Code 产品负责人首次开口，把 PM 这件事重做了一遍

你有没有想过，过去十几年所有 PM 课程里讲的"6 到 12 个月路线图、跨团队 PRD 评审、季度对齐、版本规划"，可能在 AI 公司这一两年的内部已经被默默扔进了垃圾桶？

Cat Wu 是 Anthropic 的 Claude Code 和 Cowork 产品负责人，和创造了 Claude Code 的 Boris Chen 搭班子。Lenny Rachitsky 在 4 月 23 日请她上了一期播客，1 小时 25 分钟，几乎没有一句客套话。Anthropic 当下月度 ARR 已经跑到 110 亿美金量级，是当今增速最猛的 SaaS 公司之一，整个产品团队只有 30 到 40 个 PM。Cat Wu 平时基本不公开露面，这场访谈是她第一次系统讲她和 Boris 是怎么把 Anthropic 的产品节奏拉到现在这个程度的。

下面这几节，我把她说得最锋利的几段拎出来重排了一遍，每节都先给你这节的事实底，再补一两句我自己看下来的判断。

**功能上线节奏，从 6 个月压到 1 天**

Cat Wu 进 Anthropic 之后最直接的感受是，传统 PM 那套"对齐多团队、画路线图、写 PRD"的工夫几乎都派不上用场。AI 之前的技术迭代周期慢，所以协调成本是值得的；但模型每隔几个月就跳一次能力，路线图本身就在变形。

- 功能上线周期已经从 6 个月压到 1 个月，常规节奏是 1 周，偶尔 1 天
- 内部叫"Evergreen Launch Room"：工程师 dogfood 跑通后直接发贴，文档负责人 Sarah、PMM 负责人 Alex、DevRel 的 Tara 和 Lydia 跳进来，第二天就能把发布物料和文档全部出完
- 整条链路没有 launch readiness review，没有功能冻结日，没有跨团队 PRD 评审
- 网上有人猜他们快是因为内部偷用 Mythos 模型，Cat 当场否了，原话："we do use the models internally and I think this has increased our rate of shipping a little bit but I don't think it explains the bulk of the increase"
- 真正的原因是预期：一个工程师有个想法，团队默认它周末就该上线，每一道流程都因此变得"很贵"，自然被磨掉

我做过出海产品，深知传统团队走完这条链路至少两周。Anthropic 把它压成一天，本质不是流程更高效，是流程被砍掉了。Cat 用的词是"remove every single barrier to shipping things"——这听上去像句口号，但她接着讲的细节让人相信她不是在喊场面话。预期一旦定到"周末就该上线"，所谓"流程"就从默认值变成了证明题，谁要保留一道流程，谁就得说清楚它为什么值得花掉两周。

**Research Preview 是默认发布姿态，代价是产品一致性**

如果你看 Anthropic 过去半年的功能页面，会注意到一个细节：他们绝大多数新功能都被标了一个 "Research Preview" 的小标签，写着"早期产品，可能不会一直支持"。这看起来像免责声明，Cat Wu 把它当成最重要的发布姿态来用。

- Research Preview 把"承诺"降级成"邀请测试"，一两周内就能丢出去拿反馈
- 它接受了一个代价：**产品一致性的崩塌**。Cat 原话："we're sacrificing product consistency"
- 同一种能力同时存在多个 form factor：终端里的 Claude Code、桌面里的 Claude、网页和手机上的远程会话、Cowork 的文档协作入口
- 新用户经常分不清同一件事该在哪个入口做，Anthropic 的解法不是替用户选 best path，而是同时放出去，让用户用脚投票
- 用 `/powerup` 这类内置 onboarding 补学习成本——Cat 说他们原本坚持"产品该直觉到不需要 onboarding"，最后被现实打脸，加上了

这套逻辑推翻了我以前根深蒂固的一条产品哲学：一个用户场景就该有一个 best path。但回过头想，AI 时代的形态本身还在塌缩，PM 提前替用户拍板一条 best path 反而是越位。Anthropic 这种"先放出去，让数据说话，再回收冗余"的姿态，本质上是把产品决策的权力从内部审美让渡给真实用户。它的成本不是没有，是新用户的迷茫；他们承认这一刀，所以才有 PowerUp 这种"被迫加上的 onboarding"。这件事的关键不在 PowerUp 本身，在于他们愿意公开承认自己原来的产品哲学被现实打脸——多数公司不会公开退这一步。

**AGI 信仰要刚刚好，多一分少一分都做不出产品**

整场访谈我觉得最锋利的一句话，是 Cat Wu 谈"AGI-pilled 的度"。她说，做 AI PM 最难的活，不是想象未来 AGI 多强、然后为那个未来设计产品。那种产品反而很容易做，本质就是一个聊天框加一堆 MCP 工具，模型自己会问问题、自己调工具、自己 patch 自己的弱点。真正难的是反过来：榨干当前这一代模型的能力上限。

- Cat 原话："It is very hard to be the right amount of AGI pilled"
- 极端 1：完全相信下一代 AGI 万能 → 做出来的产品今天根本不能用
- 极端 2：完全不相信模型还会跳 → 做出来的产品下一次模型升级就要废弃
- 早期 Claude Code 案例：给一个跨 20 处的重构任务，模型改完 5 处就停了。研发同事 Sid 模仿人类工作方式，加了 to-do list 工具进去，Claude 拿到任务先列清单再逐条划掉，成功率立刻拉满
- Cat 把这类东西叫做 "crutches"（拐杖）——它不是产品决策，是给一个"还不够好的模型"打的补丁
- 怎么练这个能力：(1) 每天大量用模型，让它解释它自己为什么做错；(2) 找团队里 5 个"vibe 最准"的人，专门听他们的反馈；(3) 写 eval——不是几百道的学术 benchmark，是 10 道贴着产品场景的核心 eval

读到这一段，我立刻想到了自己在训练营里反复讲的一个判断：AI 产品设计必须严格约束在当前技术边界内，不能拿一个技术做不到的功能去做产品规划。当年带 AI 写真这个项目，设计同学不了解 Stable Diffusion 的真实边界，把方案做成"巴黎/地中海/微笑/大笑"这种刻板选项，结果完全没竞争力，我得自己掏腰包把国内外几十个 photo AI 都跑一遍，才把方向纠正回来。这跟 Cat 说的"AGI-pilled 的度"是一件事的两面。你不可能脱离当前模型能力去做产品决策，你只能贴着今天模型的边缘做，然后等下一次跳跃。能做这件事的人凤毛麟角，因为它要求你既不能太信 AGI，也不能不信 AGI。

**PRD 没死，但日常运转靠的不是 PRD**

我一开始以为 Anthropic 已经把 PRD 完全砍了，毕竟节奏这么快，写 PRD 几乎是奢侈。Cat Wu 的回答比想象的细：PRD 在两种场景下还在写，但日常运转靠的是另外两件东西。

- PRD 还会写的两种场景：(1) 高歧义功能，团队对要做什么的理解明显不一致，一页纸 PRD 把目标、delightful 用例、failure modes 列清楚，比开三场会划算；(2) 重基建项目，时间跨度本来就要几个月，写 PRD 是工程协调的必要
- 日常运转替代 PRD 的两件东西：
  - 每周的 metrics readout，整支团队一起过指标——所有人都得了解业务的每一个维度怎么在跑、什么在驱动它
  - 一份"团队原则文档"，写清楚谁是核心用户、为什么是核心用户、什么值得 trade-off、什么不值得
- 这份原则文档的目的不是给 PM 撑场子，是让团队里任何一个人都可以在没有 PM 在场的情况下做出和团队一致的决策
- 结果：团队里几乎不需要"等我决定"的环节，每个人都可以自己往前推

我做过一段时间增长团队，深知大部分 PM 会把"信息流通"当成自己的护城河，越关键的判断越藏在自己脑子里。Anthropic 的做法正好相反，他们把决策原则尽量放到所有人都能读到的地方，PM 反而不再变成瓶颈。这件事对 PM 这个职能是双刃剑：你失去了"信息独占"带来的安全感，但获得了"团队可以不等你决策"带来的真正杠杆。Cat 这种打法，本质是用文档把自己的判断标准开源出去，让团队可以平行地基于同一套判断推进。

**他们更愿意招"有 taste 的工程师"，不是"会写 PRD 的 PM"**

Anthropic 招 PM 的方式让我有点意外。Claude Code 这条产品线的 PM 几乎全是工程师出身。Cat Wu 自己之前是工程师，干过短暂的 VC，然后才到 Anthropic。设计师也大多有前端背景。这并不是说他们觉得 PM 这个岗位没用，恰恰相反，他们认为能 own 整条产品链的人比纯 PM 更稀缺。

- Claude Code 团队里有很多工程师，看到 Twitter 上一条用户反馈，自己想清楚、自己写代码、自己周末上线，整个过程几乎不需要 PM 干预
- Cat 描述的"理想 AI PM"画像：能感知模型能力变化、能从"用户怎么 abuse 当前产品"里看出趋势、能把方向定下来稳定执行、在模型跳跃比预期早或晚时迅速调整路径
- 为什么"工程师背景"在未来几个月特别值钱：你能更准估算一个功能"该花多大力气"。便宜的就别开会，自己花一小时做完；贵的就在决策时把 trade-off 想清楚
- Cat 看得很清醒：她说这种"工程背景特别值钱"的窗口可能就几个月，因为每隔几个月模型能力就跳一格，所谓"高价值技能"也跟着变
- 她原话："I think product taste is still a very rare skill to have and we'll pretty much hire anyone who we feel has demonstrated this strongly"

这件事让我想起我自己在训练营里反复讲过的一个判断：市场上所谓"有 AI sense"的 PM 几乎都太浅，本质不是候选人不够聪明，而是大家对"什么是好的 AI PM"这个理想画像本身就不清晰。Cat 这场访谈，其实就是当下离这个理想画像最接近的一份描述——她讲清楚了这种人为什么稀缺：判断能力是从大量动手中长出来的，光听课、看 PRD 模板，长不出来。你光是模仿她说的形式（写 eval、用模型、读反馈），不够；你得有足够多的"在产品里被模型坑"的真实经验，那个 taste 才长得出来。

**模型升级时，最重要的动作是删功能**

整场访谈我听到最反直觉的一段，是 Cat Wu 讲他们每发布一次新模型，团队最重要的动作不是加功能，而是删功能。

- 前面提到的 to-do list 拐杖，在 Opus 4 之后 Claude 已经能自然而然拆任务、跟踪任务、收尾——这个工具在产品里逐步淡化，模型用不用都行
- 每一次大模型升级，团队会把 Claude Code 整个 system prompt 从头读一遍，问每一段提示词"模型现在还需要这个提醒吗"，不需要的就删掉
- 删掉之后真正的影响：原本为弱模型加的辅助逻辑清掉之后，强模型可以沿着更自然的路径释放能力
- 另一面同时在跑：刻意建那种"还没工作"的产品。code review 就是这么熬出来的——之前几次产品级 code review 都失败，模型不够强、误报太多，他们坚持把原型留着
- 等 Sonnet 4.6 和 Opus 4.5 上来，把模型换上去，code review 突然就成立了。现在 Anthropic 内部工程团队已经把 Claude code review 当成合并前的必经一道
- Cat 总结："Build products that don't necessarily work yet so that you know what is missing for this product to work"

这套打法在我自己常用的"上一代→当前→下一代"的 PM 框架里非常工整。我在面试辅导里反复跟学员讲：好的 PM 要能用三分钟讲清一个领域上一代技术的核心范式、当前一代的核心范式、下一代的核心方向。Anthropic 在产品上做的事情其实就是这个框架的实操版本：当前代模型只能撑起某一类粗糙功能，他们就先做粗糙功能并标 Research Preview；同时把下一代模型可能解锁的产品原型先搭起来放着；当模型真正跳跃，他们就立刻拔出已经放好的原型替换。这意味着他们的产品永远走在能力曲线的边缘，而不是落在能力曲线后面。这一招最难学的不是"加什么"，是"删什么"——大多数团队对自己加进去的功能有深度感情，要他们因为模型变强主动删功能，比加功能难得多。

**Eval 和 100% 自动化，是被低估的 PM 新技能**

访谈快结束的时候，Cat Wu 谈到一个她说"大多数 PM 都没意识到"的新技能：写 eval。她不是指那种几百道题的学术 benchmark，而是十道左右、贴着你产品最关键场景的 eval。

- Cat 原话："You don't need to build hundreds of evals for them to be useful. Just building 10 great evals is important"
- 团队里这种事并不是每个人都爱做，但凡是做得好的人，对模型的判断力都明显高出一截
- 一小撮 PM 把这件事当成主要工作，跟 research 团队联动，定义 Claude Code 的具体行为目标
- 另一个被低估的功夫：把自动化做到 100%，而不是 95%。Cat 原话："95% automation is not really automation"
- 95% 的代价：你既要花时间做，又要花时间盯，杠杆是负的
- Cat 自己在教 Cowork 帮她 inbox zero，花了不少时间还没做到 100%；Lenny 当场承认他自己也卡在这个坑里——邮件 95% 分对，但 5% 重要邮件被误丢进 spammy 文件夹，结果反而损失更大
- Cat 的劝告：把最后那 5% 啃下来，剩下的 95% 才有意义

这件事和我这两年在训练营里一直讲的方法论几乎完全重合。我在指导学员做项目时反复强调评测驱动：先人工标注 Top 5 答案，能召回到这 5 个就算成功，别一开始就上多维评测分散精力；评测暴露的常常不是模型问题，而是产品流程设计的问题，所以解法不是改评测，是改产品。这套思路和 Cat Wu 讲的"10 个好 eval 比 100 个糟 eval 有用"是同一个判断的两种表达。至于 100% 自动化这一刀，是我自己也反复踩过的坑——你以为 95% 已经很高了，但只要还有 5% 兜底要你盯，这个自动化对你的杠杆就是零甚至是负的。

**我的思考：AI 时代真正稀缺的，是离能力曲线最近的那群人**

我把这场访谈听完，最大的感受其实不是某条具体的方法论，而是一种结构性的恐惧。Anthropic 的所有打法加起来，本质上是在做同一件事：让产品决策尽可能贴着模型能力曲线本身。模型能力跳一格，产品能力跟一格；模型多了一种行为，产品立刻搭原型留着；模型砍掉一项弱点，产品立刻把对应的拐杖删掉。整个组织不是在追赶模型，是在和模型同步呼吸。

这套打法能跑通有一个前提条件，Cat Wu 在访谈里讲得也很直白：Anthropic 把"让安全的 AGI 服务全人类"这条 mission 放在任何一条产品线之上——她原话是 "If Claude Code failed but Anthropic succeeded, I would be extremely happy"。两个内部产品抢资源的时候，判断标准不是哪个 ARR 高、哪个 KR 好看，而是哪个更服务 mission；输的那一方接受、配合、推迟自己的发布。这件事的成本不是没有——每个产品 leader 都得愿意把自己的 KR 让出去——但收益是公司可以整体掉头，不需要在产品线之间内耗。我从来没在几千人规模的公司里见过这种共识真正在跑。这也是为什么前面所有"删功能、砍流程、放弃一致性"的打法能落下去：当一个组织默认值是公司层面的，砍自己功能就不是政治问题，是默认动作。

这件事在十年前的互联网产品里是不存在的。那个时代技术的迭代速度远低于产品的迭代速度，所以"产品定义"才有意义、PRD 才有意义、6 个月路线图才有意义——底层不动，你才可以基于不动的底层做加法。AI 时代正好相反，底层每三个月动一次，谁离底层最近、对底层变化反应最快，谁就吃掉那一波红利。这就是为什么 Anthropic 招"有 taste 的工程师"而不是"会写 PRD 的 PM"，为什么他们用 Research Preview 而不是 release version，为什么他们写团队原则而不是路线图。所有这些做法都指向同一个底层逻辑：让组织对模型变化的延迟尽可能短。

我看着这套打法，会想到 PC 转互联网、互联网转移动的两次切换。每一次切换都不是因为某家公司多努力，而是因为他们更早抛弃了上一代的范式。AI 这次切换最大的难点是，旧范式里"成功"的人最容易掉队——因为他们花了很多年练成的能力（管理路线图、协调多团队、写漂亮的 PRD）在新范式里变成了拖累。Cat Wu 那句"jobs are fake"，听起来像玩笑，但她讲的是一件认真的事：在能力曲线快速变形的时代，岗位描述本身就是个滞后指标，你抱着旧岗位描述去工作，等价于把自己绑在了过去。

我自己这一两年反复在讲一个判断：2026 是广义 AGI 的元年，白领工作要开始大幅变化。我之前以为这种"变化"是岗位被取代，听完 Cat Wu 之后我觉得没这么简单。真正的变化是岗位边界塌缩——工程师吃掉 PM 的判断、PM 吃掉 designer 的执行、designer 学着写代码，三者重叠的中间地带变成新的高价值区。在这个塌缩里，能拿到红利的不是某个固定职能，是那些贴着模型能力曲线、愿意每三个月把自己的方法论重写一遍的人。Anthropic 正在用一家公司的规模演示这件事可不可能。从他们 110 亿美金 ARR 的曲线看，答案已经写在那里了。

接下来一年想跟上节奏的产品和技术 leader，不必把 Anthropic 当成神话，但至少可以做一件事：把自己手里那份 6 个月路线图打开，问一下——假如这是 1 个月，我会先砍什么。这个问题问出来的瞬间，旧范式就开始松动了。

也欢迎大家留言聊聊你自己在 AI 公司或者团队里看到的节奏变化。
