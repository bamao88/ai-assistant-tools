# 大模型不认识自己：谷歌用一个轻量 Skill 把 Agent 成功率从 28% 提到 97%

你有没有想过，我们花了那么多时间调教 prompt、精心设计 Agent 架构，但有一个最基础的问题，几乎所有人都默认它"不重要"——大模型根本不认识自己。

它不知道自己发布之后的 API 长什么样。它不知道自己的 SDK 上周刚改了接口。它更不知道最新版的调用方式和它训练时见过的那个版本有哪些区别。每次你让 Agent 帮你写调用 Gemini API 的代码，它很可能给你写出一段三个月前就已经废弃的旧写法，还写得那么自信。

这不是谷歌一家的问题。所有大模型都活在自己训练时的那个快照里。软件世界在飞速迭代，模型知识却是冻住的。这个矛盾越来越难绕过去。

最近谷歌 DeepMind 的两位工程师 Philipp Schmid 和 Mark McDonald 发了一篇技术博客，讲他们怎么用一个叫"Gemini API developer skill"的东西来解决这个问题。我读完之后觉得，这篇文章值得仔细拆一遍——不是因为谷歌用了多厉害的技术，而是因为它揭示了一个被低估的工程原则，而且数字讲得很直白。

---

**大模型自己不认识自己，这件事比你想的更严重**

谷歌在博客里直接承认了一件有点尴尬的事：他们训练的模型，对自己上线后的状态是一无所知的。Gemini 模型在训练时，就算能看到关于自己的各种信息，也不可能看到上线以后 SDK 的变化、API 的调整、新推出的功能。

这会带来一个具体的工程问题：如果你让 Agent 帮你写一段使用 Gemini API 的 Python 代码，它极有可能调用一个已经过时的包，或者用一个在最新版本里早就废弃的参数写法。用旧 SDK 就是这个测试里的"失败"标准。

让我深思的是，这个问题并不是偶发 bug，而是大模型知识结构的系统性缺陷。我之前在课上讲模型知识新鲜度时提到过一个反直觉的现象：训练集截止日期并不等于知识边界，而且新事件的学习深度其实比旧事件更浅。一件发生在二十年前的事情，互联网上有大量的报道、分析、评论、复盘，模型学得透、吃得深；但一件三个月前刚发生的事，互联网还没来得及消化它，模型只是浅浅地看了个开头。

这意味着 SDK 变化、API 更新这类快节奏的技术迭代，恰恰是大模型最难跟上的那类知识。模型会用，但用的是旧版本。它用得很自信，因为那些旧写法在训练数据里出现的频率更高。

---

**他们造了个什么东西**

面对这个问题，谷歌的解法并不是重新训练模型，也不是上复杂的 RAG 系统，而是做了一个轻量到几乎让人觉得"这也行？"的东西——一个结构化的文本文件，叫做 Gemini API developer skill。

这个 skill 的内容其实很朴素：解释 API 的功能概览，列出当前在用的模型和各语言的 SDK，给出每个 SDK 的基础示例代码，然后指向官方文档的入口，告诉 Agent"如果你不确定，去这里查最新的信息"。

就这些。没有向量检索，没有图谱，没有复杂的召回逻辑。整个 skill 的工作方式是：当 coding agent 开始处理任务时，它的 system instruction 里有一段提示，告诉它"你有两个工具可以用——`activate_skill` 来激活这个 skill，`fetch_url` 来抓取最新文档"。Agent 看到 skill 里指向的文档地址，可以实时去拉最新的内容。

安装方式也极简：一行 npx 命令，全局装好，就在你的开发环境里生效了。

我觉得这个设计巧妙的地方在于它的分层思路。知识分两层：静态的部分（API 架构、模型列表、基础示例）写死在 skill 文件里；动态的部分（最新文档、接口变更）通过 fetch 工具在运行时实时拉取。它不试图把所有知识都塞进 skill，而是把 skill 定位成一个"导航员"——我告诉你方向，具体的细节你自己去源头拿。

这让我想起我们一直在强调的上下文工程理念：上下文不等于 prompt，它是一整个世界观。skill 做的事，本质就是在运行时给 Agent 构建了一个正确的"我在哪个世界里"的认知框架。RAG 是一种上下文注入，AGENTS.md 是一种上下文注入，skill 也是一种上下文注入。形式不同，本质是一样的——你给模型什么上下文，决定了它能产出什么质量的回答。

---

**数字说话：28% 跳到 97%**

谷歌为这个 skill 专门设计了一套评测体系，117 道提示词，覆盖 Python 和 TypeScript，测试场景包括 Agent 构建、聊天机器人、文档处理、流式输出等各类任务。判断标准是：你的代码用的是不是当前的最新 SDK？用了旧 SDK 就算失败。

结果出来让我一时没反应过来。

没有 skill 的时候，gemini-3.1-pro-preview 的通过率是 28.2%。加上 skill 之后，直接跳到 96.6%。差不多同一个模型，同一批任务，就因为加了一个结构化的文本文件，成功率提高了将近三倍半。

但这里有一个让我真正坐下来想了很久的细节：这个效果，只在最新的 Gemini 3 系列上才成立。

同样加了 skill，旧的 2.5 系列模型提升幅度要小得多。3.0 Pro 和 3.0 Flash 在没有 skill 的情况下，基线成功率只有 6.8%，加上 skill 有明显改善，但远没有 3.1 Pro 那么戏剧性。

谷歌的结论只有一句话：**skills work, but they need reasoning**。

这句话表面简单，但背后是一个很深的工程判断：skill 不是在替模型存储知识，它是在给模型提供导航信息，让模型自己去推理"我应该怎么使用这些信息、我应该去哪里查最新的内容、什么时候该调用 fetch_url"。如果模型的推理能力不够，即使你把导航信息写得再清楚，它也不一定知道该怎么用。

这打破了一个常见的误解：上下文注入是银弹，给模型更多信息就能解决问题。信息提供只是第一步，模型能不能用好这些信息，取决于它的推理能力。

---

**评测先于一切**

我在看这篇博客的时候，有一种特别熟悉的感觉——是因为 117 道测试题、两种运行模式、跨类别的详细分析，这背后是一个认真设计的评测体系。

我在课上一直有一个判断："没有评测的 AI 产品就是在盲飞。"谷歌能发现 skill 的效果，能发现"旧模型用 skill 收益有限"，能发现"SDK Usage 类别通过率比其他低，失败案例有一类是用户明确指定要 Gemini 2.0 的旧模型"——这些细颗粒度的洞察，都是靠一个认真构建的评测体系才能看到的。

如果他们只是"感觉上"测了一下，不会有 28.2% 这个数字。没有这个数字，他们不会知道自己的模型在自己的 API 上只有三成不到的成功率，也不会有做 skill 这件事的动力和方向感。

这让我想到一个更普遍的道理。很多团队做 AI 产品，先改 prompt、先换模型、先加工具，但没有一套 eval 告诉他们改了之后是变好了还是变坏了。他们在盲目迭代。偶尔改对了，但不知道为什么对；改错了，也不知道哪里出的问题。谷歌这篇博客的示范意义之一，是展示了一个严肃的工程团队怎么用数字说话、怎么用分类评测来理解自己的系统在哪里出了问题。

评测集是资产。117 道题是资产，分类测试的框架是资产，"用旧 SDK 即为失败"这个清晰的判断标准是资产。这些比 skill 本身更值得学习。

---

**skill 有一个真正的对手：直接写进 AGENTS.md**

谷歌在博客末尾提到了一件他们不得不诚实承认的事：Vercel 做了独立的对比测试，结果发现直接把指令写进 `AGENTS.md` 的效果，比通过 skill 机制激活的方式还要好。

这个结论让 skill 这套机制处于一个有趣的位置。

skill 的逻辑是：用一个单独的文件描述能力，让 Agent 自己决定什么时候激活它。这多了一层"Agent 需要判断要不要用 skill"的推理步骤。而 AGENTS.md 是直接把信息放在 Agent 每次启动都能看到的地方，没有这层间接性。

从上下文工程的角度来看，AGENTS.md 的做法更直接：它是静态的、确定的上下文注入，不依赖 Agent 自己的决策。skill 机制则引入了一个动态决策环节，在推理能力强的模型上可以运转良好，但也带来了新的失败模式——Agent 可能该激活 skill 的时候没激活，或者激活了但没有正确使用 fetch 工具。

谷歌自己也承认，skill 的更新机制是一个未解决的问题。如果用户安装完 skill 就不更新，几个月后 skill 里的信息可能比没有 skill 还要有害——它会给 Agent 一个"自信但错误"的知识基础。文档说"我们当前的 SDK 长这样"，但其实已经过时了。

所以 skill 的竞争对手，不只是旧的知识空白，还有比它更轻量的解法：把关键信息直接写进 AGENTS.md，让 Agent 每次都能读到，不需要任何激活机制。

这两条路背后其实是两种不同的上下文管理哲学。skill 相当于一个"按需加载"的知识模块，适合大型开发环境里有大量领域专业知识的场景；AGENTS.md 是"全局预加载"，适合需要稳定、确定传递给 Agent 的核心上下文。两者不是竞争关系，而是适用场景不同。

---

**skill 作为一种产品形式，值得认真想想**

我在想的另一件事是：谷歌发布 Gemini API skill 这件事，不只是一个技术解法，它还是一种产品形式的尝试。

任何开发者、任何 SDK 维护者、任何 API 提供方，原则上都可以做自己的 skill。你把你的产品、你的接口、你的最佳实践写成一个结构化的 skill 文件，发布到 GitHub 上，让集成了 skill 机制的 coding agent 能够找到并使用它。这是一种让 AI 生态里的"知识供给"变得可维护的路径。

但问题在于：这需要维护。谷歌能保证 Gemini API skill 跟上模型更新，但大量的小型 SDK、开源库、企业内部 API，谁来维护它们的 skill 文件？如果 skill 文件落后于实际接口，危害比没有还大。

这个困境不陌生。它和 RAG 里的知识库更新问题是同构的，和 AGENTS.md 会过时是同构的，和所有静态知识注入机制面临的问题都一样——上下文是活的，知识是活的，但文件是死的。解决这个矛盾需要运营，不只是技术。

---

**我的思考：这篇文章真正在讲什么**

表面上，谷歌这篇博客在讲一个轻量的工程技巧——用 skill 文件解决模型知识截止问题。但让我读完之后持续在想的，是一个更底层的判断。

我们正在进入一个"上下文工程才是真正战场"的时代。

模型能力在快速提升，但这个提升本身并不解决知识新鲜度的问题。哪怕是 Gemini 3.1，在没有任何上下文辅助的情况下，用自己的 API 写代码的成功率只有 28%。这是一个非常低的数字，低到有点反直觉——你会以为谷歌的模型对自己的 API 应该很熟悉。但事实是，模型的"自我认知"取决于训练数据，而训练数据是静态的快照。

这让我觉得，这篇文章揭示的不只是一个技术问题，而是 AI 产品开发的一个基本架构原则：**不要依赖模型内化的静态知识，而要在运行时给模型注入正确的当前上下文**。

这和 PC 时代到互联网时代的一个转变有点像：本地软件把所有数据存在本地，互联网应用把数据放在云端、运行时动态拉取。静态存储变动态获取，降低了维护成本，提高了时效性。现在的 skill、AGENTS.md、RAG，做的是类似的事——把模型依赖的知识从"训练时固化"转变为"运行时注入"。这个转变的方向是对的，但工具链还不成熟，更新机制还是薄弱环节。

还有一件事让我一直在想：skill 有效，但需要推理能力强的模型。这个发现背后有一个有意思的产品逻辑——上下文工程和模型能力不是替代关系，而是乘法关系。上下文写得再好，如果模型没有足够的推理能力来使用这些上下文，效果打折。反过来，推理能力再强，如果给的上下文是错的、旧的、残缺的，效果也打折。

这两件事必须同时做好，才能在实际任务上达到 97% 这样的成功率。

对于我们在做 AI 产品和 Agent 的人来说，这意味着一个务实的建议：先把你的产品上下文体系建好——什么信息是 Agent 必须知道的，哪些是静态的可以写死，哪些是动态的需要运行时拉取，哪些是用户的实时状态需要实时注入。把这个体系设计清楚，比选什么模型更重要。然后选择一个推理能力足够强的模型，让它在这个上下文框架里工作。

谷歌用 117 道测试题验证了这件事，从 28% 到 97%，差距就是一个设计良好的上下文注入机制加上一个推理能力足够强的模型。

这个公式，不只适用于谷歌的 SDK，也适用于你正在做的每一个 AI 应用。

欢迎留言聊聊你在产品里怎么处理上下文注入的问题，我很好奇大家踩到了哪些坑。
