# 大多数人造的 Agent，根本没法上生产

你有没有想过，我们花了大量时间搭建的 Agent，其实离真正"跑起来"还差着整整一层？

我最近越来越频繁地遇到一个场景：一个 AI Agent demo 效果惊艳，所有人都说"这个可以"，然后工程师开始推进部署——然后就开始头大。日志在哪里？崩了怎么重启？用户 A 的数据会不会跑进用户 B 的上下文？人工审核在哪一步介入？这些问题一个都没有答案，因为当初根本没想到。

这不是个别团队的问题。这是几乎所有人在构建 Agent 时都会踩的坑——我们太专注于"让它能用"，完全没有思考"让它在生产环境里可靠地跑"是两件截然不同的事。

当我读到 LangChain 发布的这篇技术指南《The Runtime Behind Production Deep Agents》时，我第一反应是：这终于有人把这件事说清楚了。不是又一篇"如何用五行代码搭一个 Agent"，而是在认真讨论一个真实问题：把 Agent 送上生产，需要哪些基础设施，为什么需要，怎么做。

---

**Harness 和 Runtime：两件事，大多数人只做了一件**

文章开篇有一句话我觉得击中要害："To build a good agent, you need a good harness. To deploy that agent, you need a good runtime."

Harness（线束）是你围绕模型构建的那一层——提示词、工具定义、技能、调用逻辑。这是大多数人在做的事情：调提示词、接工具、让 Agent 在 demo 里表现漂亮。这一层很重要，但它只是冰山一角。

Runtime（运行时）是 Harness 下面那层——持久化执行、记忆管理、多租户隔离、人工审核介入、可观测性监控。这一层是让 Agent 真正在生产环境里跑起来的基础。没有这层，你的 Agent 是一个随时可能崩掉、数据可能混乱、出了问题根本不知道发生了什么的定时炸弹。

我在带 AI 产品训练营的时候，经常遇到学员展示的 Agent 项目，demo 环节做得非常漂亮，但一旦问"多个用户同时使用怎么处理"，或者"任务运行到一半进程挂了怎么办"，就卡壳了。这不是他们不努力，而是整个行业在讲 Agent 开发时，默认把 Harness 讲完就算完了，从来没有人认真讲 Runtime 这回事。

这篇文章是我见过的第一篇把 Runtime 层说得足够清楚的技术文章。

---

**持久化执行：被大多数人忽略的地基**

文章花了相当篇幅讲"Durable Execution"（持久化执行），我觉得这是整篇文章最底层的洞见，也是最容易被跳过的一部分。

传统的 Web 请求是毫秒级的——你发一个请求，服务器处理，返回结果，一切在 200ms 内结束。但 Agent 的执行逻辑完全不同：它是一个循环，模型思考、调用工具、观察结果、再思考、再调用，整个过程可能跑上几分钟甚至几十分钟。在这个过程里，任何地方出了问题——进程崩了、网络断了、做了滚动部署——都意味着前面所有的工作白费，所有的 token 都打了水漂。

更复杂的情况是：Agent 需要在某个节点等人工确认。比如一个财务 Agent 准备发起一笔付款，它生成了付款单，然后需要等财务主管审批。这个等待时间可能是三十秒，也可能是三天。如果这期间你要一直占着一个进程等着，整个系统的资源占用是无法承受的。

持久化执行解决的就是这个问题：Agent 的每一步（LangChain 叫 super-step）都写入检查点，存到 PostgreSQL。进程崩了，下一个 worker 从最后的检查点接着跑。等人工审批的时候，进程可以完全释放，审批完成后，系统从检查点恢复，接着执行。

这个设计听起来简单，但它是后面所有能力的地基。流式输出要依赖它，人工介入要依赖它，定时任务要依赖它，并发处理要依赖它。没有持久化执行，这些都是沙堡。

我在研究 Claude Code 的底层架构时就意识到一件事：Agent 框架里那些"工程感"最强的设计，往往是处理"中断和恢复"的部分。怎么让一个长任务在任意位置停下来，保住状态，之后从容恢复——这才是真正难的地方，也是能和竞品拉开差距的地方。

**记忆的两种形态：短期和长期，缺一不可**

记忆（Memory）是 Agent 的另一个核心问题，而且很多人对它的理解是错的。

常见的误解是：记忆 = 把对话历史塞进上下文。这是短期记忆，而且还是最朴素的实现方式。短期记忆的问题是显而易见的——上下文窗口有限，随着对话越来越长，早期的信息会被稀释甚至截断。

文章区分了两种记忆：

短期记忆（Short-term Memory）是在一次对话内积累的东西——这一轮的消息、工具调用结果、中间状态。它属于这个 thread，thread 结束了它也结束了（在概念上）。

长期记忆（Long-term Memory）是跨对话持续存在的东西——用户的偏好、项目的规范、知识库里的积累。这些不属于任何单次对话，是用户级别或组织级别的上下文，应该在每次对话里都能被访问到。

这个区分让我想起我一直强调的一个判断：2026 年最重要的 AI 技能不是提示词工程，是上下文工程。你给模型什么上下文，决定了它能产出什么质量的回答。而记忆管理，本质上是上下文工程的动态版本——它要解决的问题是：在正确的时间，把正确的历史信息组装进来，而不是把所有东西都塞进去。

LangChain 的做法是用一个 key-value 的 store，通过命名空间（namespace）来组织跨对话的记忆，支持语义搜索，而不只是精确匹配。更重要的一个设计选择是：这个 store 默认存在你自己的 PostgreSQL 里。这意味着你的记忆数据是你自己的，你可以用任何方式分析它、迁移它、在 Agent 框架外面使用它。

这个"数据归你"的设计哲学，和某些把记忆存在加密黑盒里的做法，形成了鲜明对比。一个月内在同一个 Agent 上积累的用户行为数据，是整个系统里价值最高的资产之一。你不应该把它锁在一个你无法导出的地方。

**多租户不只是权限问题，是三个完全不同的层**

多租户（Multi-tenancy）是所有 To B 产品都绕不开的问题，但在 Agent 场景里它比普通 SaaS 复杂得多，因为 Agent 不只是在读数据，它还在替用户做事。

文章把多租户分成了三层，这个划分我觉得非常准确：

第一层是用户数据隔离。用户 A 的 thread 不能被用户 B 访问，用户 A 的记忆不能跑进用户 B 的上下文。这是最基础的隔离，通过认证和授权中间件实现——每个请求进来先验证身份，再通过 filter 确保只能访问自己的资源。

第二层是 Agent 代替用户做事时的授权。这是一个很有意思的场景：用户的日历、用户的 Slack、用户的代码仓库，Agent 需要用用户的身份去操作这些东西。传统的 OAuth 流程是由用户自己发起的，但 Agent 场景里是"用户告诉 Agent，由 Agent 代为执行"。LangChain 的 Agent Auth 模块处理的就是这个 OAuth 代理和 token 存储，让 Agent 能在后续的 run 里用用户的授权执行操作，而不需要每次都拉起一个授权流程。

第三层是平台操作者的权限管理——谁可以部署 Agent，谁可以看 trace，谁可以改配置。这是 RBAC，更接近传统的权限管理，但在 Agent 部署场景里也不能缺少。

这三层的关系是层叠的，不是互相替代的。我在辅导学员做 Agent 项目时发现一个规律：大家第一版上线基本只考虑了第一层，被用户投诉数据跑乱了才开始补第二层，Agent 出了安全问题才去加第三层。与其事后打补丁，不如一开始就把框架建对。

**Human-in-the-Loop：不是锦上添花，是很多场景的刚需**

人工介入（Human-in-the-Loop，HITL）这个功能听起来有点奇怪——我们不是要让 Agent 自动化吗，为什么还要人工介入？

但文章提出了一个让我很认同的反向观点：大多数人没有意识到，HITL 不是 Agent 能力不足时的妥协，而是很多业务场景的根本需求。

文章举了两个具体场景：

第一个是重要操作前的人工确认。Agent 准备发一封邮件给客户，准备执行一个财务转账，准备删除一批文件——在这些高风险操作前，你不想让 Agent 直接执行，你想让相关人员看一眼，可以批准，也可以修改后批准，也可以拒绝并给出原因让 Agent 重新来过。

第二个是 Agent 遇到歧义时主动提问。"我找到了三个匹配的配置文件，你想改哪个？"这不是 Agent 无能，而是它足够聪明，知道在不确定的时候不要自作主张。

这两个场景都需要 Agent 能做到：在执行过程中的任意位置暂停，把状态完整保存，等待人类的输入，然后带着人类的输入，从暂停的地方原样继续。

LangChain 的实现里有一个我觉得设计非常巧妙的地方：`interrupt()` 函数可以放在代码的任意位置，包括工具函数内部。这意味着审批逻辑是和工具本身绑定的，而不是在 Agent 的主循环里配置的。你写了一个"发邮件"工具，你可以在这个工具里嵌入 `interrupt()`，这个工具在被 Agent 调用时就会触发审批流程。这个设计让 HITL 的粒度可以非常细，而不需要改动 Agent 的整体架构。

更有意思的是，`interrupt()` 的返回值可以是任意 JSON 可序列化的值，不只是"批准/拒绝"。审批人可以返回一个修改过的邮件草稿，Agent 拿到这个草稿继续发送；也可以返回一段说明，Agent 根据说明重新生成内容。这把 HITL 从一个"门闸"变成了一个"协作节点"。

**可观测性：你不知道 Agent 在生产里会做什么，直到它真的做了**

文章有一句话让我后背一凉——"You don't know what an agent will do in production until you run it."

传统应用，你能从代码里推断出行为。Agent 不行。Agent 的执行路径取决于模型在运行时的选择：调哪个工具，怎么解读工具结果，什么时候停止。同样的 prompt，不同的时间跑，可能走出完全不同的路径。

当出了问题，"重读一遍代码"是没有用的。你需要的是 trace——完整的执行树，每一步模型看到了什么，输出了什么，调用了什么工具，工具返回了什么，然后模型又做了什么。

我一直在课程里强调一个判断：到了 Agent 时代，不做评测就没法玩了。你不知道如何评价你的产品，就不知道如何解决问题，因为你没法量化，所以也不知道往哪个方向优化。这个判断在 Runtime 层面同样适用：没有可观测性，你的 Agent 就是一个黑盒，出了问题靠猜。

LangChain 在可观测性上做的设计有几个让我注意的地方：

trace 是自动的，你部署了 Agent，trace 就在跑，不需要手动埋点。这很重要，因为手动埋点意味着有漏埋的可能，而一旦有漏洞，某些问题就永远找不到根因。

在 trace 上面，他们还加了 Online Evals——自动对生产 trace 跑评测，用 LLM-as-judge 或自定义评分器，实时发现质量退化。这和我讲 Eval-Driven Development 的理念完全吻合：评测不只是开发阶段的事，它应该是持续跑在生产里的。LangChain 用这套 loop 把 Deep Agents 在 Terminal Bench 2.0 上提了 13.7 个点——而且只改了 Harness，没改模型。这足够说明问题。

还有一个我觉得很实用的功能叫 Time Travel（时间旅行）。因为每个 super-step 都写了检查点，你可以回到任意历史节点，修改当时的状态，让后续的执行从那个修改后的状态重新跑。这对 debug 来说是个革命性的工具：你不需要重跑整个 20 步的任务，你可以直接跳到第 5 步，改一个工具调用的参数，看看后面的执行会不会走得更好。

**代码沙箱与安全代理：让 Agent 真正能"干活"的那层隔离**

一个只能调用你预先定义的工具的 Agent，能做的事情是有限的。一个能运行任意代码的 Agent，才是真正通用的——它可以装依赖、跑测试、分析数据、生成文档、克隆仓库。这是"带函数调用的聊天机器人"和"真正能干活的 Agent"之间的本质区别。

但任意代码执行是有代价的：如果 Agent 跑了 `rm -rf /`，或者读取了环境变量里的 API key，后果不堪设想。所以沙箱是必须的——你需要一个隔离环境，让 Agent 在里面执行代码，而这个环境与你真正关心的一切完全隔离。

文章里有一个关于安全性的细节让我觉得特别值得重视：**沙箱保护的是主机，不是沙箱本身**。如果攻击者能控制 Agent 的输入（通过提示词注入、恶意邮件内容、被污染的工具返回值），他可以让 Agent 在沙箱里执行任意命令。沙箱拦住了攻击者对你主机的访问，但沙箱内部放的任何东西——包括你直接放进去的 credentials——都可以被攻陷。

这就是他们设计"Auth Proxy"（认证代理）的原因：API key 不放在沙箱里，而是由一个 sidecar 进程拦截沙箱里的出站请求，在代理层注入正确的认证头。沙箱里的代码只需要调用 `api.openai.com`，不需要带任何 header，代理会自动注入。密钥永远不进沙箱，Agent 就无法泄露它不知道的东西。

这个设计思路——让 Agent 只拿到完成任务所需的最小信息集——是构建安全 Agent 的核心原则。我在讨论 Agent 架构时经常说：Agent 的设计、system prompt 的质量、环境的构建，这些东西才是决定 Agent 表现的关键变量，而不只是模型本身。Auth Proxy 是"环境构建"这个维度里的一个漂亮例子。

**定时任务与"睡眠时计算"：Agent 的主动工作模式**

前面说的所有能力，基本都是响应式的——用户发消息，Agent 响应。但文章最后讲到了一个让我觉得很有启发的模式：主动式 Agent，或者说"睡眠时计算"（Sleep-time compute）。

这个概念是说：Agent 不需要一直等着用户发消息。它可以在没有人触发的情况下，主动在后台运行有价值的任务。一个研究 Agent，每晚自动追踪你关注领域的新论文；一个会议准备 Agent，每天早上在你开始工作前，已经帮你整理好今天所有会议的背景资料；一个客服 triage Agent，每隔十五分钟扫描一批新进来的工单，按紧急程度排序，让人工客服走进来就能看到已经分类好的队列。

这些工作发生在"没人等"的时候，所以延迟不是问题，但质量和可靠性同样重要。LangChain 把 cron job 直接集成进 Agent Server，让定时触发的 run 享有和用户触发的 run 完全一样的可靠性保障：同样的持久化执行，同样的 trace，同样的认证和权限，同样的失败重试。

特别值得一提的是有状态 cron（Stateful cron）：你可以把定时任务绑定到一个固定的 thread，这样每次触发的 run 都能看到所有历史执行的上下文。一个每天跑的研究 Agent，可以知道它昨天找到了什么，前天关注了哪些趋势，然后在这个积累上继续构建。这才是真正的"AI 帮你持续关注"，而不是每天从头开始的无状态任务。

**我的思考：基础设施才是护城河，大多数人盖的是帐篷**

很多人认为 AI 产品的核心竞争力在于模型。模型好，产品就好；模型迭代了，产品就自然变好。

这个想法不完全错，但越来越不够用了。

我一直持有一个判断：当大家都在使用同样的底层模型时，产品之间的差距来自工程能力和产品理解，而不是谁先接入了哪个 API。现在这个判断在 Agent 层面有了一个更具体的形态：基础设施。

LangChain 这篇文章描述的那套 Runtime 能力——持久化执行、多层记忆、多租户隔离、人工介入、可观测性、沙箱代码执行、定时任务——这不是功能表，这是生产级 Agent 的必要条件。少一个，你的 Agent 在真实使用场景里就有一个可以被触发的故障点。

回头看 PC 时代到云计算时代的演进，会发现一个规律：每一次平台级的变革，都先有一批早期建设者搭地基，然后上层的应用才爆发。PC 时代，地基是操作系统和文件系统。互联网时代，地基是 TCP/IP 和 HTTP。云计算时代，地基是 EC2 和 S3。Agent 时代，地基是什么？

我现在的判断是：Agent 时代的地基，正是这篇文章描述的这层 Runtime。

这就是为什么我对 LangChain 在 deepagents 这个方向上的押注感到认同。他们没有试图做最聪明的模型，也没有试图做最漂亮的 Agent demo，而是在认真构建那层让 Agent 能够可靠运行的基础设施——而且选择把它做成开源的、模型无关的、协议开放的。这个策略选择，和 AWS 当年选择开放 API 而不是锁定客户，有着相似的逻辑。

当然，文章本身是 LangChain 对自己产品的描述，有一定的营销色彩。但它提出的那些技术问题——持久化执行的必要性、记忆分层的设计逻辑、HITL 作为业务刚需而非能力补丁——这些问题是真实存在的，不管你用什么框架都需要回答。

还有一个细节我觉得值得单独说：文章里那段关于"数据归属"的讨论。他们明确说记忆默认存在你自己的 PostgreSQL 里，Harness 是 MIT 许可的开源代码，Agent 暴露的协议是 MCP 和 A2A 这些开放标准。这不只是技术选择，这是一个关于"谁拥有这个 Agent"的哲学立场。如果你建了一个很有价值的 Agent，花了几个月积累了用户的偏好和行为数据，这些数据是属于你的，还是属于你选择的那个平台的？这个问题会在未来的 Agent 产品竞争里变得越来越重要。

有一件事我越来越确信：真正的 Agent 工程不是写几百行 Python 然后跑一个 demo。它是一套工程体系——你要考虑故障恢复，要考虑数据主权，要考虑可审计性，要考虑人与机器的协作边界。大多数团队现在搭的是帐篷，快，但经不起风雨。认真做 Runtime，才是真正在盖房子。

这场基础设施的竞争才刚刚开始。
