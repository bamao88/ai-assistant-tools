# 谷歌用117个测试把一个小文件逼出了99%的正确率——这件事让我重新思考知识到底长在哪里

你有没有想过，大模型"知识过时"这个问题，可能根本没有你想象的那么好解决？

大家都知道模型有训练截止日期，也都知道可以用 RAG、联网搜索、MCP 服务来补充新鲜信息。但有一个盲区大多数人没有注意到：模型连自己最新的 SDK 都不一定知道。你让它帮你写 Gemini API 的代码，它可能会自信满满地给你调用一个早就废弃的老版本接口，然后告诉你"这是正确的用法"。

这不是模型偷懒，而是它根本不知道自己不知道。

最近我读到 Google DeepMind 的两位工程师 Philipp Schmid 和 Mark McDonald 发表的一篇技术博文，讲的是他们如何用一个极度轻量的"agent skill"来填补这个知识鸿沟，并且用 117 个测试案例把这件事量化得清清楚楚。读完之后，我有点坐不住——因为这件事揭示的不只是技术方案，而是我们对"模型知道什么、不知道什么"的认知，可能一直都有一个系统性的偏差。

---

**大模型有一个它自己无法承认的盲区**

要理解这个问题，先要搞清楚大模型知识的本质。

训练集截止日期是一个大家都知道的限制，但有一个更微妙的地方经常被忽视：新事件的学习深度远不如旧事件。原因很简单——互联网对某件事的讨论、分析、解读，需要时间积累。一个三年前的技术框架，有大量教程、Stack Overflow 问答、实战博客；而一个六个月前才发布的新版 SDK，网上的高质量内容还寥寥无几，模型"学"进去的其实是浅层的、不完整的。

这就是为什么模型连自己的 API 都会搞错。Gemini 的 SDK 在持续迭代，新的模型名称、新的调用方式、新的最佳实践——这些变化的速度，比任何一次训练周期都快。模型在训练时学到的调用方式，到了真正被用户使用的时候，可能已经变成了"旧时代的写法"。

Schmid 和 McDonald 在博文里坦率地承认了这一点：谷歌的模型"在被训练时并不了解自己"，而软件工程领域的最佳实践又变化极快，每天都有新库发布。这两个因素叠加，就形成了一个知识鸿沟——模型不知道自己有多不知道。

这个场景我太熟悉了。很多人在用 AI 写代码的时候，最容易踩的坑就是模型给出的方案"能跑但已经过时"——它没有幻觉，没有逻辑错误，只是用了一个旧 API。这种错误最难发现，因为它看起来完全正常。

---

**一个 Markdown 文件，而不是 RAG 系统**

面对这个问题，解法有很多种：让模型实时联网搜索文档、搭一个专门的 MCP 服务提供 SDK 知识、做微调把新版本的用法训进权重里……

但谷歌团队选择了一个极度简单的方案：写一个结构化的 Markdown 文件，告诉 agent 这些事情——Gemini API 的高层能力是什么，现在有哪些模型和 SDK，基础示例代码长什么样，以及最重要的，去哪里找到权威的文档入口。

这就是所谓的"agent skill"。

它不是一个服务，不是一个工具调用，不是一套检索管道。它本质上是一份写给 agent 的说明书：你在给用户写 Gemini 相关代码时，先读我一遍，然后去官方文档确认最新的内容。

我认为这里最巧妙的设计，是它不试图把所有最新知识都塞进这个文件里。它只做一件事：指向文档的入口，让 agent 自己去检索真实的最新信息。这和 Agentic RAG 的思路高度一致——不是在系统里存储所有知识，而是让 AI 知道"不知道的时候去哪里找"。区别在于，传统 RAG 是检索存量知识，而 skill 指向的是源头文档，始终是最新的。

这个设计天才的地方在于，它把"知识新鲜度"的维护成本，从训练迁移到了维护一个轻量文档上。只要 SDK 更新了，你维护好文档，agent 就能通过 skill 指引获取新信息。

---

**117 个测试告诉你，推理能力才是决定因素**

说到这里，很多人可能会想：这有用吗？一个小小的文本文件，真的能让模型写出正确的新版代码？

谷歌的做法是用数据说话。

他们构建了一个包含 117 个提示词的评测集，覆盖 Python 和 TypeScript 的代码生成任务，包括构建 Agent 工作流、聊天机器人、文档处理、流式输出、以及多个 SDK 特定功能。判断标准很简单：生成的代码是否使用了正确的新版 SDK，而不是过时的旧版本。

结果出来之后，我反复看了好几遍。

在没有 skill 的情况下，Gemini 3.0 Pro 和 3.0 Flash 的通过率只有 6.8%。是的，6.8%。这意味着如果你直接让这些模型帮你写 Gemini API 代码，大约 93% 的情况下，代码会使用错误的旧版调用方式。Gemini 3.1 Pro 稍好一些，但也只有 28%。

加上 skill 之后，Gemini 3.x 系列的通过率提升到了接近 100%。不是 80%，不是 90%，是几乎满分。而 2.5 系列的老模型，虽然也有提升，但效果远不如 3.x 系列。

这个数据里藏着一个让我深思的结论：skill 本身不是魔法，它能不能发挥作用，取决于模型的推理能力有多强。

原因并不复杂。skill 文件里有一个关键指令：遇到不确定的信息，去文档里确认。这要求模型具备两种能力：知道自己什么时候"不确定"，以及会主动使用工具去检索文档。这两种能力都需要强大的推理支撑。老一代模型在这方面相对弱，给了 skill 也不一定会严格遵循；新模型推理能力更强，接到 skill 的指令之后，会真的按照要求去调用文档工具获取最新信息。

这和我一直以来的一个判断完全呼应：模型的推理能力，是 Agent 工程落地的决定性变量。你可以设计再好的工作流，写再精细的 prompt，但如果底层模型的推理能力不够，很多行为就是不可预测的。从 6.8% 到接近 100%，这个跨越不是靠 skill 一个文件实现的，而是靠新一代模型的推理能力配合 skill 一起实现的。

---

**Eval 体系：这件事本身就值得学**

我对这篇博文另一个印象深刻的地方，不是 skill 的结果，而是他们构建 eval 的方式。

117 个测试案例，分类覆盖多个场景，有明确的判断标准，在"有 skill"和"无 skill"两种条件下分别跑，结果清晰可量化。这不是"感觉上变好了"，这是用数据说清楚了到底好了多少、哪些场景好了、哪些场景还不行。

这套评测集的设计细节里有很多值得注意的地方。他们没有只测几个"典型案例"就宣布 skill 有效，而是系统性地覆盖了从入门到高级的多个任务类型。聊天机器人构建、文档处理、流式输出、SDK 特定功能……每一个类别背后代表的是真实用户在不同场景下的使用需求。这种分类设计本身就说明，他们对"什么叫真正有效"想得很清楚——不是在某一类任务上的局部成功，而是跨场景的普遍可靠性。

失败案例里有一类特别有意思：有些提示词明确要求使用 Gemini 2.0 系列模型。skill 没有覆盖这种情况——因为用户明确要求了旧版本，所以即使有 skill 指引，agent 也会"听从用户指令"用旧版本写代码，这在测试里被标记为失败。这个 edge case 让我想到一个更深的问题：当用户的显式要求和 skill 的最佳实践指引相冲突时，agent 应该遵循哪一个？这不是技术问题，而是产品设计问题。

我在构建 AI 产品时经常看到这样的困境：用户说的和他实际需要的往往有偏差。他说要 Gemini 2.0，但他其实要的是"能跑的代码"。skill 当前的设计没有解决这个歧义——它的默认策略是"用户说啥是啥"，而不是"用户要的是什么"。这也许是未来版本需要考虑的方向：当检测到用户的显式要求和最新最佳实践冲突时，是静默遵循、给出警告、还是主动澄清？

谷歌团队在博文里提到，他们知道 Vercel 的实践表明直接写进 AGENTS.md 的指令有时候比 skill 更有效——这是对自己方案局限性的坦诚承认。同时，skill 目前没有好的自动更新机制，如果用户长期不更新 skill 文件，随着时间推移，这个文件里的信息本身也会过时，反而可能成为一个错误的知识来源。一个解法是 skill 本身只包含"指引"而不包含"知识"——它永远只告诉 agent 去哪里找权威信息，而不是直接给出答案。谷歌现有的设计已经部分做到了这一点，但还不够彻底。

这种自我审视的方式，恰恰是 eval 驱动文化最核心的体现：先量化，再讨论，承认局限，然后继续迭代。这比那些只发布"我们成功了"的博文要诚实得多，也有价值得多。

**MCP、RAG、Skill：不是同一件事**

读到这里，可能有人会问：这和 MCP 协议有什么关系？它们不都是在给模型提供额外的知识吗？

有关系，但不完全一样。

MCP（Model Context Protocol）的核心是让任何第三方服务都能以统一规范向模型提供上下文和执行能力。它是一个协议标准，解决的是"如何接入"的问题。

Skill 更像是一个使用手册层面的东西——它不是数据管道，而是一份写给 agent 的行为指南：遇到 X 情况，你应该做 Y，同时去 Z 地方确认最新信息。它可以与 MCP 配合使用，但本质上是更上层的"行为规范"，而不是"数据通道"。

RAG 解决的是把存量知识塞进上下文的问题，skill 解决的是"让 agent 知道去哪里找权威知识"的问题。前者是在系统里建仓库，后者是给 agent 一张地图。

这种区别在实践中很重要。很多人构建 RAG 系统时，会花大量精力做文档切片、向量化、检索排序，试图把所有信息都纳入可检索的范围——但结果经常是切得越细知识越支离破碎，全局关系丢失。而 skill 的逻辑是：与其把所有知识都提前存储好，不如让 agent 在需要的时候直接去找原始文档。这对持续迭代的技术文档特别有效，因为原始文档本身就是最新的权威来源。

**写给自己的延伸思考：知识的锚点**

这篇博文让我想了很久的一个问题是：知识到底应该"长在哪里"？

在没有大模型之前，知识长在人脑里、书里、文档系统里。大模型出现之后，大家开始尝试把知识"训进"权重——但训练截止日期决定了它的新鲜度有一个硬上限，而且最新的事物学习深度永远比不上已经被互联网充分讨论过的旧事物。

RAG 把知识放进向量数据库，用相似度检索来补充上下文——它解决了新鲜度问题，但分块存储会破坏知识的全局结构，而且你存进去的知识也有自己的时效性。

MCP 把知识的提供标准化，让第三方服务可以动态向模型注入上下文——这是个生态层面的解法，但维护各种 MCP 服务本身也是成本。

而 skill 这个方案说：把知识锚定在原始文档，让 agent 动态获取。这个思路的优雅之处在于，它把"知识权威性"和"知识新鲜度"这两个需求合并了——原始文档既是权威的，也是最新的。

但这里有一个前提：agent 必须有足够强的推理能力，才能真正执行"遇到不确定就去文档里找"这条指令。谷歌的实验数据已经证明，推理能力弱的老模型，即使给了 skill，也不会认真执行。这让我想到一个更大的命题：agent 工程的本质，是在模型能力边界上做设计。你不是在替模型思考，而是在帮它找到能发挥的场景，然后给它正确的行为指引。

这和 Copilot 到 Agent 的演进轨迹是一致的。早期 Copilot 阶段，我们需要给模型非常明确的指令，因为它无法自主判断"什么时候该做什么"。随着推理能力提升，模型逐渐能够理解 skill 里写的意图并主动执行——它遇到不确定时会主动去找文档，而不需要你在每一个 prompt 里都写清楚"请先查文档"。这是一个很重要的进化节点：不是模型变得更"听话"了，而是模型开始真正"理解意图"了。

从这个角度看，谷歌这个实验的真正价值，不是"skill 有用"这个结论，而是它提供了一个清晰的数据基准，告诉我们在推理能力这个维度上，新一代模型究竟跨越了什么。那个从 6.8% 到接近 100% 的跳跃，是模型在自主性上真实可见的代际进化。

**我的思考：Eval 才是最容易被忽视的核武器**

这篇博文给我最深的启发，其实不是 skill 本身，而是他们验证 skill 的方式。

117 个测试，明确的成功标准，跨版本模型的对比，失败案例的具体分析——这套 eval 体系本身就是一个值得深学的范本。做过 AI 产品的人都知道一件事：效果好不好，凭感觉说不清楚，必须用数据说话。但绝大多数团队在这件事上的投入是严重不足的。大家愿意花时间调 prompt，花时间选模型，但不愿意花时间建一套严格的评测体系。

结果就是，你以为你优化了，实际上你只是换了一种方式产生不同的错误。没有 eval，你永远不知道那个新版 prompt 是真的变好了，还是只是在你手测的那几个 case 上碰巧表现更好。

谷歌这个实验之所以有说服力，正是因为他们把 skill 的价值量化到了一个让人无法质疑的程度。从 6.8% 到接近 100%，这不是一个需要主观判断的数字，它就在那里，白纸黑字。这种思维方式，其实和硅谷顶尖 AI 团队反复强调的"evaluation is all you need"是同一件事——不是上线之前跑一遍质量检查，而是把 eval 作为整个开发过程的驱动力：先定义成功是什么，再设计方案，再用数据验证，再根据失败案例迭代。

这个顺序很多团队都搞反了。先有方案，再凭感觉判断好不好，觉得差不多了就上线，出了问题再回头找原因——这套流程在 AI 产品上代价极高，因为 AI 系统的失败模式往往不直观，你不亲眼看数据就真的不知道它在哪里出的问题。

在 AI 领域有一个反直觉的现象：任何两个产品在功能上往往会逐渐趋同，但在效果上的差距会持续存在。差距的根源不是功能有没有，而是团队有没有能力持续量化自己产品的效果、识别失败模式、快速迭代。有些团队做了很多事，实际上原地踏步；有些团队只做了几件事，但每件事都有清晰的 before/after 数据，每次改动都真实有效。

skill 这个轻量方案之所以值得推广，不仅仅因为它简单，更因为它背后有一套严肃的 eval 体系在支撑——这才是它可信的原因。如果谷歌只是发了一篇博文说"我们做了个 skill，感觉效果不错"，我会礼貌性地翻过去。但他们拿出了 117 个测试、具体数字、失败分析，这就完全是另一回事了。

把视角拉开来看：谷歌这个实验代表的是 AI 工具链正在走向一种新的成熟——不是"模型越来越强就完事了"，而是围绕模型能力边界，系统性地构建辅助机制（skill、eval、MCP、AGENTS.md……），让 agent 在真实工程场景里的表现真正可靠、可测量、可改进。

这和整个 AI Engineering 从 1.0 走向 2.0 的轨迹是一致的。早期 AI Engineering 1.0 的玩法是：找到一个大模型，写个好一点的 prompt，调出来差不多的结果，上线。2.0 的玩法是：eval 先行，围绕失败案例迭代，把每一个工程层面的决策——包括 skill 用还是不用、用哪个版本的模型、什么时候去文档检索——都变成可量化、可验证的工程决策。

知识鸿沟这个问题在 AI 时代会持续存在。模型的训练跟不上技术的迭代，这是结构性的，不会因为模型变强就消失——模型变强只是让知识鸿沟的解法变得更可行。但解法本身不一定要复杂。一个写得好的 skill 文件，配上强推理能力的模型，加上一套能量化效果的 eval 体系，可以走得很远。

这场关于知识放在哪里、怎么保鲜、如何量化效果的探索，才刚刚开始。
