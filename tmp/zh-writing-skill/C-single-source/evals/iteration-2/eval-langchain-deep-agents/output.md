# 你的 Agent 上线了，然后呢？——LangChain 这篇文章让我想通了一件事

你有没有注意到，绝大多数 Agent 教程在讲完"怎么用 LangGraph 搭一个 Agent"之后就戛然而止了？

好像 Agent 能跑起来、能调用工具、能输出结果，事情就算完了。但如果你真的想把它用在生产环境里——不是给自己用，是给几千个用户用——你会发现那才是问题真正开始的地方。

崩了怎么办？用户在等结果，worker 进程挂了，整个任务从头来过？用户 A 的记忆跑进了用户 B 的对话？发了一封不该发的邮件，代理已经按下发送键了，没有任何审批机制？这些问题，都不是在 Prompt 里加几句话能解决的。

最近读到 LangChain 发的一篇技术长文，标题叫《The Runtime Behind Production Deep Agents》。这篇文章系统地讲了 Agent 从实验室跑起来、到真正扛住生产环境，中间那段几乎从没被人认真说清楚过的基础设施。读完之后我想通了一件事：**Agent 工程的核心挑战，不是让 Agent 更聪明，而是让它更可靠地运行在一个混乱的现实世界里。**

---

**Agent 的"跑一次"和"跑一千次"是两件完全不同的事**

我在带训练营的时候经常问一个问题：你的 Agent 在 Cursor 里跑通了，和它被一千个用户同时调用，这两件事有多大的区别？

大多数人第一反应是"应该差不多吧，逻辑是一样的"。

这个认知是错的。区别不在于逻辑，在于基础设施。

LangChain 这篇文章用了一个非常清晰的框架来区分两件事：**harness**（驾束）和 **runtime**（运行时）。Harness 是你围绕模型搭建的那些东西——Prompt 怎么写、工具怎么接、技能怎么组织——这是你控制 Agent 行为的地方。Runtime 是在它下面跑的那层东西：持久化执行、记忆、多租户隔离、可观测性……是那些让 Agent 在生产环境里不崩的东西。

大多数人把所有精力放在 harness 上，觉得 runtime 是"有就行，没有也凑合"。而真正把 Agent 推到生产的团队，都踩过坑之后意识到：runtime 才是决定 Agent 能不能落地的那层东西。

---

**持久化执行：Agent 的根基，不是可选项**

文章里有一段话让我印象很深。他们描述 Agent 的运行模型是一个 loop：给定 Prompt，模型推理、调用工具、观察结果、再次推理，直到任务完成。这个 loop 可能要跑几分钟甚至几十分钟。

问题来了：如果 worker 进程在第 15 分钟挂了，前 14 分钟的工作怎么办？

如果没有持久化执行机制，答案是：全没了。Agent 重启，从头再来，用户的等待变成了空等待。更糟糕的是，有些工具调用是有副作用的——发了一封邮件，创建了一条数据库记录，删除了一个文件。从头跑可能意味着这些动作被重复执行。

LangChain 的解法是把 Agent 的每一个"超级步骤"（super-step）都写入 checkpoint，存进 PostgreSQL。每个 checkpoint 用 `thread_id` 作为游标。如果 worker 挂掉，另一个 worker 接手，从最后一个 checkpoint 继续往下跑。Agent 自己感知不到中断，任务继续推进。

这个设计还解决了另一个场景：Agent 暂停等人工审批。如果用户要确认一笔转账，Agent 可能要等三分钟，也可能要等三天。在等待期间，不能一直占着一个 worker 进程——那不现实。持久化执行让 Agent 可以真正地"睡着"，把资源释放出来，等到人工回复之后，再从断点精确唤醒。

这让我想起一件事。我们在训练营里讨论过一个问题：为什么早期的 Agent 一遇到长任务就容易丢失自己的任务思路、不知道自己在干什么？很大程度上是因为缺乏这种逐步存档的机制。Agent 的"工作记忆"随着对话轮次的增加不断积累，但一旦进程挂掉或者 context 超出上限，它就失忆了。持久化执行从根本上改变了这个局面——**它让 Agent 的状态不再依赖进程的存活，而是存在数据库里。**

---

**记忆的两层结构：短期 vs 长期，不是同一个问题**

文章把 Agent 的记忆拆成两类，这个分类方式我觉得非常准确，也是很多团队在做记忆系统时容易混淆的地方。

短期记忆是单次对话里发生的一切：消息历史、工具调用记录、中间推理过程。它跟着 thread 走，对话结束就成了历史，靠 checkpoint 存着。这部分相对好处理，框架层面已经有比较成熟的方案。

长期记忆是跨对话的那些东西：这个用户喜欢什么格式的输出？上次他说的那个项目背景是什么？这个组织有哪些内部规范？这些信息不属于任何一条 thread，但应该在每次对话里都可以被调用到。

我在课上一直强调，Memory 是当前 Agent 最大的短板。那些顶尖的 Agent 产品，在工具调用和任务执行上已经接近甚至超过人类水平，但在理解用户偏好、记住跨会话的个性化信息这些事上，还差得远。Claude Code 用 CLAUDE.md 文件做记忆，本质是把上下文智能提炼成文档，手工性质很强。这是整个行业层面上的短板，不是某一家的问题。

LangChain 的解法是在运行时内置一个 Key-Value Store，按命名空间（比如 `(user_id, "memories")`）组织，存在 PostgreSQL 里，支持语义搜索。Agent 在一次对话里写进去的东西，下次对话里可以直接调出来。这个方向是对的，**但更关键的问题是记忆的质量**——存什么、不存什么、用什么格式存、怎么保证跨时间的一致性，这些才是真正需要产品和工程配合来设计的。

**Human-in-the-Loop：不是万不得已的补丁，而是架构的一部分**

我注意到一个有趣的演进。早年大家讨论 Agent，总觉得"人工介入"是一种失败的信号——Agent 不够聪明，所以才需要人来帮它擦屁股。

但 LangChain 这篇文章的态度完全不一样。他们把 Human-in-the-Loop（HITL）作为正常的架构组件来设计，而不是应急方案。

文章里举了两个最典型的场景。

一是工具调用前的审批。Agent 起草了一封邮件，准备发出去。在发出之前，系统暂停，把草稿呈现给用户：你可以直接批准，可以修改后批准，也可以拒绝并附上具体的修改意见让 Agent 重新来。整个过程 Agent 不会超时，不会丢失状态，等用户回应的时候精确恢复。

二是 Agent 主动提问。当 Agent 遇到一个自己没法决策的岔路——比如找到了三个配置文件，不知道要改哪个——它可以主动暂停，向用户提问。用户的回答就成为 `interrupt()` 调用的返回值，Agent 继续往下跑。

这个设计和我一直说的从 Copilot 到 Agent 的演进思路非常吻合。当前阶段，让 AI 意识到自己不确定然后请用户介入，比让它强行猜测要好得多。能做选择题就不让用户做填空题——HITL 的本质是把"不确定性"显性化、可管理化，而不是消灭不确定性。

从技术实现角度，`interrupt()` 的灵活性让我觉得这个设计非常精妙。它是动态的，不是静态断点——可以放在代码任何地方，可以包在条件语句里，可以嵌在工具函数内部，这意味着审批逻辑可以跟着工具走，而不是分散管理。`Command(resume=...)` 接受任意 JSON 可序列化的值，所以用户可以返回编辑后的草稿、提供缺失的上下文，甚至注入来自下游系统的计算结果。这比简单的"批准/拒绝"要强大得多。

**Guardrails：写进 Prompt 的规矩，不如写进代码的执行**

文章里有一句话让我觉得说到了点子上：不是所有的生产约束都能用"好好运行 loop"来解决，有些东西必须在 loop 之外强制执行。

最典型的两个场景：

一是 PII 脱敏。客服 Agent 收到用户的消息，里面可能包含身份证号、电话、邮箱。你不希望这些信息进入模型，不希望它们出现在日志里，合规要求在记录之前必须脱敏。这件事必须在每次模型调用前发生，确定性地执行。

二是 API 调用次数上限。如果 Agent 可以调用某个付费的外部 API，一个混乱的模型可能在一次任务里调用五十次，把预算在早上跑完。这需要硬性上限，不能靠 Prompt 里的"记住不要调用太多次"。

解法是 middleware——在 Agent loop 的固定钩子位置（`before_model`、`wrap_tool_call`、`after_model`）插入策略代码，确定性地执行。这个机制的核心价值是：它不依赖模型去记住规则，它在架构层面强制约束。

这个思路和我一直讲的"AI 是非确定性的，但守护它的系统必须是确定性的"非常一致。你不能用一个概率性的东西来执行合规要求，你必须用代码。把关键约束写进 Prompt 只是"希望模型记得"，把它写进 middleware 才是"强制它执行"——这是两种完全不同的可靠性等级。

**可观测性和时间旅行：Debug Agent 的方式和 Debug 传统软件完全不同**

文章里有一段话我觉得说得非常准确：你不知道你的 Agent 在生产里会做什么，直到它真的跑起来。

传统软件，你看代码就能推断出行为——相同的输入产生相同的输出，流水线是确定的。Agent 不是这样，它的执行路径取决于模型在 runtime 的选择：调哪个工具、怎么解读结果、什么时候放弃换个方向。这种不确定性让 debug 的方式必须完全不同。

如果没有 tracing，当用户说"Agent 一直在重复问同一个问题"，你只能从用户的描述去猜。有了完整的 trace，你能看到那次对话的完整执行树：用户的输入、模型的推理、工具调用的参数和返回值、下一轮的生成，以及它在哪里开始循环。

但我觉得更有意思的是时间旅行（Time Travel）这个功能。Agent 在第 5 步做了一个错误决策，导致后面 15 步全跑偏了。你想知道如果第 5 步做了另一个选择会发生什么，但又不想整个任务重新跑一遍。时间旅行的解法是：从 checkpoint 历史里找到第 5 步的状态快照，修改它，然后从那里重新往下跑。修改后的路径形成一个新的分支，原来的历史完整保留。

这个功能对 Agent 工程师的价值，相当于传统软件里的断点调试。你可以反复在同一个决策节点尝试不同的选择，观察路径的分叉，快速找到问题根因。

**沙箱里的 Agent：为什么隔离是刚需，不是锦上添花**

这一块是整篇文章里技术密度最高的部分，也是最容易被忽略的。

能运行任意代码的 Agent，和只能调用预先接好的工具的 Agent，能力差距是指数级的。前者可以安装依赖、克隆代码仓库、跑测试、分析数据、生成文档——它是真正意义上的"能做事"。后者只能做你提前想到的事。

但任意代码执行需要隔离。如果 Agent 在你的宿主机上跑 `rm -rf /`，这一天就报废了。如果它能读到 `env` 里的 API key，你的安全就完了。

LangChain 的方案是 sandbox backend——一个可插拔的隔离执行环境（支持 Daytona、Modal、Runloop、LangSmith Sandboxes）。当你配置了 sandbox，Agent 自动获得一个 `execute` 工具；没配置，这个工具根本不出现。隔离边界非常清晰。

但文章里有一段话我觉得特别值得标出来，因为很多人会漏掉这个安全细节：**沙箱保护的是你的宿主机，不是沙箱内部本身**。如果攻击者通过 Prompt 注入（比如 Agent 爬取了一个恶意网页）控制了 Agent 的输入，Agent 可以在沙箱内部执行任意命令。沙箱把攻击者挡在你的机器外面，但沙箱内部放的任何凭证都会暴露。所以他们设计了 auth proxy——作为 sidecar 运行，拦截沙箱内所有出站请求，自动注入认证信息。沙箱里的代码调用 `api.openai.com` 完全不带 header，proxy 在外面加上 `Authorization`，密钥从头到尾不进沙箱。这个设计思路我觉得非常值得学习。

**开放 vs 封闭：这个选择比你想的重要**

文章最后专门有一节讲"开放"，这在一篇技术文章里是不太常见的。

他们提到一个现实：现在有一种趋势，Agent 基础设施的托管方案越来越多，但很多都带来了隐性的锁定——只能用某个模型、harness 逻辑是黑箱、记忆数据格式不透明。实际结果是团队越用越看不懂自己的 Agent 在做什么，想换个方向也改不了。

LangChain 的 `deepagents deploy` 明确走了相反的路：harness 是 MIT 协议开源的，Agent 通过 MCP 和 A2A 这两个开放协议对外暴露，记忆存在你自己的 PostgreSQL 实例里。这些选择意味着你对自己的 Agent 有完整的可见性，也有完整的控制权。

这和我一直强调的"全控权"原则非常吻合。不要把 Prompt 工程外包给框架，不要把上下文窗口交给别人管，你必须知道你的 Agent 到底看到了什么。这不只是技术选择，这是对 Agent 行为的根本控制权。一个你看不懂的 Agent，是你没办法真正迭代和优化的。

**我的思考：Agent 工程进入了第二阶段**

读完这篇文章，我脑子里浮现出一条非常清晰的发展轨迹。

2023 年，大家的问题是"Agent 能不能做到这件事"。答案基本上是"能，但很脆"。那个阶段最核心的工作是证明 Agent 有能力跨步骤推理、调用工具、完成一个相对复杂的任务。Deep Research 是那个阶段的代表——它第一次让大家看到 Agent 可以真正自主探索、解决人没法提前规划路径的任务。

2025-2026 年，问题变成了"Agent 能不能稳定地、持续地、规模化地做到这件事"。这是一个完全不同的问题。前者是智能问题，后者是工程问题。

LangChain 这篇文章讲的，就是那个工程问题的答案。持久化执行解决的是"不崩"；记忆分层解决的是"有上下文"；HITL 解决的是"不失控"；middleware 解决的是"有约束"；sandbox 解决的是"能扩展但安全"；可观测性解决的是"出了问题能查"。

这条路有点像云计算的演进。早年大家关注的问题是"云能不能跑我的应用"，后来才转到"怎么让这个应用在云上跑得好、跑得可靠、跑得合规"。Agent 工程现在正在经历同样的转变——从"能跑"到"怎么把它跑好"。

但有一点让我一直在思考：这篇文章里描述的基础设施，是真正解决了确定性 vs 非确定性的核心矛盾，还是在一个本质不确定的系统外面包了一层确定性的外壳？

我倾向于认为，两者都有，而且这很重要。Middleware 是确定性的——它强制执行规则，不管模型想不想遵守。Checkpoint 是确定性的——它可靠地记录状态。但 Agent 的核心决策仍然是概率性的。这意味着系统的整体可靠性，来自于用确定性的基础设施约束住一个不确定的推理引擎。这是正确的设计思路。

对正在做 Agent 产品的人来说，这篇文章给了我一个很直接的"清单"：如果你的 Agent 还跑在一个没有持久化执行、没有分层记忆、没有 HITL 机制、没有完整 tracing 的环境里，你还没有做好上生产的准备。不是说代码写得不对，是系统架构里有几个关键的地基还没打。

Agent 时代是真的来了。但"来了"不等于"随便搭个 Agent 就能用"。真正让 Agent 产生价值的那段路，在上线之后才刚刚开始。
