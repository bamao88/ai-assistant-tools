# 你的 AI Coding Agent 在用过时的 SDK 写代码，成功率只有 6.8%

我最近看到一个数字，让我坐立不安了好一阵子。

Google DeepMind 的工程师做了一组实验：让自家最新的 Gemini 系列模型，去写调用 Gemini API 的代码。结果怎么样？Gemini 3.0 Pro 的成功率是 6.8%，Gemini 3.0 Flash 是 6.8%，就连 3.1 Pro——他们当时最强的模型——也只有 28.2%。

让我重复一遍：一个顶级 AI 模型，用自家公司的 API 写代码，成功率不到三成。

这不是什么抹黑竞争对手的故事，而是 Google 自己发出来的文章，发布在他们的官方开发者博客上。作者是两位 Developer Relations Engineer，Philipp Schmid 和 Mark McDonald。他们在文章里坦率地承认：我们发现了一个模型的严重盲区，然后我们用了一个很轻量的方法解决了它。

这个方法叫 **Agent Skill**。加上这个 Skill 之后，gemini-3.1-pro-preview 的成功率从 28.2% 跳到了 96.6%。

效果惊人，但背后的道理一点都不复杂。只是这件事，打开了我对 AI Coding 领域一个长期没想透的问题。

---

**大模型为什么不认识自己的 API**

这个问题问出来可能有点奇怪：模型不是被训练出来的吗？训练数据里肯定有 Gemini API 的文档吧？

有，但问题在于训练截止日期，以及「学到」和「学深」的区别。

我在课上经常讲一个观点：训练集学到的知识，是真正融会贯通的；RAG 外挂给的，是现学现用的浅层指示。但有一点更关键——训练截止日期决定了模型的知识边界，而且新事件在训练集里的学习深度远不如旧事件。

为什么？因为互联网对新事件的讨论量还很少。一个 20 年前的技术决策，有无数篇分析文章、StackOverflow 帖子、GitHub issue、技术博客；但一个三个月前刚发布的 SDK 版本，可能只有官方文档和几篇 release note。模型吃到的数据量不对称，学习深度自然也不对称。

所以大模型会拿 6 个月前的旧 SDK 来写代码，完全不知道新版本长什么样。Google 的博文里提到一种典型失败场景：用 gemini-2.0-flash 这个旧模型来写代码——有的 prompt 明确要求用 2.0 版本，但新的 SDK 已经不支持这种写法了，模型就卡住了。

这不是模型笨，这是信息时效性的结构性问题。训练完成的那一刻，模型就开始「老化」了。

---

**他们建的东西，以及为什么这么轻**

Google DeepMind 的做法，说起来很朴素。

他们造了一个叫 `gemini-api-dev` 的 Skill。这个 Skill 里包含四件事：解释 Gemini API 的高层级功能集；描述当前可用的模型和各语言的 SDK；给出每个 SDK 的基础示例代码；最重要的是——列出文档的入口链接，引导 Agent 去找「真正的信源」。

最后这一点我觉得设计非常巧妙。Skill 本身不试图把所有知识都装进去，而是告诉 Agent：「去这里找最新的答案。」这是一种知识工程上的自谦——承认 Skill 文件本身也会过时，但如果能指向一个持续更新的信源，就能在一定程度上绕开这个问题。

实现上，他们在评测 harness 里给模型两个工具：`activate_skill` 和 `fetch_url`。前者激活 Skill，后者让模型去抓取文档。这就是全部了。没有 fine-tuning，没有 RAG pipeline，没有向量数据库，就是一个 System Prompt 加两个工具。

安装方式也很简单：

```bash
# 用 Vercel skills 安装
npx skills add google-gemini/gemini-skills --skill gemini-api-dev --global
```

然后他们用 117 个 prompt 做了系统测试，覆盖 agentic coding 任务、chatbot 构建、文档处理、流式内容、各种 SDK 特性。判断标准很明确：如果生成的代码用了旧 SDK，就算失败。

---

**最有意思的发现：推理能力是关键变量**

文章里有一个结论，让我深思。

他们测试了多代模型——Gemini 2.5 系列和 Gemini 3 系列，加上有 Skill 和没有 Skill 的对比。结论是：旧的 2.5 系列模型，加了 Skill 也只有有限提升；但新的 3.x 系列，加了 Skill 之后效果是爆发式的。

gemini-3.1-pro-preview：从 28.2% → 96.6%
gemini-3.0 Pro：从 6.8% → 接近同等量级的大幅提升

这意味着什么？Skill 本身只是提供了信息的入口，但能不能用好这个入口，取决于模型自己的推理能力。如果模型不够聪明，它可能根本意识不到该去调用 Skill，或者拿到文档之后不知道怎么用。

这和我一直强调的一个判断高度吻合：Agent 的自控，本质上依赖模型本身的智能程度。你能控制 Agent 的手段主要是 prompt 和工具，但这些工具能发挥多大作用，取决于模型背后的推理能力和对常识的理解。给一个弱模型再好的 Skill，也没用；给一个强模型一个方向提示，它会自己找到路。

这个发现在实际工程里的含义：如果你在做 AI Coding 工具，换最新、最强的底层模型，收益可能远超你精心设计的 prompt 工程。这不是说 prompt 不重要，而是说选模型这件事，在 AI 时代永远要优先选新的。

---

**从 28% 到 96%，这个数字说明了什么**

我在带训练营的过程中，反复强调一件事：AI 产品不能凭感觉，必须有评测说话。没有 eval 的 AI 产品就是在盲人摸象。

Google 这篇文章之所以让我觉得值得认真对待，不是因为他们解决了什么神奇的技术问题——他们的解法其实很普通——而是因为他们的测试方法。

117 个 prompt，有分类，有标准（用旧 SDK = 失败），有对照组（有 Skill vs. 无 Skill），有多模型横向对比，有分域分析（agentic coding、chatbot、文档处理……）。这套测试框架，才是这篇文章真正的含金量所在。

如果他们没有这个评测体系，他们根本不会知道问题在哪——不会知道失败率有多高，不会知道哪种任务最容易出错，不会知道 Skill 对新旧模型的效果差异。也就没有这篇博客，没有这个 Skill 的存在。

eval 先于解法，这个顺序很重要。我见过太多团队，拍脑袋设计解法，然后直接上线，靠用户反馈来发现问题。这在 AI 时代的代价特别大，因为 AI 的失败模式非常隐蔽——它会自信地给出一个看起来合理但其实错误的答案，用户很难分辨。

---

**Skill 的边界：他们自己也承认不完美**

文章里有一段让我很欣赏的诚实表达。

Google 提到，他们知道 Vercel 发布过研究，表明直接通过 `AGENTS.md` 注入指令，效果比 Skill 更好。他们在探索用 MCP 直接对接文档，作为 Skill 的替代方案。

另一个问题是更新机制。Skill 文件安装进用户的工作目录之后，如果 API 又更新了，Skill 也要更新，但用户不一定会主动去更新。时间长了，Skill 里的信息也会过时，甚至可能比没有 Skill 更有害——因为它会覆盖模型的其他判断，用错误的「新知识」干扰推理。

这个问题我也没有完美答案。但我的直觉是：能动态拉取信息的方案（比如 MCP 直连文档，或者在 Skill 里嵌入 fetch 逻辑），比静态文本注入更有长期价值。把文档地址给模型，让它自己去拿，比把文档内容预先灌给它更灵活。

不过他们愿意把这些不完美写进文章，我觉得是一种成熟的工程文化的体现。不炫耀，坦承局限，继续迭代。

**Skill、MCP、AGENTS.md，到底用哪个**

读完这篇文章，我忍不住在脑子里梳理了一遍目前这几种「给 Agent 补充知识」的主流路径：

**静态注入**：把信息写死在 System Prompt 或 AGENTS.md 里。简单直接，但信息会过时，Context 占用大。

**Skill**：把知识打包成结构化文件，按需激活。轻量，但更新机制弱，有时间滞后的问题。

**MCP（Model Context Protocol）**：通过标准化协议，让 Agent 实时访问外部服务或文档。更新及时，但需要服务端支持，有一定接入成本。

**RAG**：构建向量知识库，检索时动态补充上下文。信息最灵活，但需要维护知识库，且检索效果依赖 embedding 质量。

我认为这四种路径不是互斥的，而是一个能力谱系。从静态到动态，从轻量到重型，场景不同，选择不同。对于一个 SDK 文档这样更新频繁、结构清晰的知识，MCP 接文档是最优解；对于更结构化的领域知识，RAG 更合适；对于快速验证阶段，Skill 和 AGENTS.md 的成本最低。

Google 这篇文章做的事，相当于把这个谱系的一个端点验证了一遍。他们告诉你：Skill 是可行的，而且收益巨大；但他们也诚实地说，这不是终点。

---

**我的思考：Agent 的知识边界，是一个需要持续运营的工程问题**

读完这篇文章，我最想说的一件事是：AI Agent 的能力上限，不只是模型本身的能力，还有你给它的信息质量和新鲜度。

我们习惯把模型看作一个静止的系统——训练完了，能力就定了。但实际上，一个工程上优良的 Agent，是一个「模型 + 动态知识注入 + 评测闭环」组成的动态系统。你可以通过持续更新信息来源，让一个固定的模型不断发挥出更好的效果。

这让我想到 PC 时代刚过渡到云计算时代的那段时间。很多人把软件看作一次性部署的产品，但云计算改变了这个范式——软件变成了持续运营的服务，更新、修复、调整是常态。AI Agent 现在面临类似的范式转变：它不是一个你部署完就坐等结果的系统，而是一个需要持续维护知识、持续评测效果、持续迭代 prompt 和工具的活的系统。

从 6.8% 到 96.6%，这个数字如此戏剧性，背后是两件事同时发生：用了更强的模型，以及给模型注入了更准确的当前知识。这两件事缺一不可。只有强模型，没有新知识，成功率 28%；只有新知识，没有强模型，也很难到 96%。

工程上的启发是什么？给 Agent 搭知识通道，和选模型一样重要。你不能只关注"我用了什么模型"，你还要关注"我在哪个环节让模型知道了什么，这些信息有多新鲜，准确率多高"。这是 AI 工程里一个长期被低估的问题。

另一个让我有点坐不住的结论是：eval 不是一次性的动作。Google 能发现这个 6.8% 的问题，能测出 96.6% 的效果，靠的是他们建了一套针对这个具体场景的评测体系。如果他们只是靠感觉觉得「加个 Skill 应该有用」，然后上线，他们不会知道到底有没有效果，更不会知道效果差异有多大。

eval 先于优化，是 AI 时代的第一工程原则。这场从 6.8% 到 96.6% 的跳跃，正是用数据说话的力量。
