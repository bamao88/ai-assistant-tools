# 把 Agent 跑进生产环境，你缺的不是代码，是这套基础设施

你有没有想过，搭一个 Agent 原型和把它跑进生产环境，其实是两件完全不同的事？

大多数人踩过这个坑：在本地跑得好好的，逻辑对、工具调通、模型回答也合理，一部署到真实用户场景就开始翻车。要么长任务中途崩了、状态丢了；要么多用户一上来数据互串；要么 Agent 在某个工具调用上走偏了，你根本看不见它在干什么。

这不是 Prompt 的问题，也不是模型的问题。这是基础设施的问题。

LangChain 最近发布了一篇深度技术文章，系统讲清楚了生产级 Agent 需要什么样的运行时基础设施——从持久化执行、记忆管理，到人类监督、可观测性，再到代码沙箱和定时任务。读完之后我意识到，这篇文章其实是在告诉行业：Agent 工程正在进入 2.0 阶段，光有 harness（模型外壳）不够，你还需要一套完整的 runtime（运行底盘）。

---

**Harness 和 Runtime：一个容易被忽略的根本区分**

文章一开篇就给出了一个区分，简洁但让我深思：

要构建好的 Agent，你需要好的 harness——围绕模型搭建的那套东西，包括 Prompt、工具、技能、一切支撑模型做决策的资产。要把 Agent 部署好，你需要好的 runtime——harness 下面那一层，持久化执行、记忆、多租户、可观测性，让 Agent 在生产环境里真正跑得起来、跑得稳。

这个区分让我一下子想清楚了我见过的很多团队卡在哪里。他们花了大量时间打磨 harness，Prompt 调得非常细、工具链也搭好了，但一到部署就发现：没有检查点机制，长任务崩了就从头来；没有记忆分层，用户换个线程 Agent 就什么都不记得；没有流式输出，用户等了三十秒完全不知道 Agent 有没有在工作。

这些不是 harness 能解决的问题，它们属于 runtime 层。

我在训练营里一直强调 AI 开发和传统软件开发有一个本质区别：传统软件是确定性的，你知道它会怎么跑；AI Agent 是非确定性的，你只有在它跑起来之后才知道它真的在做什么。这个非确定性，加上 Agent 任务本身的时间跨度和复杂度，就让 runtime 基础设施变得比传统 Web 服务要难得多。

---

**持久化执行：所有问题的根**

文章把持久化执行称为"一切其他能力的地基"，我完全同意这个判断。

Agent 的工作方式是一个 for loop：给定任务，模型推理、调用工具、观察结果、重复，直到它认为任务完成。这个循环可能跑几分钟，可能跑几个小时，可能在等人类审批时挂起三天。

传统 Web 请求只跑几百毫秒，崩了重来成本很低。Agent 任务不是这样——一个花了二十分钟爬数据、分析、综合结论的研究 Agent，如果工作进程在第十八分钟崩掉，你绝对不想让它从第一步重跑。那些 token 已经花了，那些工具调用已经执行了，那些中间状态是有价值的。

LangChain 的解法是把每个"超级步骤"（graph 执行的最小可恢复单元）都写进 PostgreSQL 里，用 thread_id 作为持久游标。进程崩了，新工作进程从最新检查点接着跑；Agent 在等人类输入，进程释放资源去干别的，等审批回来再从断点恢复。失败的节点有可配置的重试策略——退避时间、最大次数、哪些异常触发重试——都可以按节点精细控制。

这让我想起一个在深度调研里发现的有意思的现象：之前行业公认比较靠谱的 Agent 应用场景其实就三种——代码助手、客服和 Deep Research。其中 Deep Research 最靠谱，核心原因之一就是它的任务是有内在结构的，可以分步骤推进，每一步可以明确完成。而那些偏向于长流程、中途状态复杂、需要等人反馈的 Agent，以前要么做不好，要么稳定性极差——根源就在于缺乏持久化执行能力。

持久化执行打通之后，流式输出、人类监督、定时任务这些能力才有地方落脚。这不是可选的工程加分项，是 Agent 能不能真正大规模使用的前提。

**记忆分层：不只是"记住上下文"那么简单**

文章对记忆的描述让我觉得这个观点击中了要害：Agent 需要两种完全不同的记忆，把它们混在一起是一个常见错误。

短期记忆是单次对话内积累的东西——这一轮说了什么、调了哪些工具、中间产生了什么状态。它绑定在一个 thread_id 上，对话结束了就归零。这一点大家都知道。

长期记忆是跨对话留存的东西——用户偏好、项目规范、从历次交互中提炼出来的知识。这些东西不属于任何一个线程，它是用户级别或组织级别的资产，每次对话都应该可以读取，也应该持续写入。

Agent Server 用一个独立的 store（键值接口）来处理长期记忆，以 namespace 元组组织（比如 `(user_id, "memories")`），默认存在 PostgreSQL 里，支持向量检索——Agent 可以按语义而不是精确匹配来读取历史记忆。

这个设计和我一直在想的一个问题直接碰上了：记忆是 Agent 产品最大的护城河，也是当前最大的短板。我在课上反复讲过：Claude Code 在工具调用和执行任务上已经接近超人类表现，但在跨会话记忆、用户偏好积累这件事上，是明显最嫩的地方。不是说模型不够聪明——而是记忆基础设施根本没搭好。所有顶尖 Agent 产品在这个维度上都和人类智力有最大的差距。

LangChain 这套分层设计从工程角度给出了答案：短期用检查点，长期用独立 store，两者各司其职，而不是用一个巨大的 context window 把所有东西都塞进去。而且它还做了一个我认为非常关键的判断：这些记忆数据要存在用户自己的 PostgreSQL 里，可以直接通过 API 查询，可以迁移、可以分析，不锁定在任何一个黑箱里。

这个判断背后有一个更深的逻辑——Agent 跑了几个月积累下来的记忆，可能比 Agent 本身的代码还值钱。数据主权不能让给平台。

**人类监督：不是"人工审核"，是架构级设计**

文章里让我觉得设计巧妙的，是 interrupt/resume 机制的具体实现。

大家都知道 Human-in-the-Loop 是什么概念，但在 Agent 里真正实现起来，有一个很具体的工程难题：Agent 在等人类回复的时候，这个进程怎么处理？你不能让一个工作进程就这么挂在那里等——用户可能三秒钟回来，也可能三天后才回来。

LangChain 的解法非常干净：`interrupt()` 调用会触发运行时的检查点机制，把当前图的完整状态写进持久层，然后释放进程资源。等到 `Command(resume=...)` 到来——无论是三秒还是三天后——这个返回值成为 `interrupt()` 调用的返回值，执行从断点精确恢复。

两个场景文章都讲到了：一是工具调用前的审批（比如发邮件前让人确认），人类可以直接批准、修改内容再批准、或者附上理由拒绝让 Agent 重来；二是 Agent 遇到歧义主动提问（"我找到三个配置文件，你要改哪个？"），人类的回答直接成为 Agent 下一步的输入。

比这更有意思的细节是：`interrupt()` 不是静态断点，不是只能放在节点前后——它可以放在代码里任何地方，可以写在条件判断里，可以嵌进工具函数里，让审批逻辑跟着工具走，而不是硬编码在图的拓扑结构里。并行分支各自调用的 `interrupt()` 可以一起 surface 给人类，也可以逐个回复。

我认为这背后的工程哲学很重要：人类监督不应该是"先让 Agent 跑，出了问题人工介入"的补丁，而是从架构上就把 human oversight 设计成一等公民。这和我一直说的"AI 开发是迭代式开发，你必须对每个节点的状态有完全的控制权"是同一件事。

**可观测性：你不看见，你就不知道**

文章有一句话我觉得说得最准："You don't know what an agent will do in production until you run it."（你不知道 Agent 在生产环境里会做什么，直到它真的跑起来。）

这句话对做过传统软件的人来说有点反常识——你不是写了代码吗，代码不就是你让它干什么就干什么？Agent 不是这样。它的执行路径取决于模型在运行时的选择：调哪个工具、传什么参数、怎么理解结果、什么时候放弃重试。这些都不在代码里，在模型的推理里。

所以当用户反馈"Agent 一直在问同一个问题"，你没有可观测性就只能猜——是 Prompt 的问题？是某个工具的返回格式让模型困惑了？是记忆里写了什么错误的东西让它陷入循环？有了完整的 trace，你能看到完整的执行树：用户消息、模型推理、工具调用、工具返回、下一条消息、循环开始的那一步。

LangChain 在这里做了一个很有意思的闭环设计：trace 不只是用来 debug，它直接喂给优化循环。他们用这套循环在 Terminal Bench 2.0 上把 Deep Agents 提升了 13.7 个百分点——只改了 harness，没改模型，没改架构。这就是可观测性真正的价值：它让你看见哪里出了问题，然后你改一个地方，再跑评测，再看新的 trace，循环推进。

时间旅行（Time Travel）功能是可观测性的延伸，也是我觉得工程设计上最优雅的部分之一。因为每个超级步骤都写了检查点，任何一个历史时刻的状态都可以被恢复、修改、从那里重新跑出一个分支。你可以在第 5 步替换掉模型的错误决策，看后续 15 步会不会走回正轨——不用重跑整个任务，不用手动重建中间状态。这对调试复杂 Agent 行为极其有价值。

**沙箱代码执行：从"有工具调用"到"真的能干事"**

文章里有个对比我觉得一针见血：一个只能调用你预先连好的工具的 Agent，是受限的；一个能运行任意代码的 Agent，是通用的——它可以装依赖、克隆仓库、跑测试、做数据分析、生成文档、渲染图表。这是"有函数调用的聊天机器人"和"真的能干事的 Agent"之间的差距。

但任意代码执行需要隔离。如果 Agent 在你的宿主机上跑 `rm -rf /`，你的一天就毁了。如果它读了你的环境变量，你的 API key 就泄露了。

LangChain 的沙箱方案通过 `SandboxBackendProtocol` 接口对接多个沙箱提供商（Daytona、Modal、Runloop 以及自家的 LangSmith Sandboxes），只要配置了沙箱后端，Agent 就自动获得一个 execute 工具；没配，Agent 根本看不见这个工具。

他们还专门设计了一个 auth proxy（认证代理）来解决一个每个团队都会遇到的问题：Agent 需要调用有认证要求的外部 API，但把凭证放进沙箱里是安全风险。代理作为一个 sidecar 跑，拦截沙箱的出站请求，从工作区密钥里自动注入正确的 Authorization header——沙箱里的代码只需要调用 api.openai.com，什么 header 都不用加，代理在出去的路上加好了。凭证永远不进入沙箱，也就不会被提取。

这个安全警告文章说得很直白：沙箱保护的是你的宿主机，不是沙箱本身。如果攻击者通过 prompt injection（比如爬到一个恶意网页）控制了 Agent 的输入，Agent 被指示在沙箱里执行某些命令，这个命令还是会跑。沙箱只是把爆炸半径限制在了沙箱内部。这一点做 Agent 工程的人必须清楚。

**定时任务与多租户：生产级 Agent 的最后一公里**

文章还涉及了两个我认为容易被忽视但非常关键的能力。

多租户不只是"权限控制"。Agent Server 把多租户问题拆成三层：用户数据隔离（一个用户的线程和记忆另一个用户看不见）、Agent 代表用户行动（Agent 用用户自己的 OAuth token 去操作他们的日历、Slack、GitHub），以及团队操作权限（谁能部署 Agent、看 trace、改配置）。这三层分别有独立的机制，而不是用一套访问控制一把梭。这种分层设计在多用户产品里是必须的，但很多团队在早期根本没想这么清楚就开始写代码。

定时任务让 Agent 从"被动响应"变成"主动工作"。文章描述的几个场景我非常有感：夜间 research agent 跑完新论文摘要等你早上来看；日历 prep agent 在你醒来前把今天的会议 brief 都准备好；监控 agent 每十五分钟检查一次，有问题就 escalate。这些 Agent 的价值不在于实时交互，在于它们主动积累、持续产出，用户受益于 AI 在空闲时间完成的工作。而这些定时任务跑在同一套 runtime 里，同样有持久化执行、tracing 和认证保障——崩了会重试，出了问题有 trace 可查，不需要再搭一套独立的调度基础设施。

**我的思考：Agent 生产化，是这一年最容易踩的坑**

这篇文章让我越读越坐不住，倒不是因为它说了什么特别新的东西，而是因为它把我一直有的一个隐约的担忧说清楚了。

2026 年 Agent 真正大规模落地了，这是事实。推理模型的成熟、长上下文的普及、工具调用的稳定化，这三个条件在 2024 年底集中就位，Agent 的技术条件终于到位了。但技术条件和工程条件是两件事。

我在训练营里常说 AI 开发最核心的矛盾是确定性与非确定性：传统软件你想好了怎么实现就能做出来，AI Agent 是迭代式的，你在第一天根本不知道它最终跑起来会是什么样子。这个非确定性不是 bug，是 Agent 的本质。但正因为如此，生产化要解决的问题也比传统软件复杂得多——你没法只靠单元测试覆盖，没法只靠日志排查，你需要完整的 trace、需要检查点、需要能在任何中间状态 fork 出一条新路径的能力。

LangChain 这篇文章本质上是在说：Agent 基础设施有一套固定的需求清单，你可以自己从零搭，也可以用现成的，但这个清单你不能跳过——持久化执行、记忆分层、人类监督、可观测性、沙箱、多租户，缺一不可。这和 YC 提出的 Twelve Factor Agents 框架想表达的东西是同一个方向：对你的 Prompt、对你的上下文、对你的执行状态，你必须有完全的掌控权。把这些外包给黑箱，就是在盲飞。

还有一点让我觉得 LangChain 这次做了一个正确的价值判断：他们明确拒绝了 vendor lock-in 的诱惑。harness 是 MIT 开源的，agent 通过 MCP 和 A2A 这两个开放协议暴露，记忆数据存在你自己的 PostgreSQL 里。这不是技术决策，是产品哲学——Agent 跑了几个月积累的记忆和 trace 是你最有价值的资产，如果它锁在一个闭源平台的加密摘要里，你就永远依赖那个平台，也永远无法在平台外分析和使用这些数据。

Agent 工程正在从"能跑起来"迈向"能跑好"，这一步比第一步难得多，也重要得多。第一个阶段的赢家是最先把 Agent 跑通的人；第二个阶段的赢家是把生产化基础设施搭得最扎实的人。

这场变革才刚刚进入真正有意思的部分。
