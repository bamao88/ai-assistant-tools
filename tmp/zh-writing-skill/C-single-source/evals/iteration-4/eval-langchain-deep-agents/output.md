# 你的 Agent 跑通了，然后呢？

你有没有想过，"让 Agent 跑起来"和"让 Agent 在生产环境里稳定运行"，这之间的距离可能比从零到跑通还要远？

我见过太多人把一个 Agent demo 做得很漂亮——调好了工具调用、写好了 Prompt、测试了几十个 case——然后信心满满地部署上线，然后开始被各种问题淹没：进程崩了任务丢了、多用户之间数据串了、Agent 用了多少 token 完全不可见、用户在等 spinner 转圈没有任何反馈……

把 Agent 做出来，和把 Agent 做成一个可以放心交给用户跑的生产系统，是两件完全不同的事。

最近读到 LangChain 发的一篇技术文章，专门讲他们把 Deep Agents 推向生产环境的基础设施设计。读完之后我脑子里浮现出的第一个念头是：这其实是一份"Agent 工程债务清单"——那些你在 demo 阶段可以假装不存在的问题，在生产里会一个不落地还回来。我把这篇文章里最核心的几个工程决策拆出来，加上我自己在实战里踩过的坑，一起聊。

---

**"Harness"和"Runtime"：一个容易混淆的区分**

LangChain 的文章做了一个我觉得非常值得记下来的概念区分：Harness（线束）和 Runtime（运行时）。

Harness 是你围绕模型构建的那层东西——Prompt、工具定义、skill 配置、记忆管理策略。这一层是让你的 Agent "聪明"的部分，是让它在特定领域里能干活的部分。大多数教程和框架教你的，基本都是 Harness 层的事情。

Runtime 是 Harness 下面那层：持久化执行、多租户隔离、Human-in-the-loop 机制、可观测性、定时任务、沙箱环境。这一层是让你的 Agent "可靠"的部分。

这个区分之所以重要，是因为很多人在搭建 Agent 时，花了 90% 的精力在 Harness 上，然后发现上线之后 Runtime 的缺失让 Harness 完全没法发挥价值。就好像你给一辆赛车换了最好的引擎，但底盘是纸做的，路一颠就散架了。

我在带学员做 Agent 实战的时候，经常看到一个规律：Harness 问题会在测试阶段暴露，Runtime 问题只会在生产里暴露。这也是为什么很多团队的 Agent "测试时挺好，上线就出问题"。

---

**持久化执行：Agent 不能"死了就从头再来"**

这是文章里我认为最根本的一个工程挑战，也是做过 Agent 生产部署的人都会被逼着解决的问题。

一个 Web 请求通常在几百毫秒内完成。但一个真正做复杂任务的 Agent 可能要跑几分钟甚至几小时——它要循环调用工具、生成中间结果、等待外部 API 响应。在这个过程里，如果进程崩了、机器重启了、部署更新了，那之前所有的工作就都白费了。模型调用的 token、工具执行的结果、Agent 走到一半的推理链——全部清零。

LangChain 的解法是把每个执行步骤（他们叫"super-step"）的状态都写进 PostgreSQL，用 `thread_id` 作为游标。任何一步失败了，任务的 lease 释放，另一个 worker 从上一个 checkpoint 继续跑。整个过程对 Agent 本身是透明的，写 Agent 的人不需要自己管这套状态机。

更值得注意的是等待人工介入的场景：Agent 起草了一封邮件，需要等你确认发还是不发。你可能三十秒就回，也可能三天才看到。如果这期间还得占着一个 worker 进程，根本不可行。持久化执行让 Agent 可以真正"停下来"——释放资源，等到你发来确认信号，再从原位置继续。

这个设计背后有一个更大的哲学：Agent 的任务执行不是"一次性的函数调用"，而是"可以被暂停、恢复、重试、分叉的状态流"。一旦接受了这个设定，很多后续的能力——Human-in-the-loop、time travel debug、定时任务——都自然成立了，因为它们都依赖同一套 checkpoint 机制。

**两种记忆，一个经常被忽视**

这部分我读得格外仔细，因为 Memory 模块是我一直认为 Agent 最大短板所在的地方。

短期记忆和长期记忆，很多人在概念上都清楚，但真正实现起来的时候经常做错。

短期记忆好理解：一次对话里的消息历史、工具调用结果、Agent 的中间状态——这些都在同一个 `thread_id` 的 checkpoint 里，对话结束就"消失"了（对其他对话不可见）。同一个 thread 里，Agent 能看到所有历史。

长期记忆是真正难的那个：用户跨对话的偏好、项目的约定俗成、Agent 从每次任务里提炼出的经验——这些东西不属于任何单一的 thread，但每次新对话都需要能读到。如果只靠 checkpoint，这些信息是不存在的，因为 checkpoint 是 thread-scoped 的。

LangChain 的 Agent Server 用一个 key-value store 解决这个问题，namespace 可以按 user_id、assistant_id、organization 任意组合。支持语义搜索，也就是说 Agent 不需要精确匹配关键词就能找到相关记忆。存储默认是 PostgreSQL，如果自己部署，数据就在自己手里。

这一点我觉得非常重要：Memory 数据是 Agent 跑了几个月之后最有价值的东西，它是"Agent 从使用中变得更好"的物质基础。如果这份数据锁在某个闭源服务里，或者没有标准格式，你就失去了分析它、迁移它、在 Agent 之外利用它的能力。

我自己研究过 Claude Code 的记忆模块，它现在的实现是把记忆写进 Markdown 文件，简单直接，但也非常基础。OpenAI 的 Codex 做得更复杂一些，分成多个文档。本质上都是在用某种方式把上下文智能地压缩存储下来。这是整个 AI Agent 行业现在公认的最大短板——Memory 做不好，规划和反思能力就是空中楼阁。你没办法让 Agent 反思它都不记得的事情。

所以 LangChain 把长期记忆设计成一等公民，而不是事后加的 feature，这个判断我很认同。

**Human-in-the-loop：不是"让人兜底"，是设计一种协作模式**

很多人把 Human-in-the-loop 理解成"Agent 出错了让人来修"，这个理解有点窄。

LangChain 文章里描述的两种典型场景更值得思考：

Agent 在执行高风险操作之前主动暂停，等人确认。比如要发一封邮件、执行一笔金融交易、删除文件——Agent 起草好内容，展示给你看，你可以直接批准，可以修改内容再批准，也可以拒绝并说明原因让 Agent 重新来过。这不是"让人兜底"，这是在关键节点上保持人类的决策权。

Agent 遇到歧义主动提问。当 Agent 发现一个问题有三种可能的理解方式，而选错了代价很高，它不应该猜——它应该直接说："我找到三个符合条件的配置文件，你要改哪个？"你的回答变成 `interrupt()` 的返回值，Agent 从刚才停下的地方继续。

这个设计最精妙的地方在于：`interrupt()` 可以放在代码的任何位置，包括工具函数内部。这意味着审批逻辑跟着工具走，不需要在 Agent 的主循环里做特殊处理。`Command(resume=...)` 的返回值不限于 approve/reject，可以是任意 JSON——修改过的草稿、缺失的上下文、计算结果。这种灵活性让 HITL 真正成为一个通用的人机协作原语，而不是一个特定的"审批流程"。

这其实和我一直讲的产品设计原则很吻合：在 Agent 自主性不够高的时候，不要让用户填空题，让 Agent 主动问、给用户做选择题。60% 准确率的 Agent 加上合理设计的 HITL，比 60% 准确率的全自动 Agent 好用很多。关键是让用户感受到掌控感，而不是被一个不透明的系统支配。

**可观测性：你不跑起来，你就不知道它会干什么**

LangChain 文章里有一句话说得很准：

> "Unlike a traditional application where you can reason about behavior from the code, an agent's execution path depends on the model's choices at runtime."

这句话背后的含义我有时候觉得还没有被足够多的人真正吸收进去。传统软件的 bug，你读代码就能推理出来。Agent 的 bug，很多时候你必须看 trace——看它在那个具体的 case 里到底调用了什么工具、传了什么参数、得到了什么结果、然后做了什么决定。

一张 trace，能看到：用户发了什么消息、模型的意图是什么、调了哪些工具、工具返回了什么、Agent 陷入循环是从哪一步开始的。没有 trace，你只能靠用户的抱怨文字去猜。

这让我想到 AI 开发和传统软件开发最根本的差异之一：AI 产品是非确定性的，相同的输入可能产生不同的输出，同样的 Prompt 在不同的模型调用里行为不同。这意味着传统的单元测试逻辑无法覆盖 Agent 的真实行为，你必须在生产里持续观测、持续评估。LangChain 的 Online Evals 就是把 LLM-as-judge 接到生产 trace 上，自动跑评分，实时发现回归。

他们还有一个叫 Time Travel 的功能：从某个 checkpoint 开始，改变其中的状态，让 Agent 从那里重新跑，看会发生什么不同。这对 debug 非常有价值——不需要从头重现整个对话，直接定位到出问题的那一步，改一个变量，看结果怎么变。这其实就是 AI 工程里的"控制变量实验"，只是被集成进了 runtime 的基础设施里。

**沙箱执行：Agent 有没有能力"真正动手做事"**

这是 Deep Research 类 Agent 和普通 chatbot 之间的一条分水岭。

一个只能调用预先定义好工具的 Agent，能做的事情被工具集死死限制住。一个能执行任意代码的 Agent——安装依赖、克隆 repo、跑测试、做数据分析、生成文档——才是真正意义上的"能做事的 Agent"。

但随意执行代码的问题也很明显：如果代码在你的宿主机上跑，Agent 一旦被 prompt injection 攻击，或者自己出了逻辑问题，后果可能是灾难性的。

LangChain 的解法是沙箱隔离：Daytona、Modal、Runloop 或者自研的 LangSmith Sandboxes，配置一个 sandbox backend 之后，Agent 自动获得 `execute` 工具；不配置就没有这个工具。沙箱和宿主机之间有隔离边界，Agent 的代码只能影响沙箱内部。

但他们有一句提醒值得单独记住：**沙箱保护的是你的宿主机，不是沙箱本身**。如果攻击者通过 prompt injection 控制了 Agent 的输入，让 Agent 在沙箱里执行恶意代码，沙箱内部的凭证就会泄露。这就是为什么他们设计了 auth proxy——API key 不放进沙箱，由一个 sidecar proxy 拦截出站请求，自动注入认证头。沙箱里的代码调 `api.openai.com` 不带任何 header，proxy 在出去之前加上 `Authorization`。这个设计意味着凭证从来不进入沙箱环境，即使沙箱被攻破，攻击者也拿不到 key。

**开放性：你对自己的 Agent 有多少控制权**

文章最后有一段话让我停下来多想了一会儿。

LangChain 提到当前 Agent 基础设施领域有一个趋势：某些托管方案把越来越多的 Agent 行为封装进黑箱——Prompt 被框架接管、记忆压缩生成加密摘要你没法用在其他地方、模型和沙箱供应商被锁定。团队慢慢失去了"我知道我的 Agent 在干什么"的能力，也失去了"我可以改变它"的能力。

这和我一直在讲的一个原则很接近：不要把 Prompt 外包给框架，要对自己 Agent 看到的东西有完整的控制权。上下文工程（context engineering）是 Agent 开发最核心的技术能力，如果这部分你看不见、改不了，你实际上是在用一个黑盒产品，而不是在做 Agent 工程。

LangChain 的 Deep Agents 选择了 MIT license，harness 完全开源，用 AGENTS.md 作为开放标准，通过 MCP 和 A2A 协议对外暴露，不锁定模型和沙箱供应商。你可以看到每一层在做什么，可以修改任何一层，可以把 PostgreSQL 的数据迁移走，可以换模型提供商。

这种选择背后有一个判断：在 Agent 基础设施领域，锁定用户的短期收益和失去用户信任的长期代价，是不成比例的。对于真正要做生产级 Agent 系统的团队来说，对底层的可见性和可控性不是 nice-to-have，而是能不能长期维护和演进这个系统的前提条件。

**我的思考：Agent 工程的"隐性成本"正在被算清楚**

我认为这篇文章揭示的不只是 LangChain 自己的技术选择，而是整个 Agent 工程领域正在经历的一次认知迭代：从"让 Agent 跑起来"到"让 Agent 跑得住"。

回顾 AI 应用的发展轨迹，第一波 ChatGPT API 爆发的时候，大家建的东西大多是"把 LLM 嵌进一个输入输出框里"。第二波是 RAG 加 function calling，Agent 能调工具了，demo 能跑了。现在是第三波——真正意义上的 long-horizon agent，能跑几十分钟、能暂停等人、能跨对话积累记忆、能在生产里稳定运行。

这三波之间的跨越，每一次都不只是模型能力的提升，更是工程基础设施的系统性升级。从数据库到消息队列到微服务，传统软件工程花了几十年解决的可靠性、可伸缩性、可观测性问题，在 Agent 领域正在被重新解决，而且需要在"非确定性执行"这个约束下重新解决。这比传统软件难一个量级。

让我有点坐不住的是记忆这个问题。LangChain 这篇文章把长期记忆做成了基础设施的一部分，按 user_id 和 organization 分级存储，支持语义检索，数据在自己的 PostgreSQL 里。这是对的方向，但我们现在能做到的还是太初级——大多数 Agent 的"记忆"，本质上是"把一堆文字压缩成摘要再喂给下一次"，和真正意义上的"从经验中学习并改变行为"还差得很远。

但正是因为这个方向还没被完全解决，才是现在最值得深入的地方。Memory 做好了，Agent 才能真正从"工具"变成"助手"。助手和工具的区别，不是它能做什么，而是它知道你是谁、你习惯什么、你上次做到哪一步。

还有一个角度我想补充：这整套 Runtime 设计，让我意识到"Deep Research"类的 Agent 之所以是目前落地最靠谱的场景，除了任务本身的确定性，很大程度上也是因为这类任务的容错性高——跑个二十分钟、中间出错了从上个 checkpoint 重试、最后出一份报告——这个模式和持久化执行 + checkpoint 的机制配合得天衣无缝。反过来说，那些需要实时响应、高度个人化、强记忆依赖的 Agent 场景，才是 Runtime 挑战最大、也最值得下功夫的地方。

这场基础设施的搭建才刚刚进入认真的阶段。
