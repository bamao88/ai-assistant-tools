# 模型的知识总是过期的——但 Google 用一个 Skill 把这个问题解决了

你有没有想过，你花了几个月时间调教的 AI Coding Agent，其实一直在用一套过时的 API？

不是模型不够聪明，不是 prompt 写得不好，而是模型本身根本不知道这个 API 已经换了。它在训练的时候学到的是旧版本的写法，它非常自信地给你生成代码，每一行都像是经过深思熟虑的，但跑起来就报错——因为那个 SDK 已经三个月前就弃用了。

这是一个没有多少人认真对待的问题。大家都在讨论 RAG、MCP、多 Agent 协作，但几乎没有人正面回答这个最基本的问题：**模型的知识是静态的，软件工程的世界是动态的，这个裂缝怎么补？**

最近 Google DeepMind 的开发者关系团队发了一篇技术博客，我读完之后心里有点不是滋味——不是因为内容不好，恰恰相反，是因为他们用一个极其简单的方案，把一个我以为很难的问题给解决了，而且拿出了让人坐立不安的数据。

---

**知识截止日是 AI Coding Agent 的阿喀琉斯之踵**

我在教 Claude Code 的时候，经常遇到一类问题：学员按照某篇教程，让 AI 帮他们写 Gemini API 的调用代码，AI 写出来的是旧版 SDK 的写法。他们照着跑，报错，然后来问我为什么。

我告诉他们：这不是 AI 的错，是时间的错。

模型在某个时间点完成了训练，它对世界的认知就定格在那一刻。API 在后来怎么更新、新 SDK 出了哪些 breaking changes、最佳实践怎么演进——这些它都不知道。更麻烦的是，它不知道自己不知道。模型没有元认知能力意识到"哦，这是我知识截止日之后的内容，我应该去查一下"，它只会用它学到的东西自信地回答你。

Google 内部也遇到了同样的问题。他们自己的 Gemini 模型，在被问到如何使用 Gemini API 时，大量生成的是旧版 SDK 的代码。不仅是外部开发者会被坑，连模型自己都不知道如何正确调用自己的 API。

这是一个有点讽刺的现实：世界上最先进的语言模型，在使用自己家 SDK 这件事上，一开始的准确率只有 6.8%。

---

**Skill 是什么，为什么不是 RAG，也不是 MCP**

面对这个问题，市面上的常见解法是两类：一是给 Agent 加网络搜索能力，让它自己去查最新文档；二是搭一个 MCP 服务器，把文档库实时接进去。

这两条路都能用，但都有代价。搜索需要模型知道去哪里搜，搜回来的内容需要再次理解；MCP 服务器需要用户安装配置，维护成本不低，而且协议层面不是每个环境都支持。

Google 团队探索了一条更轻量的路：**Agent Skill**。

Skill 这个概念，我在自己的 Agent 系统里用得很深。最简单的理解是：一段结构化的指令文本，告诉 Agent"这个领域有什么能力、有什么工具、应该去哪里找最新信息"。它不是代码，不是 API 调用，就是一份写给 Agent 看的能力说明书。

Google 做的 Gemini API developer skill 里包含了四类信息：API 的高层功能介绍、当前在用的模型版本和各语言 SDK 信息、每个 SDK 的基础代码示例，以及最重要的——官方文档的入口链接。最后这一条才是关键。

这个设计很巧妙：Skill 本身并没有把所有文档都塞进去，它给的是"去哪里找真相"的指针。Agent 在执行任务时，一旦 Skill 被激活，它就知道对于 Gemini API 相关的编码任务，有两个工具可以用：`activate_skill` 和 `fetch_url`。它会去主动拉取最新的官方文档，而不是依赖自己的记忆。

这让我想起我一直说的一个判断：**Agent 能力的上限，取决于它能访问的知识质量**。一个 Agent 给它的 Skill 越好，它能完成的任务质量就越高。MCP 解决的是"能不能调用工具"，Skill 解决的是"能不能完成任务"。两者的层级是不一样的。

---

**数据是残酷的：从 6.8% 到 96.6%**

让我有点坐不住的，是他们公布的评测数字。

Google 团队搭了一个包含 117 个 prompt 的评测集，涵盖 Python 和 TypeScript 两种语言，测试场景横跨 Agentic coding、聊天机器人、文档处理、流式输出、SDK 特定功能等多个领域。判定标准很直接：如果生成的代码用了旧版 SDK，就算失败。

没有 Skill 的时候，最新的 Gemini 3 系列模型（3.0 Pro 和 Flash）准确率是 6.8%，3.1 Pro 是 28.2%。加上 Skill 之后，3.1 Pro 的准确率跳到了 96.6%。

这组数字有几件事值得单独拎出来说。

第一，**提升幅度不是线性的，是指数级的**。从 28% 到 97%，不是优化，是质变。这意味着之前的错误不是随机分布的，而是有系统性的根源：模型的知识边界。一旦给它补上了这个信息，它的推理能力立刻就发挥出来了。

第二，**旧版模型（2.5 系列）受益有限**。同样加了 Skill，2.5 系列的提升远没有 3.x 系列那么显著。Google 的解释是：Skill 需要配合强推理能力才能发挥最大效果。弱一点的模型拿到 Skill 之后，不一定能正确理解并执行"去拉文档"这个动作链。

这个发现很重要。它说明**知识注入和推理能力是相互依赖的**，你不能只补知识，不管推理；也不能只追求模型推理能力，而忽视给它正确的上下文。两者缺一不可。

---

**推理能力是 Skill 发挥作用的必要条件**

这是这篇博客里我认为最深刻的一个判断，但它几乎被轻描淡写地带过了。

Google 的数据表明，Gemini 2.5 系列模型加了 Skill，提升有限；但 Gemini 3.x 系列模型加了 Skill，提升巨大。区别不在 Skill 本身，而在模型能不能正确使用 Skill。

怎么用 Skill？要先读 Skill 说明，判断当前任务是否适合激活，然后调用 `activate_skill`，拿到额外指令后再决定是否需要 `fetch_url` 去拉最新文档，拿到文档之后还要理解文档，提取出正确的 SDK 用法，然后才开始写代码。

这个流程看起来不复杂，但每一步都需要元认知：我在做什么任务？我知不知道这个任务的最新实践？我需不需要去查？我拿到的文档里哪部分是关键的？

这些判断，弱一点的模型做不好。它拿到 Skill 可能不知道要激活，或者激活了但拿到文档不知道怎么用。只有推理能力足够强的模型，才能把 Skill 这件"打辅助"的外部能力真正转化为任务完成率。

我一直认为，Agent 工程里最难的不是写工具调用的代码，而是**让 Agent 知道什么时候该用什么工具**。一个好的 Agent 系统，工具调用的触发逻辑应该是模型自发决策的，而不是靠 prompt 里把每个工具的调用时机都手工写死。越能自主判断，越说明模型和 Skill 的配合达到了真正的协同。

---

**Skill 的局限：新鲜度和更新机制是真实痛点**

Google 自己在博客里也承认，这个方案并不完美，有两个具体的问题。

第一个是 Skill 文件本身的新鲜度问题。用户一旦安装了 Skill，这个文件就停在了安装那一刻。如果之后 API 又有更新，Skill 没有自动同步机制，用户需要手动更新，这件事大多数人都不会做。长期来看，一份过期的 Skill 可能比没有 Skill 更危险——因为它会给 Agent 一个错误的自信，让它觉得自己知道最新情况，但其实用的还是旧信息。

第二个是 Vercel 的对照实验提供了一个反例。Vercel 自己测试过，直接用 `AGENTS.md` 这种项目级配置文件把指令写进去，比让 Agent 主动激活 Skill 效果还要好。原因也不难理解：直接在 system prompt 或项目配置里把关键信息写死，模型不需要额外的推理步骤去决定要不要激活，直接就有了上下文。

这两个问题叠加起来，指向一个更深层的问题：**Skill 本质上是"外挂知识 + 延迟加载"，直接注入是"即时知识 + 零延迟"**。前者更灵活、更轻量，但在关键时刻可能不如后者可靠。

我在自己的系统里也在反复面对这个取舍。做成 Skill 的好处是可组合、可复用，一份 Skill 可以装进很多不同的 Agent 环境；但如果任务的核心知识是固定的，直接写进上下文要比等 Agent 自己去加载更稳定。这不是哪种方式更好的问题，而是**要根据任务的稳定性和知识的时效性来判断使用哪种注入方式**。

---

**SDK 维护者可以做的事：不只是等模型更新**

这篇博客让我意识到一件事，我之前没有想清楚过。

以前每次 SDK 出了大更新，大家的期待是：等下一个模型版本训练完，它就知道了。这个"等"的周期少则半年，多则一年以上。在这段时间里，所有用 AI 写这个 SDK 相关代码的开发者，都处于一个"高自信低准确"的陷阱里。

但 Google 这次展示了另一条路：**SDK 维护者自己可以主动出手，发布一份配套 Skill 文件，立刻弥补模型的知识滞后**。

这件事的门槛非常低。不需要重新训练模型，不需要搭复杂的服务，就是维护一个 Markdown 文件，写清楚"现在的用法是什么、官方文档在哪里"，然后打包发布。

如果这个模式被更多 SDK 维护者采用，整个 AI Coding 生态的可靠性会有质的提升。每一个活跃维护的 SDK，如果都随版本更新同步一份 Skill 文件，那些因为模型知识滞后导致的低级错误将会大幅减少。

这是一个开发者社区本来就有能力做、但几乎没有人认真推动过的基础设施。

---

**我的思考：上下文供给能力，正在变成 AI 时代的核心竞争力**

读完这篇博客，我一直在想一个比 Skill 本身更大的问题。

过去两年，大家讨论 AI Coding 的焦点，几乎都集中在模型能力上：参数量多大、上下文窗口多长、推理有没有 chain-of-thought。但这次 Google 的实验给了一个非常清醒的提示：模型能力只是一半，另一半是**你给模型提供了什么上下文**。

一个 96.6% 准确率的 Gemini 3.1 Pro，和一个 28.2% 准确率的 Gemini 3.1 Pro，是同一个模型。区别只是后者多了一份 Skill 文件。换句话说，**相同的推理能力，搭配不同质量的上下文，产出可以相差三倍以上**。

我一直有一个判断：2026 年最重要的 AI 技能不是 prompt engineering，是 context engineering。怎么给模型构造高质量的上下文，比怎么写出一句聪明的 prompt，要重要得多。Skill 是 context engineering 的一种具体实践：把"什么是这个任务域的基础知识"这件事结构化，提前整理好，在需要的时候注入进来。

这件事往更大了想，其实和整个 AI 时代软件产品的竞争逻辑有关。以前你的产品壁垒是功能，是体验，是用户规模。但在 AI 时代，会越来越多地出现这样一类竞争：谁能给 AI 提供更好的上下文，谁的 AI 就输出更好的结果，谁就赢。

这有点像 PC 时代操作系统的竞争，最终不是纯粹比谁的内核性能更好，而是比谁的生态能提供更多可调用的能力。AI 时代的新版本是：谁能维护更新鲜、更准确、更覆盖全面的上下文供给体系，谁的 AI 就更强。Google 这次发布的 Gemini Skill，其实是在为自己的 SDK 构建这套上下文供给基础设施的第一步。

还有一件事值得单独说：这次实验再次证明，**弱工具 + 强推理，远比强工具 + 弱推理有效**。Skill 本身只是一个 Markdown 文件，两个工具调用，没有什么魔法在里面。真正让它发挥威力的，是模型能够正确理解"我现在该激活这个 Skill"这件事。这和我自己在 Agent 工程里反复遇到的情况一模一样：你做了多少工具，不如你的 Agent 有多少判断力。

而判断力，是模型本身带来的，不是 Skill 带来的。这意味着随着模型越来越强，Skill 这个机制的价值会越来越大——不是因为 Skill 变好了，而是能用好 Skill 的模型变多了。

这场关于"如何给 AI 提供正确知识"的基础设施之战，才刚刚开始。
