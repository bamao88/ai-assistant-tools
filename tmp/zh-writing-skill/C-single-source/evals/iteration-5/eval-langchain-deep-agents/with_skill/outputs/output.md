# 你的 Agent 为什么在 Demo 阶段很完美，上了生产就崩了？

你有没有想过，现在大多数人做的 Agent，其实还没离开"Demo 阶段"？

表面上看起来一切顺利——本地跑起来，测试用例全过，演示时效果惊艳，投资人点头，老板满意。但一旦真正部署到生产环境，问题就接二连三冒出来：用户刚发完一条消息，Agent 就崩了重头来过；一个耗时二十分钟的研究任务，因为服务器重启全部白费；多个用户同时使用，数据一不小心就串了；Agent 明明已经快完成任务，用户突然改了需求，整个流程乱成一锅粥。

这些不是模型不够聪明的问题，也不是 Prompt 写得不够好的问题。这是基础设施的问题。

我最近读到 LangChain 发布的这篇技术指南，它系统讲述了把 Agent 送进生产环境所需要的底层运行时基础设施。读完之后我意识到，我们行业里有相当多的人，正在把 80% 的精力放在打磨 Harness（Prompt、工具、技能这些 Agent 外壳），却把支撑整个系统长期稳定运行的"地基"完全忽略了。

这篇文章，我想认真说一说这个"地基"是什么，为什么它比你以为的重要得多。

---

**Agent 上线等于走钢丝，没有安全网就是在赌命**

先说一个让我印象最深的基本问题：Agent 和传统 Web 服务有一个本质区别——它跑的不是几毫秒的请求，而是可能持续几分钟甚至几十分钟的长流程任务。

传统 Web API 的生命周期很短：一个请求进来，处理完，返回结果，连接关闭。你可以无状态部署，随便扩缩容，服务崩了重启就好。但 Agent 的执行逻辑完全不同。一个研究型 Agent 可能在一次运行里调用几十次模型、抓取数十个网页、生成大量中间结果。如果服务器在第 18 分钟挂了，这一切都从头来过——那些已经花掉的 Token 算谁的？那些用户等待的时间还要再等一次？

更极端的情况是 Human-in-the-Loop（人工审核介入）。一个 Agent 起草完一封邮件需要用户审批，用户可能 30 秒就回复，也可能三天之后才打开邮件。在等待这三天的过程里，那条进程要一直挂着吗？这显然不现实。

LangChain 这篇指南指出，解决这两个问题的答案是同一个东西：**持久化执行（Durable Execution）**。核心机制是 Checkpoint——每次执行一个"超步"（super-step），就把完整的图状态写入持久化存储（默认是 PostgreSQL），以当前线程的 `thread_id` 为索引。服务器崩了，新 worker 自动从最后一个 Checkpoint 接着跑；Agent 需要等待人工审核，进程直接释放，等到用户回复时再精确地从中断处恢复。

这个观点击中了要害。我在辅导学员做 AI 产品时，经常看到大家把注意力全放在"怎么让 Agent 更聪明"上，却很少想"怎么让 Agent 不因为基础设施问题而白白浪费"。持久化执行不是加分项，是生产级 Agent 的基础条件。

**短期记忆与长期记忆，是两个完全不同的工程问题**

Memory 这个话题，我一直觉得行业里理解得比较浅。很多人说"给 Agent 加记忆"，其实只是在 Prompt 里塞更多上下文，或者在代码里维护一个 conversation history 数组。这能解决一些问题，但它解决的只是短期记忆——同一次对话里的上下文连贯性。

LangChain 这篇指南里做了一个我认为非常重要的区分。

短期记忆（Short-term Memory）：属于一次对话的状态，跟着 thread_id 走，对话结束就可以清掉。这是 Checkpoint 里自然存储的内容。Agent 在同一个线程里的第二条消息，能看到第一条消息以及所有工具调用结果——这很好实现，Checkpoint 机制天然支持。

长期记忆（Long-term Memory）：跨对话的用户级别或组织级别信息。比如用户的偏好、某个项目的约定规范、Agent 在多次对话中积累下来的经验。这些东西不属于任何一个具体的 thread，它们应该在所有对话之间共享和持续更新。

这两者的工程路径完全不同。短期记忆依托 Checkpoint；长期记忆需要一个独立的 Memory Store，用命名空间组织（比如 `(user_id, "memories")`），支持语义搜索（按含义检索而不是精确匹配），并且要能跨线程读写。

这让我想起自己在研究 Claude Code 时观察到的现象：Claude Code 的工具调用能力已经相当超人类，但在理解用户长期偏好、记住项目个性化约定这件事上，确实是明显的短板。各家 Agent 产品的解法不一——有的用 Markdown 文件，有的用结构化文档——但本质都是在做同一件事：把"对未来有价值的信息"从当前对话里提炼出来，存到一个持久的地方。

但这里有一个我认为常被忽视的工程考量：这些跨对话积累的记忆数据，可能是整个 Agent 系统里最有价值的数据。它们是用户与 Agent 交互的历史总结，是 Agent 个性化能力的来源。它们存在哪里、谁能访问、格式是否标准——这直接决定了你未来能否迁移模型、分析行为、在 Agent 之外独立使用这些数据。放在可以被自己 SQL 查询的 PostgreSQL 里，和锁在某个黑盒 SaaS 系统里，长期价值差异是巨大的。

**多租户不是"加个登录"这么简单**

很多人以为多租户问题就是给 API 加一个 Authentication，检查一下用户 Token，然后在数据库查询里加个 WHERE user_id = xxx 过滤。这在传统 Web 应用里基本够用，但 Agent 的场景要复杂得多。

LangChain 这篇文章把多租户拆成了三个独立的工程问题：

第一个问题是用户数据隔离。A 用户的对话线程不能被 B 用户访问，A 用户的长期记忆不能被 B 读取。这听起来基础，但在 Agent 的多步骤执行过程中，状态在各种存储之间流转，隔离要做到每一层。

第二个问题更有意思：**Agent 代替用户执行操作**。一个代理你管理日历的 Agent，需要用你的 Google OAuth Token 去调用 Google Calendar API，而不是用系统级服务账号。但这个 Token 应该怎么安全存储、怎么自动刷新、怎么在多次对话之间复用？这需要一套专门的 Agent Auth 机制，处理 OAuth 授权流程和 Token 生命周期，让 Agent 在用户授权一次之后，在后续所有对话里都能代表用户行动。

第三个问题是内部权限控制。谁可以部署新的 Agent 版本？谁可以查看生产环境的 Trace？谁可以修改认证策略？这是面向你的团队成员的 RBAC（基于角色的访问控制），与面向终端用户的认证完全分离。

这三层在实践中必须同时存在，而且不能混淆。我见过很多早期 AI 产品，多用户场景出问题大多不是因为加了恶意代码，而是因为三层混在一起，某个细节的疏漏导致数据泄露或越权操作。

**Human-in-the-Loop 的正确打开方式**

Human-in-the-Loop（HITL）这个概念现在被说得很多，但大部分讨论停留在"应该让人审核"的层面，很少讲清楚工程上该怎么实现。

文章里给出了两个典型场景，让我觉得设计非常巧妙的一点是，它们的触发逻辑完全不同。

第一种是工具调用前的审批。在 Agent 准备执行一个高风险操作之前——发邮件、转账、删文件——系统暂停，把"Agent 准备做什么"显示给用户，等待用户批准、修改或拒绝。用户不只是 approve/reject，还可以在邮件内容上做修改，然后把修改后的草稿作为"恢复值"返回给 Agent，Agent 继续执行修改后的版本。

另一种场景更有意思：Agent 遇到了歧义，主动暂停提问。与其猜测用户意图然后走错方向，不如直接说"我找到了三个匹配这个模式的配置文件，你想修改哪一个？"这个问题本身成为 interrupt() 的返回值，用户的回答让 Agent 从精确的暂停点继续。

关键工程细节是 interrupt() 和 Command(resume=...) 这一对原语。interrupt() 触发 Checkpoint，把整个图状态写入持久化存储，进程释放资源；Command(resume=...) 带着用户的响应回来，恢复值成为 interrupt() 调用的返回值，执行从中断处精确继续。由于 resume 接受任意 JSON 序列化值，响应不限于 approve/reject——可以是修改后的草稿，可以是缺失的上下文信息，可以是外部系统注入的计算结果。

这个设计背后有一个我认为非常深刻的工程原则：确定性逻辑监管不确定性 AI。我在研究 Agent SDK 架构时一直在强调 Hook 的价值——Hook 是确定性的传统代码在 AI 决策流程里的"安检站"。HITL 的 interrupt/resume 机制本质上就是这个原则的自然延伸：在关键决策点，让人类（最终的确定性判断者）进入循环，而不是完全依赖模型的概率性判断。Agent 越自主，这个安检站越重要。

**你不知道 Agent 在生产环境里会做什么，直到它真的跑起来**

文章里有一句话让我后背一凉："You don't know what an agent will do in production until you run it."

这句话在 AI 开发语境里有特殊的重量。传统软件你可以从代码推断行为——给定相同输入，相同输出，测试覆盖就是保障。但 Agent 的执行路径取决于模型在运行时的选择：调哪个工具、传什么参数、怎么解读返回结果、什么时候放弃重试。相同的输入，你可能得到完全不同的执行轨迹。

这就是 Observability（可观测性）对 Agent 来说不是加分项而是必需品的原因。

用户提了一个 Support ticket 说"Agent 一直在重复提同一个问题"。没有 Trace，你只能根据用户的文字描述猜测。有了 Trace，你看到完整的执行树：用户的原始消息、模型的规划输出、每次工具调用的参数和返回值、下一轮模型生成的内容、最终陷入的循环——哪一步出了问题，一目了然。

比这更有价值的是，Trace 是改进循环的起点。你可以按 cost 过滤找出 Token 消耗异常的 run，按 error 过滤找出失败的 run，按 user 过滤看某个特定用户的体验。这些聚合视角，是任何单一测试用例都给不了你的。

这和我一直强调的观点一致：AI 应用的本质是"确定性迭代不确定性"——你无法在设计阶段预判所有执行路径，但你可以通过对生产数据的持续观测，把不确定性慢慢压缩到可接受范围内。Trace 就是这个压缩过程的核心数据来源。

LangChain 还提到了一个叫 Time Travel 的能力，让我觉得这个概念非常巧妙的一点是它超越了传统 Debug 的范式。不只是"看发生了什么"，而是"如果这个时间点的状态不一样，后续会怎么走"——pick 一个 Checkpoint，修改它的状态，fork 出一条新的执行分支，观察不同决策的下游影响。这才是真正意义上的 Agent Debugging。

**Guardrails（护栏）不能放在 Prompt 里，要写进代码**

这一点我一开始看的时候有点意外，但想清楚之后觉得完全对。

很多人处理敏感数据脱敏或操作频率限制的方式，是在 System Prompt 里写"你不能对外暴露用户的个人信息"、"每次最多调用 X 工具三次"。但 Prompt 是概率性的——模型不总是遵守，在长流程任务里可能"忘记"早期的指令，在复杂推理链条里可能被引导绕过。

工程化的解法是 Middleware（中间件）。Middleware 包裹 Agent 的执行循环，在 before_model（模型调用前）、wrap_model_call（包裹模型调用）、wrap_tool_call（包裹工具调用）、after_model（模型调用后）这些确定性节点上运行传统代码。不管模型怎么"想"，这些代码都会跑——这才是真正意义上的 Guardrail。

PII 脱敏、模型重试、模型降级 Fallback、工具调用次数上限、内容审核——这些都可以作为 Middleware 插入，而不是寄希望于 Prompt 里的语言描述。这与 Hook 的核心逻辑一脉相承：用传统代码的确定性监管 AI 的概率性，不是建议，是强制执行。

**沙箱隔离：Agent 跑任意代码的正确姿势**

能运行任意代码的 Agent 比只能调用预设工具的 Agent 强大得多。一个可以安装依赖、执行测试、运行数据分析的 Agent，才是真正意义上的"能做事的 Agent"，而不只是"聊天机器人加工具调用"。

但任意代码执行意味着安全边界的问题。如果 Agent 在你的主机上运行 `rm -rf /` 或者读取环境变量，后果是灾难性的。沙箱隔离的意义就在这里：给 Agent 一个隔离的执行环境，让破坏只限于沙箱内部。

文章里特别提到了一个我认为在工程实践中经常被忽视的细节：**沙箱保护的是你的主机，而不是沙箱本身**。如果攻击者通过 Prompt Injection（在 Agent 抓取的网页里注入恶意指令）控制了 Agent，可以让 Agent 在沙箱里运行任何命令——沙箱阻止了攻击者进入你的主机，但沙箱内部的凭证（API Keys、Token）可能已经泄露。

所以真正安全的方案是 Auth Proxy：API 凭证不进入沙箱代码，而是由一个 sidecar 进程拦截沙箱的出站请求，在请求离开之前注入正确的 Authorization header。沙箱代码调用 API 时不携带任何凭证，凭证在沙箱外部被注入，Agent 无法读取、也无法泄露。这是一个非常精妙的安全设计——隔离了职责，最小化了攻击面。

**Cron：大部分有价值的 Agent 任务其实不需要用户触发**

最后一个让我深有共鸣的点，是关于定时任务（Cron）的。

文章区分了两种 Agent 工作模式：reactive（被动响应用户消息）和 proactive（主动在调度时间运行）。

绝大多数人做的 Agent 是 reactive 的——用户发消息，Agent 回复。但很多最有价值的 Agent 工作，其实不需要用户来触发。每天晚上整理明天的日程并生成简报，每晚扫描新发布的论文把相关的标注出来，每 15 分钟检查一次监控告警并在发现问题时通知值班人员——这些都是"sleep-time compute"，在用户不在场的时候完成有价值的工作，让用户回来时直接看到结果。

这种模式的关键在于：Cron run 需要和普通 run 享有同等的基础设施支持——同样的 Durability、同样的 Tracing、同样的 Auth。一个凌晨三点运行的 Cron 任务，如果遇到模型服务暂时不可用，它应该自动重试，不应该静默失败然后用户第二天早上发现什么都没做。这和日间的用户交互请求没有任何区别。

**我的思考：我们可能把 80% 的精力放在了 20% 的问题上**

读完这篇技术指南，让我深思的是一个反直觉的认知：大多数人说"做 Agent"，其实做的只是 Harness——Prompt、工具、技能、模型选型。这些确实重要，是 Agent 能力的上限。但把 Agent 送进生产、让它稳定运行、让它能服务真实用户、让它在出错时能恢复——这是 Runtime 的问题，不是 Harness 的问题。

回顾 AI 工程的演进，每一代技术的成熟都经历过同样的路径。早期大家都在讨论"模型能不能做到"，然后当模型能力不再是瓶颈时，工程化问题就浮出水面。RAG 刚出来时大家关注召回质量，后来大家发现缺的是生产环境的监控和评测体系。Agent 现在走的是同一条路：2025 年之前，核心问题是"Agent 能不能完成复杂任务"；2025 年之后，越来越多的团队发现，真正的难点是"让 Agent 在生产环境里稳定、可控、可观测地运行"。

这就像互联网早期，大家都在研究怎么写功能，到后来才发现 CDN、负载均衡、数据库连接池这些"不性感但必要"的基础设施，才是撑起大规模商业化的关键。Agent 正在经历同样的范式转变。

从我自己的实践来看，Agent 工程从来都不是在"更聪明的 Prompt"和"更好的模型"上打转，而是在确定性与非确定性的张力之间不断找平衡。Middleware 是确定性代码监管非确定性模型的工具，Checkpoint 是确定性状态持久化支撑非确定性长流程的工具，Trace 是确定性数据驱动非确定性行为改善的工具。每一个 Runtime 能力，本质上都是在给 AI 的不确定性套上一层确定性的框架。

AI Agent 的能力上限，取决于模型和 Harness 的设计。但 Agent 能否进入真实世界、服务真实用户、被企业信任并付费——这取决于 Runtime 的完善程度。那些今天看起来"Demo 很完美"却迟迟无法商业化落地的 Agent 产品，很多并不是因为模型不够聪明，而是因为地基还没打好。

这场变革才刚刚开始，但基础设施的竞争，早就已经开始了。
