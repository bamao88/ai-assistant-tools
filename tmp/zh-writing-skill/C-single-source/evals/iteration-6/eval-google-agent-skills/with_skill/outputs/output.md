# 一个实验让成功率从28%跳到96%，Google DeepMind告诉了我一件非常重要的事

你有没有想过，让 AI 写出"正确的代码"这件事，可能比你想象中难得多？

不是难在技术复杂度，而是难在一件特别奇怪的事情：模型根本不知道自己现在已经"过时"了。

上个月我在看 Google DeepMind 发布的一篇技术博客，内容是他们为 Gemini API 构建了一个叫"agent skill"的东西——说白了，就是一份给 AI 读的"最新使用说明书"。他们用 117 个测试用例跑了前后对比，结果让我后背一紧：同一个模型（gemini-3.1-pro-preview），在没有 skill 的情况下，通过率是 28.2%；加上 skill 之后，通过率跳到了 96.6%。

这不是小幅提升。这是一次接近质变的跨越。

我当时读完第一反应不是"哇这个 skill 真厉害"，而是：等一下，模型自己不知道自己的最新 API 是什么？这件事本身说明了什么？

**模型天生活在过去，这才是真正的问题**

大语言模型有一个基本特性：训练截止日期。在那个日期之后发生的所有事情，模型一概不知。这个道理大家都懂，但大多数人没有认真想过这件事意味着什么。

对 Google 自己的模型来说，问题尤其明显。模型被训练的时候，Gemini API 的文档、SDK 规范、最佳实践，可能已经是几个月前的版本了。而软件工程这个领域，几个月意味着什么？意味着 SDK 可能改了名字，API 接口可能换了参数，旧的调用方式可能被废弃了，新的功能可能上线了。

Google DeepMind 在博客里直接承认了这件事：他们的模型"不知道自己"——也就是说，模型不了解自己最新版本的能力和接口规范。这个表述有点反直觉，但仔细想想非常合理。你不能指望一个在去年某个时间点被"冻结知识"的模型，自动知道今天最新的 SDK 应该怎么用。

这让我想起一个我在训练营里经常说的类比：想象你招了一个技术能力很强的工程师，但他在入职前有三个月完全没有接触过任何技术新闻和文档更新。你让他直接开始写代码，他写出来的东西从逻辑上没问题，但用的是过时的库，调用的是已经被废弃的接口。这不是他的能力问题，而是信息问题。

AI 也面临完全一样的处境。只不过对 AI 来说，这个"断联"的时间窗口是无法避免的，因为训练本身就需要时间。

**skill 到底做了什么，为什么有效**

Google 构建的这个 skill 内容其实并不复杂。它主要做了四件事：解释 Gemini API 当前的能力范围，说明现在应该用哪些模型和 SDK，提供最新版本的示例代码，以及——这是最关键的一点——列出了文档的入口地址，引导模型去"取新鲜的信息"。

最后这一点我觉得特别聪明。与其把所有最新内容都塞进 skill 里，不如告诉模型："如果你不确定，去这个地址拿最新文档。"这实际上是一种元能力的注入——不是给答案，而是给取答案的路径。

技术实现上，当模型开始任务时，系统会给它两个工具：`activate_skill` 和 `fetch_url`。前者激活 skill 的指导内容，后者让模型可以实时抓取文档。模型如果遇到不确定的地方，可以主动去查最新资料，而不是依赖自己训练时"记住"的旧内容。

让我深思的是这背后的设计哲学——它把 AI 的知识分成了两层：一层是训练进模型的"静态知识"，另一层是运行时通过工具获取的"动态知识"。skill 本身只是一个轻量级的连接器，告诉模型如何访问那层动态知识。

这个观点击中了要害。我一直认为，好的 Agent 设计不是把所有东西都训进模型，而是让模型知道"我不知道的东西在哪里可以找到"。

**推理能力才是决定性变量**

这里有个细节值得单独拿出来讲。实验里，Gemini 3.0 和 3.1 系列加了 skill 之后效果非常显著；但 2.5 系列的模型加了 skill，效果提升就非常有限。

这说明什么？skill 本身不是万能药。它能起效的前提，是模型有足够强的推理能力，能读懂 skill 的指导内容，能判断什么时候需要去查文档，能正确调用工具，能把查到的信息整合进自己的代码生成过程里。

这其实和我在做 Agent 产品时反复遇到的一个规律完全一致：Agent 系统里，能力的上限永远是模型的推理能力，而不是 prompt 的精巧程度。如果底层推理能力不够，再好的 skill、再精心设计的工具调用序列，都是在沙滩上建楼。

Gemini 2.5 做不到的事，3.1 可以做到。不是因为 skill 对 3.1 更友好，而是 3.1 有足够的推理能力来正确"使用"这个 skill。这个区别非常本质。

在我自己的 Agent 实践里，我也是反复遇到这个问题。早期我们做的一个场景，设计了非常精细的 workflow，给了非常多的工具选项，结果效果很糟糕——直到我们把底层模型换成推理能力更强的版本，很多问题才自然消失了。原来以为是 prompt 的问题，其实是模型的问题。

**这件事让我重新想清楚了 skill 的本质**

我一直在思考一个问题：skill 和 MCP（Model Context Protocol）之间到底有什么本质区别？

Google 的这个实验给了我一个新的思考角度。MCP 解决的是"模型怎么调用外部工具"的协议问题——它是连接器，是基础设施。而 skill 解决的是"模型怎么知道该做什么、怎么做好"的能力问题——它是能力单元，是经验的结晶。

类比一下：MCP 相当于 USB 接口，定义了设备之间的通信标准；skill 相当于操作系统里的驱动程序，决定了设备实际能做什么。没有 skill，就算接口再标准，模型也不知道如何正确调用那个接口背后的能力。

Google 的做法其实是在说：给模型一个 skill，不只是给它指令，而是给它一套思维框架——在什么情况下去查文档，怎么解读文档，如何把文档信息整合进代码生成里。这是一种认知层面的增强，而不仅仅是工具层面的扩展。

这个场景我太熟悉了。我在 Claude Code 里构建自己的 skill 体系的时候，也是在做类似的事——不是告诉 AI 每一步怎么做，而是给它一套判断框架，让它能在遇到新情况的时候自己找到正确的处理方式。

最好的 skill 不是"这是正确答案"，而是"这是找到正确答案的路径"。

**评测体系是整件事的基础**

这篇博客里有一个细节我特别欣赏：Google 不是靠直觉说"加了 skill 效果更好"，而是认认真真设计了 117 个测试用例，覆盖 agentic coding、chatbot 构建、文档处理、流式输出、SDK 功能等多个维度，每个 prompt 被严格判断是否用了正确的 SDK。

这个做法和我一直在说的评测驱动开发（eval-driven development）高度吻合。AI 产品不能凭感觉优化，必须先建立评测体系，才能有改进依据。

更值得注意的是，他们不只是跑了"成功率"这一个指标，而是按类别分析了哪个领域的 skill 效果好、哪个领域还有短板。比如 SDK Usage 类的通过率是 95%，低于其他类别——深挖之后发现，有些 prompt 里用户明确要求用旧版模型（"使用 Gemini 2.0"），这是 skill 无法覆盖的情况，因为用户的要求本身就是"要用旧的"。

这种细粒度的失败案例分析，才是真正有价值的评测工作。不是"整体通过率是多少"，而是"哪类情况下会失败，为什么失败"。

我在训练营里反复强调一句话：evaluation is all you need。这不是玩笑，而是我真实的实战体会。一个没有扎实评测体系的 AI 产品，优化方向是盲的，效果改进是撞运气的。Google 这个实验展示了一个非常标准的评测驱动优化范式——先定义什么是"失败"，再大规模测，再分析失败原因，再迭代改进。

**skill 生态的长期挑战**

读完这篇博客，我觉得有一个问题 Google 自己也承认了，但可能还没完全想清楚怎么解决：skill 的更新机制。

目前的做法是，用户手动安装 skill，skill 里的内容是某个时间点的快照。如果 Gemini API 发布了重要更新，skill 本身也需要被更新——但如何通知用户、如何自动更新、如何处理用户工作区里的旧版 skill，这些问题还没有好的答案。

Google 在博客里直接承认了这个问题："长期来看，旧的 skill 信息可能会留在用户工作区里，造成负面影响。"这是一个诚实的承认，也是一个需要长期解决的工程问题。

更有意思的是，他们提到 Vercel 的研究发现：在某些场景下，直接用 `AGENTS.md` 文件注入指令，效果可能比使用 skill 更好。这个发现有点反直觉——skill 被设计为专门的知识注入机制，为什么有时候反而不如一个简单的 Markdown 文件？

我的猜测是：skill 有一层"激活"的开销——模型需要判断是否需要调用 skill，然后激活它，然后读取内容。而 `AGENTS.md` 是直接注入到上下文里的，模型无需主动触发，信息直接可用。对于那些模型已经"差不多知道怎么做"的任务，skill 的触发成本反而成了负担。

这个场景很像我之前说过的一个判断：skill 适合"跨场景、跨用户都需要的最佳实践"，而如果只是特定任务的知识，直接写成 Markdown 文档放在 system prompt 里引用，往往更直接、更可靠。

**我的思考：知识的时效性才是 Agent 时代最被低估的问题**

Google 这个实验，表面上是在讲"skill 有效"，但我认为更深层的 insight 是：在 Agent 时代，知识的时效性管理是一个独立的、被严重低估的工程问题。

我们已经习惯于思考 Agent 的推理能力、工具调用能力、记忆管理能力——但很少有人系统地思考：Agent 如何知道自己的知识是不是过时了？Agent 如何在运行时补充缺失的最新知识？Agent 如何在"我知道"和"我需要去查"之间做正确的判断？

这不是一个模型训练的问题，因为模型的训练截止日期是不可避免的。这是一个系统设计的问题。

从更宏观的视角来看，这其实是一个经典的软件工程问题在 AI 时代的新形式：缓存失效（cache invalidation）。静态训练的知识是"缓存"，而现实世界的文档和最佳实践是"源头"。当源头更新的时候，如何让系统知道缓存已经失效，并且去取最新版本？

Google 的 skill 方案本质上是一个轻量级的缓存失效通知机制——它告诉模型："你在这个领域的知识可能已经过时了，这里是拿最新内容的地址。"这个方案很优雅，也很实用。

更进一步想，这个问题会随着 Agent 系统越来越复杂而越来越重要。当一个 Agent 负责处理跨越多个快速迭代的技术栈的任务时，知识时效性管理将成为系统可靠性的核心挑战之一。今天还是一个 Gemini API 的 SDK 版本问题，明天可能是整个 Agent 编排框架的接口变化问题。

历史上，我们经历过类似的跃迁时刻。PC 时代的软件更新靠光盘，云计算时代变成了自动 patch，但那解决的是软件本身的更新，而不是 AI 认知的更新。我们现在面对的是一个新问题：如何让 AI 的"知识视野"和现实世界的演进保持同步。这是 Agent 工程的一个核心基础设施问题，和工具调用、记忆管理、推理能力一样重要。

28% 到 96%，这个数字背后是一个简单但深刻的教训：让 AI 知道去哪里找真相，比让 AI 自己猜，要可靠得多。这场变革才刚刚开始。

也欢迎大家留言分享你们在 Agent 开发中遇到的知识时效性问题，我很好奇大家是怎么处理的。
