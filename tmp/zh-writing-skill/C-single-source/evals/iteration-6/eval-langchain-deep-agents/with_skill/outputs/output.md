# 你的 Agent 跑得起来，但能活多久？

你有没有想过，一个 Agent 做到能 Demo 的程度，和真正在生产环境里跑起来，是两件完全不同的事？

我最近读到 LangChain 分享的一篇技术文章，讲的是他们在把 Deep Agents 推向生产时，踩过哪些坑、搭建了什么样的底层运行时。读完之后，我脑子里浮现的第一个画面是：有多少团队，花了三个月做出一个令人惊艳的 Demo，却在正式上线后的第一个星期就悄悄下线了。

不是因为他们的模型差，也不是因为 prompt 写得不好——而是他们没有搞清楚一件事：**Agent 在 Demo 里活着，靠的是一次顺利的演示；Agent 在生产里活着，靠的是一整套你几乎看不见的基础设施。**

这篇文章让我坐立不安——不是因为内容本身有多惊悚，而是它把很多我只是模糊意识到、却说不清楚的问题，用非常精准的方式讲透了。

**Harness 和 Runtime，是两件不同的事**

文章一开头就把问题点得很准。他们区分了两个概念：harness（线束）和 runtime（运行时）。

Harness 是你围绕模型建立的一切：prompt 策略、工具集、技能配置、上下文管理。这是大多数 Agent 工程师花精力最多的地方，也是 Demo 能不能打动人的核心。Runtime 则是藏在 harness 下面的那一层：持久化执行、内存管理、多租户、人工审批、可观测性——这些是让 Agent 在生产环境里不崩溃、不泄漏、不失控的保障。

让我觉得关键的是，这两层的分工其实非常清晰：harness 决定 Agent 能不能做好事情，runtime 决定它能不能持续做好事情。

这和我一直讲的"从 Demo 到工业级产品"的路径是完全对应的。我在训练营里反复强调一件事：产品迭代要复刻人类软件产研的完整流程——需求分析、PRD、技术架构规划、实现、单元测试、模块测试、集成测试，每个环节不能跳。真正的问题不是模型够不够强，而是有多少团队从一开始就没有把"运行时层"纳入技术规划。他们的 harness 搭得很精心，runtime 却是空的。

**持久化执行：Agent 生死攸关的地基**

文章里讲得最透的一个点，是"durable execution"（持久化执行）。

理解这个概念需要先想清楚 Agent 和普通 Web 请求的区别。一个普通的 HTTP 接口，处理时间是毫秒级的；一个跑 Deep Research 的 Agent，可能要执行二十分钟。在这二十分钟里，它会调用几十次模型，打开网页，读 PDF，写中间结论——一旦进程崩溃，所有进度全部归零。

更要命的是另一个场景：Agent 在执行中途需要暂停，等人类审批。比如一个财务 Agent 准备执行一笔转账，需要等财务主管确认。这个确认可能在三十秒内到，也可能三天后才来。如果你把一个工作进程锁定在那里等了三天，这个系统根本没法上规模。

LangChain 的解决方案是把每一步的执行状态写进 checkpoint，存在 PostgreSQL 里。每个 thread 有唯一的 thread_id，作为运行的"书签"。进程崩溃了，另一个 worker 捡起来继续跑；人工审批来了，执行从上次停的地方接着走。

这个观点击中了要害。我之前在研究 Claude Code 的子代理架构时，也注意到一个有趣的演进——把"前台/后台"区分出来，本质上就是在解决这个问题：有些任务不应该阻塞主流程，需要异步执行、断点续跑。但我当时没有把这个问题用"持久化执行"这个框架完整地讲出来。LangChain 这篇文章帮我想清楚了为什么这个设计是必须的，而不只是"更好的选择"。

文章说得很直接：持久化执行是整个 runtime 的地基，没有它，后面所有功能——流式输出、人机协作、定时任务、并发控制——全都是空中楼阁。

**短期记忆和长期记忆，不是一回事**

内存管理是另一个让我觉得很多团队犯了经典错误的地方。

大多数人做 Agent 记忆系统时，想的是"怎么把历史对话塞进上下文"。这解决的是短期记忆问题：当前会话里发生的事情，工具调用的中间状态，这一轮的推理链——这些东西确实需要在 thread 内保持。

但长期记忆是另一回事。用户偏好、历史决策、跨会话的经验积累——这些不属于任何一个 thread，不能靠 checkpoint 来存。LangChain 用的方案是一个独立的 memory store，按 namespace 组织（比如 `(user_id, "memories")`），支持语义搜索，存在 PostgreSQL 里，完全归你控制。

说实话，这让我有点不舒服——不是不舒服于这个设计，而是它让我意识到，很多团队做的"记忆增强 Agent"其实只解决了浅层问题：会话内有记忆，跨会话就失忆。用户换个新对话，Agent 就像刚认识他一样。这和真正的"Agent 记住你"差了一个数量级。

文章里说的一句话让我记了很久：**记忆是系统产生的最有价值的数据之一**。这个数据应该放在你控制的地方，你能查、能迁移、能在 Agent 之外用。如果它被锁在某个闭源平台的加密存储里，你才是真正的输家。

**人机协作不是"偶尔让人看一眼"**

Human-in-the-loop（HITL）这个词，我们在 Agent 讨论里说了很多，但真正理解它的设计要求的人，其实不多。

文章里区分了两种核心场景。一种是在 Agent 要执行高风险操作前，给人类一个确认窗口——发邮件、执行财务交易、删除文件，这些不能让模型自己决定。另一种是 Agent 遇到不确定性需要问用户——"我找到了三个配置文件，应该改哪一个？"

这两种场景，都需要 Agent 能真正"停下来"——不是 spinner 还在转、进程还在挂着，而是彻底释放资源、保存状态，等到人类回应后再从断点继续。

LangChain 用 `interrupt()` 和 `Command(resume=...)` 两个原语实现这个机制。有一个设计细节我觉得非常巧妙：`resume` 接受任意 JSON 序列化的值，所以人类的回应不只是"批准/拒绝"——可以是修改过的文本草稿，可以是补充的上下文，可以是下游系统注入的计算结果。这让 HITL 从一个"要不要继续"的开关，变成了一个真正的人机协作通道。

**Agent 越自主，你越需要守门人**

Guardrails（护栏）这部分，文章讲的是中间件（middleware）机制——在每次模型调用前后、每次工具调用前后，注入确定性的传统代码逻辑。

这和我在研究 Claude Code 的 Hook 机制时得到的结论是完全一致的——用传统软件监管不确定性 AI 的唯一靠谱方式，就是在 SDK 层面强制注入。只要 Agent 想调用某个工具，Hook 就一定跑。不是靠 prompt 提醒，不是靠模型"记住"。

文章里举了两个具体例子。第一个是 PII 脱敏：客服 Agent 处理的用户消息里可能含有姓名、邮箱、账号，这些数据不应该出现在模型 context 里，也不应该出现在日志里——必须在每次模型调用前被确定性地清除。第二个是工具调用限额：一个可以调用付费 API 的 Agent，如果没有硬性上限，一个糊涂的模型可以在午饭前调用五十次，把你的预算烧光。

**我在 Agent 工程培训里经常看到一个问题是：**大家喜欢用 prompt 来做安全兜底，告诉模型"不要做 X"、"最多调用 Y 次"。这在 Demo 里有时候管用，但在生产里不可靠。模型是概率性的，安全性必须是确定性的。用中间件做 guardrails，这件事没有退路。

**可观测性不是加分项，是你的调试权**

文章有一段话我认为说得非常准：**你不知道你的 Agent 在生产里会做什么，直到它真正跑起来。**

传统应用你可以从代码推导行为，Agent 不行。它的执行路径取决于模型在运行时的决策：调哪个工具、怎么理解返回值、什么时候判断任务完成。出了问题，你没法靠"读代码"来排查。

LangChain 的追踪系统自动捕获每一步：模型调用、工具调用、子 Agent 执行、中间件钩子，全部有结构化记录。你可以按用户过滤，按成本过滤，按错误状态过滤。出现"Agent 一直在问同一个问题"这类 bug，不需要靠用户的描述来猜——直接看完整执行树，问题在哪里一目了然。

文章还提到了"时间旅行"调试：因为每一步都有 checkpoint，你可以回到 20 步里的第 5 步，修改那时的状态，让后续流程重新展开。这让"调试一个复杂 Agent"变得可控，而不是每次都从头重跑。

更有意思的是他们用这套可观测性系统反过来改进 Agent 本身——在追踪数据里发现模式，针对性调整 harness，最终在 Terminal Bench 2.0 上提升了 13.7 分，而底层模型没有任何改动。可观测性不只是事后排查，它是迭代循环的起点。

**定时任务：Agent 的主动性从哪里来**

这是文章里我觉得最被低估的部分。

绝大多数 Agent 是被动的：用户发消息，Agent 响应。但最有价值的 Agent，往往是主动的。一个夜间运行的研究 Agent，在你睡觉时把行业动态整理好，等你早上打开的时候已经是一份摘要。一个每十五分钟检查一次报警的 on-call Agent，发现异常自动升级，而不是等人类盯着监控。

LangChain 把 cron 任务直接集成进了运行时，定时触发的 Agent run 和用户触发的 run 享有完全一样的持久化、追踪和权限保障。这一点很重要——很多团队做定时任务是另起炉灶，弄一套单独的调度系统，结果可观测性脱节，运行时保障也打折。

**我的思考：我们正在补的是一套真正的 Agent 操作系统**

回头看这整篇文章，我越来越觉得它揭示的不只是一个产品的技术架构，而是整个 Agent 工程正在经历的范式转变——从"模型调用加几个工具"的原型阶段，到需要一整套生产基础设施的成熟阶段。

想想 PC 软件到 SaaS 的跃迁。PC 时代，你只要代码能跑就算交付了；SaaS 时代，你还要对用户隔离、数据安全、99.9% 的可用性、版本回滚负责。这是截然不同的工程复杂度，不是原来的工程师"努力一下"就能做到的——需要一整套新的基础设施思维。

Agent 工程正在经历同样的跃迁。harness 是"让 Agent 能做好事情"，runtime 是"让 Agent 持续可靠地做好事情"。这两件事的难度量级完全不同。现在很多团队卡在这道门槛上——他们的模型调用逻辑很扎实，但持久化、多租户、安全隔离，统统还没有考虑。

而且这个问题会越来越显性。因为 Agent 任务的时长和复杂度都在增加——今天是 Deep Research，明天是 Deep Agents，后天是长达数天的自主工作流。任务越长，每一个基础设施缺口被暴露的可能性就越高。

有一件事我想说得更直接：**并非所有团队都需要自己搭这套 runtime**。LangChain 的这套方案本身就是一个选项，deepagents deploy 把上面所有能力打包进一行命令。但更重要的是——不管你用谁的方案，你需要知道这些东西的存在，知道为什么它们是必需的，而不是等到生产崩了才意识到自己漏掉了什么。

从 Demo 到生产，这不是一段线性的延伸，而是一次跃迁。跃迁需要基础设施，需要思维方式的升级，需要你把整个产研流程跑完，不跳步骤。

这场 Agent 工程的成熟期，才刚刚开始。
