# 细分 Agent 产品，先别急着讲壁垒

很多团队做细分 Agent 产品时，最容易高估自己的时刻，不是 demo 跑不起来。

恰恰是 demo 跑起来了。

模型能回答，工具能调用，页面看起来也像一个完整产品。团队很自然地会觉得：我们已经比通用模型更懂这个行业了。

但我现在会先问一个更冷的问题：你有没有跑过 baseline？

这里的 baseline 不是学术 benchmark，而是同一组真实任务下，通用模型、结构化上下文、skill 和产品方案分别能做到什么程度。这个表不跑出来，很多所谓“垂直 Agent 壁垒”其实只是错觉。

## 真正的对手不是裸模型

我最近看一个电商客服 Agent 的训练营项目，第一版 demo 很顺。用户问退款、物流、优惠券，模型都能给出一段像客服一样的回答。

如果只看 demo，这个项目很容易被包装成“AI 客服助手”。但我们把它拆成 30 个真实高频 case 跑了一遍，结果一下就清楚了。

| 测试对象 | 配置 | 通过数 |
|---|---|---:|
| Baseline 1 | 通用模型裸跑 | 14/30 |
| Baseline 2 | 通用模型 + 结构化知识库说明 | 21/30 |
| Baseline 3 | 通用模型 + 客服 skill | 24/30 |
| 产品方案 | 再加订单状态工具、退款政策版本校验、优惠券规则 API、低置信度转人工 | 28/30 |

这个表最有价值的地方，不是最后的 28/30。

而是中间那一列：加一份结构化知识库说明以后，通用模型已经从 14 个 case 提升到 21 个。再加一份客服 skill，又到了 24 个。

这意味着什么？

如果你的产品只能做到 21 或 24，你就不能说自己证明了“垂直 Agent 产品价值”。你只证明了“这个任务需要更好的上下文”。

这两件事差别很大。

“通用模型裸跑”不是你的真实竞争对手。今天的真实竞争对手，是一个越来越强的通用模型，加上一份写得还不错的结构化上下文，再加一个会查文档、会调用工具的 coding agent。

很多细分 Agent 产品没有跑过这个对照，所以误把“比裸模型强”当成“产品有壁垒”。

## 产品价值藏在最后那 4 个 case 里

这组测试里最值得看的，不是通用模型为什么失败，而是产品方案为什么能多过 4 个 case。

有一个典型失败 case：

用户问：“我这单到哪了？还能不能用之前那个满减券？”

模型裸跑时，它会把两个问题混成一个客服话术：先安慰用户，再说订单正在配送中，再补一句“优惠券以页面显示为准”。听起来没错，但客服系统里这句话不可执行。

因为这里其实有两个不同系统状态：

订单状态要查物流和订单履约系统。

优惠券能不能用，要查这张券的适用范围、订单金额、有效期、是否和当前商品冲突。

结构化知识库能告诉模型退款规则和优惠券规则，但它拿不到这笔订单的实时状态。客服 skill 能告诉模型处理顺序，但它还是无法验证用户这张券到底能不能用。

所以真正的产品增量不是“提示词写得更像客服”。

真正的产品增量是四件事：

第一，订单状态必须走工具，不让模型猜。

第二，退款政策要带版本号，不能让模型用旧规则回答。

第三，优惠券规则要走 API 校验，而不是靠模型记忆。

第四，低置信度时转人工，不强行生成确定答案。

这才是产品方案比 skill 多出来的部分。

如果一个细分 Agent 产品没有多出来这一层，它就只是把一份上下文包装成了产品。

## baseline 表是产品经理的照妖镜

很多 AI 产品讨论会卡在一个很虚的问题上：模型够不够聪明？

这个问题当然重要，但它不是产品经理能独立回答的好问题。产品经理更应该问：

同一组任务里，裸模型能过多少？

加一份结构化说明能过多少？

加 skill 能过多少？

接入真实工具和兜底流程后，能多过多少？

多出来的这些 case，到底是靠模型能力，还是靠产品系统？

这个问题一问，很多产品价值会变得很清楚。

如果结构化上下文已经解决了大部分问题，你的产品就不应该继续卖“我们更懂行业”。你要卖的是权限、状态、流程、审计、人工介入和失败恢复。

如果 skill 能解决大部分问题，你的产品就不能只做一个聊天界面。你要证明自己在真实业务系统里多做了什么。

如果产品方案确实多过了几个关键 case，那这几个 case 就是你的壁垒，不是首页上的那句“行业专属 Agent”。

## 我会怎么判断一个细分 Agent 值不值得做

现在我看细分 Agent 项目，会先让团队填一张表。

| 层级 | 要回答的问题 | 不通过说明什么 |
|---|---|---|
| 裸模型 | 模型自己能解决多少 | 如果已经很高，产品不能只卖“能做” |
| 结构化上下文 | 明确规则和知识后提升多少 | 如果提升很大，问题主要是上下文，不是产品架构 |
| Skill | 加入任务流程和工具说明后提升多少 | 如果继续提升，说明经验沉淀有效 |
| 产品系统 | 接入权限、状态、工具、兜底后提升多少 | 这里的增量才最接近产品壁垒 |

这张表不是为了让文章显得专业。

它会逼团队面对一个事实：你到底是在做产品，还是在给模型补课。

给模型补课也有价值，但它不一定值得做成一个独立产品。真正值得做成产品的，通常是最后那层：业务状态、权限边界、失败处理、人工协作和可追踪的效果改进。

这也是为什么我说，细分 Agent 产品先别急着讲壁垒。

先跑 baseline。

如果你的产品只比裸模型强，你还没证明自己。

如果你的产品比“通用模型 + 结构化上下文 + skill”还强，而且强在关键业务 case 上，你才真的有资格讲壁垒。

否则，你以为自己在做一个垂直 Agent。

实际上，你只是把一份更好的说明书，包装成了产品。
