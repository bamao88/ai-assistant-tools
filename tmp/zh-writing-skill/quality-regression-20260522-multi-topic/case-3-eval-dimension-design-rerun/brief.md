## Viewpoint Core
评测集的维度是「能区分好坏的变量」，不是「应该测的项目清单」。多一个不区分结果的维度，不增加信息，只增加噪声、标注量和放弃率。

## Topic
单个 AI 产品评测目标里，评价维度该怎么定。不是评测体系全貌。

## Why Now
训练营里每期都有人把「大而全多维打分表」当第一版评测方案交上来——这是反复出现的真实共性问题（来源：shopify 答疑、kickoff、YC Mind AMA）。

## Author Right
张和亲手设计过背景虚化评测集、在 AMA 里把 YC Mind 的三维度砍成一维度、长期点评学员评测方案并主张评测驱动。

## Core Claim
评测集维度越多，不是越全面，反而越容易做错——因为大多数人加的维度不是「影响结果的变量」，而是「听起来该测的项目」；正确的维度数量常常是 1 个，是先跑 case 跑出来的，不是开会列出来的。

## Evidence Plan
1. 背景虚化评测集：维度按伸手姿态 / 光线 / 人数分，不按男女老少分（因为性别年龄不区分虚化效果）。【主案例脊柱】
2. YC Mind 招聘搜索：三维度（有用性 / 正确性 / 引用正确性）砍成一维度（检索正确性，召回 top 5）。
3. shopify 答疑：「先看几个 case 常见问题，再断定真正重要的几个维度」「不要预设大而全的评价体系」。
4. kickoff 观察：要求科学多维打分时，十组七组放弃。

## Case Fact Boundary
- **已给事实**：背景虚化的维度划分（单双人 / 前后排 / 伸手与否 / 光线）+ 不分男女老少的理由（伸手姿态影响、小孩更爱伸手）；YC Mind 的三维度→一维度 + 人工标 5 个标准答案 + 召回即成功；shopify「先跑 case 再定维度 / 不要大而全」；kickoff「十组七组放弃」。这些都有明确来源文件，可写。
- **合理产品判断**：多余维度的四条危害机制（信号稀释 / 假精确 / 执行率下降 / 精力错配）——属本文推演，按论点写，不归因给张和原话。
- **不可写的场景补全**：不补提交这两份方案的学员是谁、什么时候交的、当时怎么对话、情绪如何、张和当场什么语气。
- **代表性模式不伪装成最近事件**：来源没给明确时间 / 人物 / 渠道，所以写「训练营里反复见到」「有人交上来的评测方案」「我设计背景虚化评测集时」，**不写**「上周一个学员」「过去两周被问最多」「昨天有个客户」这类时间锚点。

## Primary Case Spine
背景虚化评测集。
- 原始状态：第一反应想把人群按男女老少、不同年龄段铺开成维度，看起来很全。
- 失败证据：性别和年龄根本不改变虚化效果——按它们分，每一格的好坏排序是一样的，维度没有区分力。
- 修改动作：换成真正影响虚化的变量——单双人、前后排、伸手不伸手、光线明暗逆光。
- 结果变化：维度数量没增反减，但每一个维度都能让好坏分开；「小孩更爱伸手」这种真实差异自然落进「伸手」维度，不需要单列年龄。
- 产品判断：维度的资格不是「这件事重不重要」，而是「它变了，结果会不会跟着变」。

## Reader Takeaway
定维度前先跑 5-10 个真实 case，只保留「去掉它、好坏排序会变」的维度；其余的删掉。维度的正确数量经常是 1，不是 5。
