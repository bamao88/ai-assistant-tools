# 你那个细分 Agent，先过这条 baseline 再谈架构

你有没有算过一笔账：你正在做的那个细分领域 Agent，如果今天直接拿 Claude 或者 Gemini，配上一个几百行的通用 skill，能干到你产品的几成？

大部分人没算过。我在训练营里给学员的产品做诊断，最常见的卡点不是技术不会，而是顺序错了。一上来就纠结用什么框架、要不要自建数据库、架构怎么分层，唯独没人先问一句：今天最强的通用方案，已经能把这件事做到什么程度？这个问题不回答，后面所有的工程投入都是在赌博。

最近 Google DeepMind 的 Philipp Schmid 和 Mark McDonald 发了一篇博客，标题叫《Closing the knowledge gap with agent skills》，把这笔账替很多人算了一遍。他们给 Gemini API 做了一个开发者 skill，就一件朴素的事：告诉模型现在有哪些现役模型和 SDK、给几段示例代码、再列出官方文档入口当作 source of truth。然后他们拿 117 道生成 Python / TypeScript 代码的题去测，只要模型用了过时的旧 SDK 就判失败。结果是 gemini-3.1-pro-preview 这个模型，不带 skill 的时候成功率只有 28.2%，带上这个 skill 之后跳到了 96.6%。

我看到这个数字的第一反应不是惊讶 skill 有多神，而是后背有点发凉。因为它精确地量化了一件我这两年一直在跟学员强调、但很多人始终听不进去的事：你产品要对标的那条 baseline，又被悄悄抬高了一大截。

**第一步永远是建 baseline，不是搭架构**

先说清楚我说的 baseline 是什么。

开发任何 AI 产品，第一版一定要先用当下最领先的模型，把 prompt 调好，作为一个基准。有了这个基准，再去和竞品对比，你才知道这个 demo 到底能不能做出来、差距具体在哪、然后才轮到决定要不要换技术栈，要不要上微调、上 RAG。这个顺序我在第一期训练营的第二课就讲过，到现在没变过。

很多人觉得这是废话，真正动手的时候还是反着来。我带过一个做陪伴类产品的学员，方案画得很复杂，要找小说创作的垂直模型来微调。我给的建议是：先别动这些，直接用 Claude 3.5 跑一个第一版，用 system prompt 去模拟竞品的行为，半天就能出来。有了这个 baseline 和竞品一比，如果差距特别大,再去找别的技术方案不迟;如果差距没那么大,你那套微调方案可能根本不必要。产品评测是 AI PM 最重要的技能，要从立项第一天就开始做。

为什么是半天，不是半个月？因为这一步根本不需要写产品。不管你做的是 RAG 还是 Agent，所有工程到最后都是把"系统 prompt 加参考资料加用户输入"拼成一个 prompt 喂给大模型。那你用 ChatGPT Plus 或者对应的对话产品，手动把这三段拼起来发过去，马上就能测出效果，连 API 都不用调。效果不好，就改参考资料、改 prompt，根本不碰代码。这一层验证的成本，低到没有任何理由跳过。

而 Google 这篇博客真正的价值，是它告诉你：这条 baseline 这一年又往上挪了。

**baseline 的位置变了，从裸模型变成了模型加一个 skill**

过去我们说"先用最强模型跑一版"，潜台词是裸模型。你拼个 prompt，看它能做到哪。

现在不一样了。Google 的实验里有个容易被忽略的细节：3.1 Pro 裸模型在那批 SDK 编码任务上只有 28%，3.0 Pro 和 Flash 甚至只有 6.8%。单看这个低基线，你会觉得"模型还不行，这里有我的产品空间"。但只要补上一个轻量 skill，同一个模型直接干到 96.6%。这中间没有换模型，没有微调，没有训练，就是给它接了一份活的文档加上 SDK 指引,再给它 activate_skill 和 fetch_url 两个工具去自己拉最新资料。

这意味着，你今天要对标的 baseline，已经不再是"裸的通用模型"，而是"通用模型加一个几百行的通用 skill"。这条线，是本文我自己的推论，不是 Google 替你下的结论，但数据摆在这儿，推论并不激进。

这件事对细分 Agent 产品的杀伤力，比表面看上去大。很多产品的立项逻辑是这样的：我观察到通用模型在某个垂直场景表现不好，比如它不熟悉某个新 SDK、不懂某个行业的最新规范，所以我要做一个懂这个领域的专用 Agent。这个逻辑在裸模型时代成立，但 Google 的实验恰恰打在它的命门上,模型在某个领域"不懂"，很多时候不是能力问题，是知识过期问题，而知识过期是一个轻量 skill 就能补上的窟窿，根本轮不到你做一个产品。

所以我现在给学员的判据更狠一点：你那个细分 Agent，如果干不过 Claude Code 加一个通用 Skill，那你应该回过头重新想想，是不是你的产品架构、你对 Agent 的理解、你的核心算法框架，已经落后于今天这个 Agent 时代了。这话我是在评估自己做的那个 Excel AI coding agent 时对自己说的，不是站着说话不腰疼。正常情况下，一个架构和 Claude Code 同水平的细分 Agent，是一定能超过 Claude Code 加通用 Skill 的,因为你比它多了领域工具和领域交互。超不过，问题就出在架构本身。

**没有对比，就没有产品判断**

为什么我反复揪着 baseline 不放？因为做产品评测，你得先有"正确答案"，才能判断自己的架构是好是坏。

这两年的黑客松 demo day 上，我批评得最多的一类思路就是"自建数据库"。团队花大量精力去自己攒一个数据库、搭一套自以为很聪明的检索架构，然后兴冲冲来 demo。我经常要泼一盆冷水：你自己想的这套架构，说不定根本干不过那些非常通用的方案。做 deep research 类产品的，我直接建议去把 Open Deep Research 那个开源代码拿来，要么在它基础上改，要么直接复用，然后跟你现在的效果比一比。如果你辛苦搭的架构干不过一个开源的通用方案，那不是细节问题，是说明你的架构哪里出了根本性的问题。

这就是 baseline 的真正用途。它不是一个让你心里有底的参考值，它是一面照妖镜,照出你那些"我觉得很有技术含量"的设计，到底有没有创造出相对通用方案的增量。Google 那 117 道题的评测集也是同一个道理，他们定的失败判据特别干脆,用了旧 SDK 就算失败。判据清楚，对比才有意义,你才知道 28% 和 96% 之间那 68 个百分点，到底是 skill 补回来的，还是模型本来就会。

顺便说一个 Google 自己点出来的边界，免得你以为 skill 是万能解。他们提到 Vercel 的实验显示，直接用 AGENTS.md 给指令，可能比挂 skill 还有效；而且 skill 现在还没有一套像样的更新机制，时间一长，用户工作区里那些过期的 skill 反而可能帮倒忙。这恰恰说明，"通用方案"本身也在快速迭代、互相竞争,你对标的那条线不光高，还在动。你越晚跑 baseline，对标的位置越尴尬。

**把方法论拍成一张你能直接用的表**

讲到这儿，我把上面这些 case 拍成一张表。这不是空模板，是我真的用这套判据给具体产品做过诊断的结果，你可以直接照着套你自己的产品。

| 产品对象 | baseline 用什么 | 怎么搭 | 达标判据 | 我的结论 |
|---|---|---|---|---|
| 陪伴类产品 | Claude 3.5 | system prompt 模拟竞品行为，半天出一版 | 和竞品逐项对比，差距是否大到非换技术栈不可 | 差距不大就别急着上微调，先把 prompt 和资料喂饱 |
| AI 相机辅助 | GPT-4o 高级语音 / Gemini 2.0 Flash | 对着取景器实测，找 10 个不同场景问它怎么拍 | 10 个场景里有 6-7 个建议真正贴合，才算技术可行 | 达标比例上不去，产品化免谈，先验证上限 |
| deep research 产品 | Open Deep Research（开源） | 直接复用或在其上改 | 你的自研架构能否跑赢这个通用开源方案 | 跑不赢说明架构有根本问题，不是调参能救的 |
| 细分编码 / 工具 Agent | Claude Code 加通用 Skill | 同场景跑同一批任务 | 你的细分 Agent 能否超过 CC 加通用 Skill | 超不过，说明架构和 Agent 理念可能过时了 |
| 某 SDK 编码助手 | 通用模型加通用 skill | 参考 Google：补活文档加 SDK 指引加文档入口 | 一批真实任务的成功率（用旧写法即失败） | Google 实测从 28% 抬到 96%，你的增量必须建在 96% 之上 |

这张表最关键的一列是最后一列，结论。前面四列是动作，最后一列才是产品判断。我见过太多团队跑了对比、出了数字，然后就把数字放进 PPT 当业绩，没有逼自己回答那个最难的问题：这个对比说明我该继续做，还是该重做，还是该放弃？

填这张表的时候，我建议你对自己狠一点。达标判据要在动手前就定死，别跑完再凑一个能让自己通过的标准。AI 相机那个 6-7 个达标，是先定的门槛,不是测完发现"诶好像有六个还行"才补的。门槛先定，对比才有约束力。

**那"我有私有数据"这个挡箭牌呢**

我知道有人要反驳：我做的是垂直领域，我有别人拿不到的私有数据、有行业特有的工作流，通用方案根本比不出来这一层。

这个反驳一半对，一半是逃避。

对的那一半是：私有数据和深度工作流，确实是通用 baseline 短期补不上的东西，这也是细分产品真正该建壁垒的地方。但逃避的那一半是,你不能用"我有私有数据"来豁免跑 baseline 这一步。恰恰相反，你更要跑，因为你得知道:在你那份私有数据真正发挥作用之前，通用方案已经免费帮你做到了几成。如果通用方案靠公开知识已经做到很高比例，你那份私有数据只多带来个位数百分点的增量，这点增量未必撑得起一个独立产品，你更适合做成一个挂在通用底座上的 skill 或者插件。

这不是我臆想的场景。我带过一个在股票分析场景做了很多 skill 的学员，skill 攒了一大堆，技术上都能跑，但用户就是用不起来。问题不在 skill 本身,在于 skill 只是内部工具,你总不能让用户先去装 Claude Code、再学着用你的 skill。用户要的是一个端到端的产品。只做 skill 形不成壁垒，也没法收费，做着做着就得往 web、往 APP 上走，把 skill 和 Agent SDK 包成一个完整产品，才卖得动钱。

反过来，真正聪明的细分做法，是为通用底座封装它现场写不稳的那部分。比如 Excel 场景，光靠模型现场生成 VBA 不可靠，那就封装一个 Execute VBA 的工具，让模型生成的代码能被第三方稳定触发执行。这种增量是 baseline 比得出来的,有了这个工具，成功率涨了多少，一测便知。这才是细分产品该花力气的地方，而不是去重做一遍模型已经会的事。

说到底，Skill 这个东西的本质，并不是什么 Anthropic 或者 Google 的专有魔法。它就是"结构化的 Prompt 加文件系统加工具调用"这么一个设计模式，任何支持工具调用的模型都能实现。Google 这篇博客的全部意义，不在于教你怎么写 skill，而在于它用 28% 到 96% 这个落差，硬生生把"通用方案的能力天花板"这件事，摆到了每一个想做细分 Agent 的人面前。

所以回到开头那笔账。动手做你那个细分 Agent 之前，先花半天，用今天最强的模型加一个通用 skill，搭一条 baseline，定下 10 个场景的达标判据，跑一遍。跑得赢，恭喜你，你找到了真实的产品空间，接下来每一行架构代码都花得值。跑不赢，那省下来的不只是几个月工程，是你对这件事到底有没有壁垒的清醒判断。

baseline 不会替你做产品，但它会在你投入之前，诚实地告诉你这仗还值不值得打。
