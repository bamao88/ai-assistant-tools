# 我在小米踩过上亿的坑：到了 Agent 时代，评估是 AI PM 躲不掉的基本功

先说一个我自己花了上亿才换来的教训。

当年在小米做自动驾驶的数据闭环，几百人的团队，上亿的预算，我们把绝大部分精力都压在了训练集上。多收数据、多标数据、多喂给模型，听起来天经地义。结果呢，效果就是上不去，我们也说不清到底卡在哪。

后来我去拆特斯拉怎么干，发现一个让我后背发凉的细节：在他们那儿，AI 测评的负责人和数据引擎的负责人，是同一个人，而且直接向马斯克汇报。换句话说，人家把「怎么衡量模型好不好」当成了和「怎么把模型练出来」同等重要、甚至更靠前的事。我们是反过来的。

这件事我反刍了很久，最后想明白一句话：**在 AI 里，评测的权重应该和研发五五开，而不是传统互联网那种二八开。** 互联网产品你功能做出来、跑通流程、上线就行，质检是测试岗收尾的活。AI 产品不是，它是个黑盒，你不实际测，根本不知道它在什么概率下、什么场景下会出什么妖蛾子。

这几年我带训练营，把这套方法论讲了几十遍。但到了 Agent 大行其道的今天，我的判断又往前走了一步：评估已经不只是「方法论」了，它正在变成 AI 产品经理躲不掉的基本功。而且我越来越觉得，一个 AI PM 的水平上限，基本就等于他建评测体系的水平——不是他需求文档写得多漂亮，也不是他背了多少模型原理。

## Agent 把链路拉长，「只看最后那个答案对不对」就彻底失效了

为什么偏偏是 Agent 把评估逼成了基本功？

因为 Agent 把链路拉长了。一个传统功能，输入 A，期望输出 B，对就是对、错就是错，你盯着最后那个结果就行。但一个 Agent 干活，中间要规划、要调工具、要检索、要根据一轮结果改下一步计划，可能来回好几轮。这种形态下，你只盯着它最后吐出来的那段话，会漏掉一大堆东西：它工具调用对不对、检索路径走偏没有、是不是反复试错烧了一堆 token、有没有在某一步就埋下了下次崩溃的雷。

一个最终结果看起来对的 Agent，它的运行轨迹里很可能已经写满了下一次会崩的理由。你只看输出，这些全看不见。

这不是我一个人的体感。真正在一线做 Agent 的工程团队，思路是一致的：Anthropic 在自己讲 agent 评估的工程文章里，明确把「轨迹」（trace、transcript，也就是一次运行的完整记录：输出、工具调用、推理过程、中间结果全在里面）当成评估的起点，而不是只对最终答案打个分。LangChain 那边做 agent 评测，干脆把它拆成三个粒度：只看最终回答的、看整条工具调用轨迹的、和把某一个单步拎出来单独评的。

你看，业界已经用脚投票了——评 Agent，得评过程，不能只评结果。

## 想看见过程，前提是你先把过程「录」下来

那怎么才能看见过程？前提是你得先把过程记下来。

我在训练营里反复强调一件听起来很工程、但产品经理必须懂的事：评测能跑起来，靠的是 trace 这个模块。你得有办法把这个 AI 应用执行的整条日志先拉下来——用 OpenTelemetry 这种开源规范就能做，只要你的 Agent 平台支持它，运行时的 tracing 数据就能导出来。有了这条日志，你才能去分析：router 路由对不对、skill 选得对不对、planner 规划对不对、memory 召回对不对。

记下来之后的流程其实很朴素：攒一个评测集，批量跑任务，把模型结果和人工标注对比，在几千条里快速筛出那几十条不一致的，然后一条条去看它为什么错。本质上，这就是一个不断从混乱日志里挖数据、定位失败模式的过程。

这里我要泼一盆冷水，也是我自己最深的教训：**别一上来就改 prompt。** 我见过太多团队，看到效果不好，手就痒，立刻去调 prompt。结果既不知道原来的能力边界在哪，也不知道自己改对了没有。正确的顺序是先看懂——看够日志，理解每个 Agent 的上下文窗口到底是怎么拼起来的、哪个环节信息最多、哪步最容易崩。我给的硬指标是先看够 200 条。look at your data，最重要的事就是坐下来，老老实实看一两百条真实的输入输出。

## 成熟的 Agent，要养两套评测集

光有一套评测集还不够。一个真正成熟的 Agent 产品，得同时养两套。

一套是端到端的，从用户场景层面覆盖：中文的英文的、简单的复杂的、带语音的不带语音的，模拟真实用户怎么用。另一套是模块专属的，跑某个模块的时候把别的屏蔽掉，单测它——比如只测工具调用准不准。千万别只做端到端，那样你看不到中间过程，出了问题只能干瞪眼。这跟前面说的「评轨迹」是一回事：端到端给你最强的整体信号，但要定位到底是哪个 Agent、哪一步出的问题，你必须能下钻到单模块、单步去看。

评测集还有个反直觉的地方：它的难度分布不该和真实世界一样。真实世界可能 99% 是简单 case，但你的评测集得故意把困难 case 的比例放大——简单的留个六七成就够，剩下的留给有难度的和极端的。这跟高考命题一个道理，全是送分题就没有区分度了。评测集贵也贵在这儿，标一条评测 case 的成本，是标一条训练数据的两到三倍，因为它要的是区分度，不是数量。

而且评测集永远穷尽不了业务场景，它是持续进化的。这周你觉得这些场景难，下周多跑几个 case 又发现新的盲区。它不是上线前做完就扔的一次性质检，是跟着产品一起长大的资产。

## 这件事，本来就该 AI PM 来抢

讲到这儿，最该说清楚的是：这一整套，到底归谁管。

我的态度很明确——这是产品经理的活，而且你要主动去抢。硅谷那些顶尖团队早就形成共识了，产品经理一定要做评测，连设计师都得做评测。原因很简单：评测有极强的牵引力。你只要能定期输出一份专业的测试报告——相比竞品平均分多少、分场景分维度的量化对比、带着真实 case 截图——你就能驱动整个团队。研发自己会去找优化方案，你负责告诉他们「往哪个方向使劲」。这个牵引模块要是交出去了，你这个 PM 就被动了。

很多人不敢碰，是觉得评测太「技术」、太苦。这里我也要给一颗定心丸：**别被「科学打分」吓退。** 我带组的时候发现，一旦要求大家做严格的多维度量化打分，十个组里有七个会喊「太难评了」然后放弃，这是最大的浪费。我的建议是，先干起来——每人测五个 case，用你自己的脑子、自己的主观感受，把优劣排个序，能讲清楚谁好谁差就行。干了，你就赚了；定性分析出来了、有体感了，比什么都强，科学化是后面慢慢补的事。

但有一条不能省：一定要亲自看原始 case，别只看那张统计图、别信 benchmark 跑分。我自己的经验是，测 10 个 case 你的认知大概是 55 分，测到 100 个能上 80 分，再往上还会涨。所谓困难 case、benchmark 分数，离开了你亲眼看过的一个个具体 case，基本没用。

## 它能把你从 40 分推到 95 分，但救不了「选题本身太难」

最后说说边界，免得把评估讲成万能药。

训练营里有个特别典型的例子：学员做一个自然语言下单的快递助手，默认状态下成功率可能就 40%、50%，根本没法上线。从这个数到能上线的 95%，靠的不是再加几个炫酷功能，而是评测驱动——一轮轮测出哪类 case 在崩、改架构、补异常处理、调 API。这个把成功率啃上去的过程，又苦又不性感，但它才是真正体现一个 AI PM 能力的地方，也是你面试时唯一能讲出血泪的环节。

可评估也有它够不着的地方。它是给普通团队兜底的方法论，能帮你把一个本来能做成的事扎实做成；但它替你解决不了「选题本身就太难」的问题。这也是为什么我一直说，评估重要，但它前面还有选题判断和技术边界判断——这些是另一篇要聊的事了。

回到开头那上亿的坑。如果你现在做 AI 产品、尤其在做 Agent，今晚就可以干一件事：别急着改任何 prompt，先想办法把你那个 Agent 的运行轨迹完整拉下来，挑 20 条真实 case，一条条看它中间到底在干什么。看完你大概率会发现，你以为你懂你的产品，其实你只是懂它的最终输出。
