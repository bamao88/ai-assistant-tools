# 做细分 Agent，先跑 baseline：一条 14→28 的曲线说明了什么

做细分 Agent 的人，立项第一件事八成是纠结技术栈。要不要上 RAG，要不要微调一个垂直模型，要不要先搭一套多 agent 编排。我的看法一直很简单：这些都是第二步。第一步是先把 baseline 跑出来。

baseline 不是个仪式，跑完打个勾就算数。它是你早期唯一靠得住的那把尺子，量的是三件事：这个产品到底能不能做、现在离能用差多远、接下来力气该往哪使。没有这把尺子，你后面所有的技术决策都是在猜。

我手上正好有一条很干净的曲线，来自训练营一个学员做的电商客服 Agent。我把它完整摆出来，因为它几乎把「为什么要先跑 baseline」这件事讲透了。

## 14/30：这就是你的起跑线，难看也得认

这个学员先做的事很对：他固定了 30 个真实 case，覆盖退款、物流、优惠券三类最常见的问题，然后直接用通用大模型裸跑，什么都不加。结果是 30 个里成功了 14 个。

差不多一半。

很多人看到这个数字第一反应是失望，觉得是不是模型不行，是不是该赶紧上点别的技术。我恰恰觉得这一步是整件事里最有价值的。因为这 14/30 是你第一个可信的坐标。在此之前，你对这个产品能不能做的所有判断都是体感；有了这个数，你才第一次知道纯靠模型的语言能力和通用理解，你能拿到的底分大概在哪。

我在课上反复讲过一个动作：做任何 AI 产品，先用今天最强的模型，找 10 个 case，看它给出满意结果的比例是多少。比例够高，技术可行性就成立，再谈产品化；比例太低，再多的工程也救不回来，这事可能根本不该做。30 个 case 过 14 个，是个尴尬但有救的位置：它说明模型听得懂客服这摊事，只是还差得远。值得继续投入，但绝不能这么上线。

关键在于，这个起跑线一旦立住，后面每加一样东西，你都能算出它到底值多少分。

## +7：知识库补的是「它不知道你家的规矩」

学员第一个动作，是加了一份结构化的知识库说明。成功数从 14 涨到 21，加了 7 个。

这 7 分涨在哪，是有讲究的。裸跑时模型失败的相当一部分 case，不是因为它不会说话，而是因为它根本不知道你家的退款规则怎么定、物流口径怎么算、优惠券有哪些限制。这些东西不在模型的知识里，它再聪明也只能编。把这套规矩结构化地喂给它，等于把「不知道」补成「知道」，这一类失败自然就被收掉了。

所以这 +7，验证的是一件事：原来卡住的失败里，有很大一块是知识缺口，不是能力缺口。这个判断很重要，因为它直接告诉你下一步该往哪走。如果你跳过 baseline，上来就纠结要不要微调，你根本分不清自己是在补知识还是在补能力，很可能花大价钱微调了半天，解决的其实是一个喂文档就能解决的问题。

## +3：skill 补的是「它不知道该按什么步骤来」

第二个动作是加 skill，把处理这几类问题的标准流程固化下来。成功数从 21 到 24，加了 3 个。

增量明显变小了。这件事本身就是信号。

到这一步，模型已经知道你家的规矩（知识库给的），也知道遇到退款、物流、优惠券大概该按什么步骤走（skill 给的）。这 +3 说明，固化流程确实还能再收一批失败，但剩下的失败已经不是「不知道知识」或「不知道流程」能解释的了。换句话说，靠往模型嘴里喂更多文本，你能拿的分快见顶了。

我一直跟学员强调一个朴素的对照：如果你的细分 Agent 干不过 Claude Code 加一个通用 skill，那你该重新想想是不是架构本身落后了。反过来，当你把知识库和 skill 都加齐，分数却只是温和地往上爬，这通常不是说明你不够努力，而是说明你撞到了另一类问题的墙。这堵墙，不在文本里。

## +4：最后这段，是工程抬上去的，不是换模型换出来的

真正上线前，学员加了三样东西：一个能查订单状态的工具、一条低置信度就转人工的兜底规则、一个退款政策的版本校验。成功数从 24 到 28。

注意这一段的增量,跟前面性质完全不一样。前面加的是知识和流程，喂的都是文本；这一段加的是真实系统状态的接入和对不确定性的兜底，没有一样是靠让模型「更懂」实现的。订单状态工具，是把模型从「猜这个订单到了哪」变成「去查这个订单到了哪」；低置信度转人工，是承认有些 case 模型本来就不该自己拍板；版本校验，是保证它引用的退款政策不是过期的那一版。

这三样，工程味十足，跟换模型、上 RAG 没什么关系。但恰恰是它们，把分数从 24 推到了 28，逼近了可上线的水平。

如果把整条曲线连起来看：知识库 +7，skill +3，工程 +4。前两段是在补模型的「认知」，越补边际越小；最后一段切换到补产品的「工程」，又拿回一个不小的增量。这条曲线我的解读是，细分 Agent 可靠性的天花板，很大程度上是工程抬上去的，不是靠换一个更强的模型换出来的。而你能看清这一点，唯一的前提就是你从头跑了 baseline，每一段增量来自哪你都拎得清。

## 那个最典型的失败，根本不是模型笨

这条线里有一个特别值得说的失败 case：用户在一句话里同时问订单状态和优惠券限制，模型把这两个系统的状态混在了一起，答出来的东西是错的。

这种 case 很容易被误读成「模型不够聪明」，然后被拿去当上微调、换大模型的理由。但我倾向于换个角度看它。模型答错，不是因为它理解不了「订单」和「优惠券」这两个词，而是因为在没有真实状态接入的时候，它手里压根没有这两个系统各自的真实状态，只能靠语言把两件事脑补到一块儿去。它缺的不是智力，是同时持有两个系统真实状态的能力。

这其实是个状态和编排的问题，不是模型能力的问题。这也是为什么前面加订单状态工具能直接见效：你把真实状态喂进去，模型就不用靠脑补了。如果把这类 case 误判成模型问题，一头扎进微调，大概率是白费力气，因为你修的根本不是出问题的地方。

顺带说一句，这也是我一直不主张随便把任务拆成一堆子 agent 的原因之一。状态这东西一旦被切散，分给不同的环节各拿一块，谁也看不到全局，最后混在一起的概率只会更高。能让主流程一次性看见的状态，就别拆出去。

## 所以，先跑 baseline 到底在防什么

把这条 14→21→24→28 的曲线倒过来看，baseline 真正的价值就清楚了：它是唯一能帮你把「模型能力不够」和「产品工程没做」这两件事分开的工具。

没有 baseline，你看到客服 Agent 答得不好，第一反应往往是怀疑模型，于是去赌技术栈，上 RAG、上微调。有了 baseline，你能看清这些失败里哪些是知识缺口（喂文档解决）、哪些是流程缺口（skill 解决）、哪些是状态和兜底缺口（工程解决）。这三类问题的解法天差地别，赌错方向的代价不小。

这里要说清楚边界：先跑 baseline，不等于不上 RAG、不做知识库。恰恰相反，这个学员的知识库实实在在地贡献了最大的一段增量。我反对的不是这些技术，而是在没有 baseline 的情况下凭感觉选技术栈。该上 RAG 的时候上，但你得先用 baseline 证明你卡住的真是知识检索，而不是别的什么。

如果你现在正在做一个细分 Agent，立项第一周别急着争论技术选型。先固定一组真实 case，用最强通用模型裸跑出一个底分；再一样一样地加东西，每加一样都记下它换来了多少分。等这条曲线画出来，下一步该补知识、补流程还是补工程，曲线自己会告诉你，比任何人拍脑袋都准。
