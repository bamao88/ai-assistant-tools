## Core Claim
细分 Agent 早期最该先做的不是技术选型，而是跑 baseline；因为多数团队在没有 baseline 时，会把「产品工程没做」误判成「模型能力不够」，于是一头扎进 RAG 或微调，而真正卡住可靠性的往往是状态接入和不确定性兜底这类工程问题。

## Evidence Plan
- 主脊柱：某训练营学员客服 Agent 的 14→21→24→28 曲线（30 个退款/物流/优惠券 case）。
- 分段增量解读：知识库 +7、skill +3、上线前工程动作 +4，增量来源逐段变化。
- bad case：订单状态与优惠券限制混在一起，归因为状态/编排问题。
- 张和方法可核查表达：找 10 个 case 看比例、先效果再难度、先 baseline 再换技术栈。

## Case Fact Boundary
- **已给事实（可直接写）**：30 个 case 覆盖退款/物流/优惠券；裸跑成功 14；加结构化知识库说明后 21；加 skill 后 24；上线前加订单状态工具、低置信度转人工、退款政策版本校验后 28；最典型失败是用户同时问订单状态和优惠券限制、模型把两个系统状态混在一起。
- **合理产品判断（可写，须用推演措辞）**：每段增量说明模型缺什么；bad case 是状态/编排问题不是智力问题；baseline 的用途是分开模型问题和工程问题；后段增量靠工程而非换模型。
- **不可写的场景补全（禁止）**：学员当时的对话、情绪、是否慌、有没有问要不要上 RAG；张和当场怎么回应、说了什么；客户或老板的反应；学员团队规模、上线后线上表现等任何未提供细节。涉及张和判断时一律写成「如果这时……我的判断会是……」，不写成现场发生过的互动。

## Primary Case Spine
- 原始状态：通用模型裸跑，30 个 case 过 14（约一半）。
- 失败证据：最典型 bad case 是订单状态与优惠券限制被模型混在一起。
- 修改动作：加结构化知识库（→21）、加 skill（→24）、上线前加订单状态工具 + 低置信度转人工 + 退款政策版本校验（→28）。
- 结果变化：14→21→24→28，三段增量分别为 +7、+3、+4。
- 产品判断：知识库补的是「不知道你家规矩」，skill 补的是「不知道处理流程」，最后一段补的是工程（真实状态 + 不确定性兜底）；可靠性的天花板是工程抬上去的，不是换模型换出来的。

## Reader Takeaway
