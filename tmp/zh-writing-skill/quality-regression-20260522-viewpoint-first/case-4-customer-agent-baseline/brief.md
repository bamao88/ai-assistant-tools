细分 Agent 是当下最热的项目方向，但多数人开局就陷在调 prompt 里；训练营这一期正好有个电商客服 Agent 的真实案例，把这条路径完整跑了一遍。

## Author Right
张和长期教「先 baseline、看比例、再换技术栈」；本期训练营学员的真实案例曲线和 bad case 作为一手证据。

## Core Claim
跑 baseline 不是为了证明「能做」，是为了把模型能力问题和产品工程问题分开——这条 14→28 的曲线里，真正的产品壁垒在 24 分以后，而那一段恰恰是 prompt 和 skill 修不动的。

## Evidence Plan
- 主曲线：通用裸跑 14 → 加知识库 21 → 加 skill 24 → 加工具/转人工/版本校验 28（30 个 case）。
- bad case：用户同时问订单状态和优惠券限制，模型混淆两个系统状态。
- 一张填好的「增量归因表」：每段提升对应模型缺的是什么、该用什么补。
- 张和方法判断：先 baseline、找 10 个 case 看比例、再换技术栈。

## Primary Case Spine
- 原始状态：通用模型裸跑（system prompt 模拟客服），30 个退款/物流/优惠券 case，看起来能跑。
- 失败证据：只过 14 个；最典型的失败是订单状态+优惠券限制混在一起答。
- 修改动作：加结构化知识库说明（→21）、加 skill（→24）、上线前加订单状态工具+低置信度转人工+退款政策版本校验（→28）。
- 结果变化：14→21→24→28，增量逐段递减又在最后一段反弹。
- 产品判断：前半段靠喂知识（模型不知道你的事实），后半段靠接系统状态（模型拿不到实时真相）；真正壁垒在后半段，prompt 和 skill 到不了。

## Reader Takeaway
开局先跑 baseline、固定一组 case；按「增量归因表」判断每一分提升来自哪、下一步该加知识、加 skill 还是接系统状态；别把所有力气押在调 prompt 上。
